# Девконтейнер homelab

Образ для работы с манифестами и локальных гейтов. Он собирается из
[`Dockerfile`](Dockerfile), список версий — в нём же, хэши скачиваемых
артефактов — в [`tools.tsv`](tools.tsv), скачивание и проверку хэша делает
[`install-tool.sh`](install-tool.sh).

## Зачем он нужен

Локальные гейты (`.githooks/`, `scripts/check.sh`) на хосте собираются из
Homebrew и Rancher Desktop, и версии инструментов там ничем не закреплены. Гейт
от этого не перестаёт работать, но перестаёт значить одно и то же: `kube-linter`
другой версии находит другой набор проблем, `gitleaks` другой версии — другой
набор секретов, и зелёный локальный прогон расходится с зелёным CI. В образе
версии те же, что в `artifacts.tsv` и в workflow, поэтому расхождение вердикта
между контейнером и CI остаётся только у самих инструментов.

Образ даёт одну среду на любой машине, включая ту, где нет Homebrew и Rancher
Desktop. Кластер для него не нужен: это инструменты для файлов в репозитории.

## Что в нём есть

- `kubectl`, `helm`, `kustomize` — прочитать, отрендерить и проверить манифест
  без обращения к кластеру (`--dry-run=client`, `helm template`, `kustomize build`).
- `kubeconform`, `kube-linter` — те же проверки манифестов, что в гейтах.
- `shellcheck`, `actionlint`, `gitleaks`, `commitlint` — те же проверки скриптов,
  workflow, секретов и сообщений коммитов, что в гейтах и хуках.
- `bun` — пакетный менеджер репозитория; `commitlint` поставлен глобально, чтобы
  `.githooks/commit-msg` находил его в `PATH`, как описано в
  [`docs/agents/commit-conventions.md`](../docs/agents/commit-conventions.md).
- `jq`, `yq` — разбор вывода и манифестов руками.
- `git`, `sudo`, `curl`, `unzip`, `zsh` — обычные пакеты из архива Ubuntu.

## Почему база — `ubuntu:26.04`

Сначала базой была `mcr.microsoft.com/devcontainers/base`, и она занимала 730 МБ
из 1.8 ГБ образа: внутри gcc, cargo, perl, locales, конфиги zsh и собранный из
исходников git (`/usr/local/libexec/git-core` — 133 МБ). Из этого набора гейтам
нужен только git, а он есть в архиве Ubuntu в той же версии. Обычная
`ubuntu:26.04` даёт 134 МБ, и весь образ становится 895 МБ вместо 1.8 ГБ.

Цена решения: компилировать что-то внутри контейнера нечем (нет gcc, cargo,
perl), локаль — `C.UTF-8` вместо `en_US.UTF-8`, нет `devcontainer-info` и
метаданных фич в лейбле образа. Ничем из этого гейты не пользуются; если
понадобится — ставится apt-пакетом или фичей.

Встроенный в образ пользователь `ubuntu` (uid и gid 1000) переименовывается в
`vscode`, чтобы `remoteUser` остался прежним: контейнеру нужен не root, а имя
пользователя — часть контракта с редактором.

## Чего в нём нет и почему

- **`terraform` и `ansible`.** IaC-слой запускается только с macOS: приватный
  слой (`terraform.tfvars`, state) в контейнер не попадает, а без него
  `terraform plan` бессмысленен. Тянуть в образ инструмент, которым нельзя
  воспользоваться, — только видимость покрытия.
- **Доступа к кластеру.** Ни `kubeconfig`, ни Vault-токена: образ не монтирует
  ни `~/.kube`, ни хостовый `$HOME`. Расширять периметр из
  [`information-handling.md`](../docs/agents/information-handling.md) ради
  контейнера, который проверяет файлы в git, незачем.
- **`k9s` и подобных интерактивных клиентов.** Им нужен кластер, которого у
  образа по построению нет.

## Как пользоваться

Через VS Code или `devcontainer` CLI — репозиторий монтируется в контейнер, а
`postCreateCommand` включает хуки (`core.hooksPath`):

```sh
devcontainer up --workspace-folder .
```

Без devcontainer CLI — обычной сборкой:

```sh
docker build -t homelab-devcontainer .devcontainer
docker run --rm -it -v "$PWD:/workspaces/homelab" -w /workspaces/homelab \
  homelab-devcontainer ./scripts/check.sh
```

Хуки внутри контейнера работают те же, что и на хосте: `.git` примонтирован
вместе с рабочим деревом, `core.hooksPath` выставлен на `.githooks`.

## Хостнейм и расширения

Контейнер поднимается с фиксированным хостнеймом `homelab` (`runArgs` с
`--hostname`): без этого Docker даёт имя из id контейнера, и приглашение в
терминале выглядит как `vscode@0ee0ad8d4b85:/workspaces/homelab$`. Имя одно на
проект и не претендует на уникальность: контейнер один.

Расширения редактора перечислены в `customizations.vscode.extensions` и
ставятся редактором при подключении — CLI их не устанавливает. Критерий отбора
один: расширение должно работать в этой среде. Поэтому здесь YAML и Kubernetes
для манифестов, `shellcheck` для скриптов (бинарь есть в образе), `git-graph`
для истории, cSpell с русским словарём (в `.vscode/settings.json` уже лежит
`cSpell.words`, без расширения он ничего не значит), mermaid для диаграмм в
README и rainbow-csv для `*.tsv`. Расширений, которым нужно то, чего в образе
нет, в списке нет: Terraform (IaC живёт на macOS), Docker (докера внутри нет),
GitHub Actions (CI в Forgejo).

## Git внутри контейнера

Личность git приезжает **копией** хостового `~/.gitconfig`: расширение
Dev Containers копирует его само (настройка `dev.containers.copyGitConfig`,
включена по умолчанию) и дописывает туда credential helper, который берёт
учётные данные у хостового VS Code. Поэтому коммит внутри контейнера подписан
правильно, а ключи и агент для этого не нужны.

Личный глобальный игнор копируется только строкой `core.excludesfile`, а сам
файл лежит вне воркспейса и в контейнер не попадает. Поэтому правила про мусор
операционной системы живут в `.gitignore` репозитория: в контейнере, в CI и в
любом другом клоне личного игнора нет. Монтировать хостовый конфиг вместо копии
— не выход: абсолютный путь к игнор-файлу останется хостовым, а `git` на
несуществующий exclude-файл отвечает `fatal: cannot use … as an exclude file`.

`git push` по SSH внутри контейнера не работает: в образе нет `openssh-client`,
`~/.ssh` не монтируется, сокет агента не пробрасывается. Remote репозитория —
`ssh://`, так что для пуша из контейнера в образ нужно добавить клиент, а в
контейнер — пробросить `SSH_AUTH_SOCK`.

## Как обновлять версии

- **Инструмент из apt** (`shellcheck`, `kustomize`) обновляется вместе с базовым
  образом: его версия — та, что лежит в архиве Ubuntu. Apt берётся там, где
  версия пакета совпадает с версией в CI, иначе закреплённый артефакт с
  проверкой sha256: у линтера расхождение версий — это расхождение вердикта.
- **Инструмент из закреплённого артефакта** — две правки: `ARG` в `Dockerfile` и
  строки в `tools.tsv` (сначала строка с новым `url`, потом `sha256` оттуда же).
  Каждый инструмент ставится своей инструкцией `RUN`, то есть своим слоем: при
  смене версии пересобирается только он, а не весь набор. Скачивание, проверку
  sha256 и распаковку делает `install-tool.sh`: аргументы — путь в `tools.tsv`,
  `url`, куда положить и, если это архив, путь файла внутри него. Строки для
  amd64 обязаны совпадать с
  [`artifacts.tsv`](../clusters/casa/apps/rustfs/manifests/artifacts.tsv): там
  хэши для CI, здесь — для образа, и расхождение между ними означает, что
  локальный гейт и CI проверяют разные бинари.
- `yq` — исключение из правила про apt: в архиве Ubuntu под этим именем лежит
  другой инструмент (обёртка над `jq`), а не `mikefarah/yq`, поэтому он
  закреплён артефактом.

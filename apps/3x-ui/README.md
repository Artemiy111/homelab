# 3x-ui

3x-ui — веб-панель для управления Xray-core. Она создаёт inbound-подключения,
клиентов и подписки, считает трафик, задаёт лимиты и сроки действия, показывает
активные подключения и экспортирует готовые клиентские конфигурации. Поддерживает
VLESS, VMess, Trojan, Shadowsocks, WireGuard, Hysteria2, HTTP/SOCKS и несколько
транспортов, включая TCP, WebSocket, gRPC и XHTTP.

Проект предназначен авторами для личного использования. Панель получает полный
контроль над прокси-конфигурацией, поэтому её нельзя публиковать напрямую в
интернет. В этом репозитории интерфейс доступен только через локальный Traefik,
а Xray получает один заранее опубликованный порт `8443` по TCP и UDP.

## Подготовка

Из корня репозитория:

```sh
bash scripts/bootstrap-platform.sh 3x-ui
```
> Любые последующие команды `docker compose` этого сервиса требуют того же окружения:
> выполняйте их через `bash scripts/compose-secrets.sh 3x-ui …` или повторным
> `bash scripts/bootstrap-platform.sh 3x-ui`.


Последняя команда удаляет завершившийся init-контейнер, чтобы его окружение с
первоначальным паролем не оставалось в метаданных Docker. При последующих
обновлениях init-контейнер увидит существующую базу и не изменит учётные данные;
после запуска его снова можно удалить той же командой.

Панель будет доступна по адресу, составленному из `XUI_HOST` и
`XUI_WEB_BASE_PATH` в секретах сервиса, например:

```text
https://xui.example.com/<случайный-путь>/
```

Логин и пароль находятся в тех же секретах: `init.sh` генерирует случайный пароль
администратора и случайный URL-путь панели. После первого входа включить 2FA.
Внутренний TLS панели включать не нужно: HTTPS завершается на Traefik.

## Создание первого inbound

Docker публикует только порты, перечисленные в `compose.yaml`; добавленный в UI
произвольный порт сам по себе снаружи контейнера не появится. Поэтому для первого
inbound указать порт из `XUI_INBOUND_PORT` (`8443` по умолчанию). Один порт нельзя
одновременно назначить двум несовместимым inbound-конфигурациям.

Для подключения через интернет отдельно потребуются:

1. NAT на роутере с выбранного внешнего порта на `192.0.2.10:8443` с нужным
   протоколом TCP и/или UDP.
2. Разрешающее правило firewalld на сервере для `8443/tcp` и/или `8443/udp`.
3. Публичный адрес или DNS-имя, доступное клиенту извне.

Не публиковать порт панели `2053`, домен `XUI_HOST` или Traefik `80/443` на
роутере. Если удалённым клиентам достаточно Tailnet, NAT не нужен, но текущая
привязка inbound-порта к LAN-адресу рассчитана именно на перенаправление с
роутера.

## Дополнительные порты и обновление

Для ещё одного inbound добавить в `ports` отдельные TCP/UDP mappings, проверить
`docker compose config --quiet` и пересоздать только этот Compose-проект.
`network_mode: host` намеренно не используется: он открыл бы все порты панели и
Xray на хосте без явного списка.

Обновлять закреплённый тег образа отдельным изменением в `compose.yaml`, после
чего выполнить:

```sh
docker compose pull
docker compose up -d
```

SQLite-база и настройки находятся в `$APPS_STORAGE_PATH/3x-ui/db` и попадают в общий
Restic backup каталога `$APPS_STORAGE_PATH`. `init.sh` закрывает каталоги 3x-ui
режимом `0700`, поскольку база содержит клиентские конфигурации и ключевой
материал.

## Egress-прокси (порт 8440)

На порту `XUI_EGRESS_PORT` (по умолчанию `8440`) работает HTTP forward proxy.
Внутри Xray пересылает трафик через VLESS-подключение на внешний сервер в
другой стране. Локальные приложения могут использовать его как обычный
HTTP-прокси, указывая `http://192.0.2.10:8440` в качестве proxy URL.

Gatus использует этот прокси для:

- Доставки Telegram-уведомлений (Telegram заблокирован в России).
- Мониторинга доступности самого прокси: HTTP-запрос к `api.telegram.org`
  через `client.proxy-url` показывает реальную задержку маршрута.

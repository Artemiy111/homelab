# Alertmanager (демо)

Отдельный Alertmanager поставлен параллельно с Grafana Unified Alerting, чтобы
изучить модель уведомлений Prometheus на живом стенде. В кластере работают три
потока, и все они наблюдаемы в UI Alertmanager:

- Grafana по-прежнему считает все правила и напрямую шлёт уведомления в ntfy —
  этот поток не изменён;
- тот же contact point Grafana дублирует алерты в Alertmanager с лейблом
  `source="grafana"`. Они попадают в приёмник `am-inbox`, у которого нет
  интеграций: видны в UI и API, но не создают второе уведомление;
- vmalert считает 13 перенесённых PromQL-правил (`source="vmalert"`) и шлёт их в
  Alertmanager. Они идут в ntfy, но подавляются inhibit-правилом, если одновременно
  активен тот же `alertname` от Grafana. LogQL-правило осталось в Grafana.

Алерты без лейбла `source` (в том числе отправленные вручную) идут в ntfy по
корневому приёмнику.

## Что он делает и чего не делает

Alertmanager не вычисляет алерты. Правила оценивает Prometheus, vmalert или
Grafana; Alertmanager получает уже сработавшие события по HTTP API и занимается
только тем, что происходит после срабатывания: дедупликация, группировка,
маршрутизация по дереву `route`, подавление одних алертов другими (`inhibit`),
тишины (`silences`) и доставка в приёмники. Поэтому он не знает про PromQL,
дашборды и источники данных — это задача того, кто шлёт ему алерты.

Формат его webhook'а (`receiver`, `status`, `alerts[]`) совпадает по форме с
тем, что отправляет Grafana Unified Alerting, поэтому ntfy с шаблоном
`alertmanager` понимает оба потока. Это совпадение формата, а не общий код:
встроенный notification engine Grafana — не Alertmanager.

## Откуда он берётся

Это отдельный бинарник проекта Prometheus со своим конфигом `alertmanager.yml` и
API `/api/v2`. Как компонент он входит в состав kube-prometheus-stack, но
существует и отдельный чарт `prometheus-community/alertmanager`. Чарт — лишь
способ упаковки Deployment/StatefulSet, Service и ConfigMap; саму модель
уведомлений он не меняет.

Установленный в кластере VictoriaMetrics Operator тоже умеет этот компонент:
CRD `VMAlertmanager` поднимает инстанс, `VMAlertmanagerConfig` описывает его
конфиг, а `VMAlert` шлёт ему сработавшие правила. Здесь выбран автономный
Deployment: в нём виден «сырой» `alertmanager.yml` и весь цикл его чтения, без
генерации конфига оператором.

## Устройство конфига

Конфиг состоит из нескольких независимых частей:

- `global` — параметры, общие для всех уведомлений, например таймаут разрешения
  алерта.
- `route` — дерево. У корня задаются приёмник по умолчанию, ключи группировки и
  интервалы ожидания/повтора; дочерние маршруты уточняют адресата через
  `matchers` по лейблам алерта. Порядок братьев в дереве имеет значение: первый
  совпавший маршрут забирает алерт.
- `receivers` — куда и как доставлять. Приёмник может содержать несколько
  интеграций; здесь используется `webhook_configs` с URL ntfy.
- `inhibit_rules` — при каком совпадении лейблов «сильный» алерт глушит
  «слабый».
- `templates` — свои шаблоны заголовков и тел уведомлений.

Группировка означает, что несколько алертов с одинаковыми `group_by` приходят
одним сообщением, а повторная отправка того же состояния ждёт
`repeat_interval`. Тишины и подавление действуют до доставки, поэтому алерт
может быть активным, но не произвести уведомления.

Тема ntfy не хранится в Git. Конфиг содержит токен-заглушку, а init-контейнер
подставляет значение из Secret'а, который VSO материализует из `kv/ntfy/topic`.
Готовый конфиг живёт в tmpfs пода и пересоздаётся при каждом старте. Новая
Vault-роль для демо не заводилась: переиспользуется Secret `grafana-ntfy` из
юнита Grafana. Это осознанная зависимость между юнитами, приемлемая для демо; для
штатного инстанса нужна была бы своя роль с доступом только к этому пути.

## Ограничения

Состояние (silences и журнал уведомлений) лежит в `emptyDir`: после рестарта
пода тишины исчезают, а список уведомлений начинается заново. Одна реплика без
gossip — это не HA-конфигурация. UI не опубликован наружу, доступ — только через
port-forward. Тема ntfy остаётся открытой в URL: публичный `ntfy.sh` не имеет
контроля доступа, и тема — единственный секрет. В Git и в логи она не попадает,
но лежит открытым текстом в рендеренном конфиге внутри пода, поэтому логировать
его содержимое нельзя.

Дальнейший шаг, когда захочется сравнить модели: направить сюда алерты из
`VMRule`/`VMAlert` или добавить внешний Alertmanager как contact point Grafana —
тогда станет видно разницу между вычислением правил в Grafana и в vmalert.

Проверки и команды — в `RUNBOOK.md`.

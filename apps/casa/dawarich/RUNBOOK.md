# Dawarich: эксплуатация

## Первый запуск

На пустой базе встроенный seed Dawarich создаёт администратора
`demo@dawarich.app` с паролем `safepassword`. Сразу после первого входа измените
email и пароль в настройках аккаунта.

## Проверка

```sh
curl --resolve dawarich.example.com:443:<node1-ip> \
  -fsS https://dawarich.example.com/api/v1/health
```

Health endpoint должен вернуть JSON со `"status":"ok"`.

После раскатки убедитесь, что процесс не под root и что метрики собираются
целиком:

```sh
kubectl -n dawarich exec deploy/dawarich -- id                # uid=1000, не 0
kubectl -n dawarich get pods                                  # все Running
```

Веб и фоновые джобы живут в одном процессе, поэтому у сервиса один под —
`deploy/dawarich`; база, Redis и его экспортёр считаются отдельно.

```sh
curl --resolve dawarich.example.com:443:<node1-ip> -fsS \
  -u netdata:<пароль> https://dawarich.example.com/metrics | grep -c '^sidekiq_'
```

Счётчик больше нуля означает, что метрики Sidekiq попали в `/metrics` веба. Если
их нет, смотреть лог запуска: Sidekiq стартует из Puma после старта веба, и
ошибку видно в логе контейнера, а не в отдельном поде. Проверить также, что
`PROMETHEUS_EXPORTER_ENABLED` не выключен.

Метрики очередей (`sidekiq_queue_latency`, `sidekiq_jobs_waiting_count`) приходят
из того же эндпоинта. Их отсутствие при живых `sidekiq_jobs_executed_total`
означает, что выключен сбор кластерных метрик Sidekiq, а не что очереди пусты.

## Владелец томов

Процесс работает от uid 1000, и столько же владелец томов `storage` и `watched`.
Новые файлы создаются с этим uid, а группе доступ выдаёт `fsGroup`. Если файлы на
томе принадлежат другому uid — типичный случай после восстановления из backup —
загрузки и рендер постеров начнут падать с `Permission denied`. Вернуть владельца
можно одноразовым chown из пода, который умеет писать в том:

```sh
kubectl -n dawarich exec deploy/dawarich -- \
  chown -R 1000:1000 /var/app/storage /var/app/tmp/imports/watched
```

При обычном перезапуске это не требуется: `fsGroupChangePolicy: OnRootMismatch`
поправит права, если корень тома не совпадает с группой пода.

## Обновление

Порядок важен: миграции идут в entrypoint веба, а джобы — в том же процессе,
поэтому обновление версии перезапускает и обработку очередей.

1. Прочитайте release notes. Если меняется схема запуска или набор переменных,
   правки манифестов входят в тот же PR, что и версия образа.

2. Снимите согласованный дамп. Файл содержит историю перемещений — храните его
   вне репозитория, в git он не попадает:

   ```sh
   kubectl -n dawarich exec dawarich-db-1 -c postgres -- \
     pg_dump -Fc -U postgres -d dawarich > ~/dawarich-$(date +%F-%H%M).dump
   ```

3. Проверьте запас на томе базы: миграции раздувают и таблицы, и WAL, а том сам
   не расширяется (инцидент `docs/incidents/0001`):

   ```sh
   kubectl -n dawarich exec dawarich-db-1 -c postgres -- df -h /var/lib/postgresql/data
   ```

4. Мержить и синкать — в тихое время, без запущенных импортов. Миграции берут
   эксклюзивную блокировку на `points` с коротким `lock_timeout`; активная
   запись в таблицу может сорвать их применение и оставить под в рестарте.
   Prune удалённых ресурсов идёт в конце синка, поэтому обновление, меняющее
   схему запуска, какое-то время держит старый и новый обработчики одновременно;
   джобы при этом не теряются — они остаются в Redis.

5. Проверьте результат:

   ```sh
   kubectl -n dawarich get pods
   kubectl -n dawarich exec dawarich-db-1 -c postgres -- \
     psql -U postgres -d dawarich -Atc 'select max(version) from schema_migrations'
   ```

   Версия должна совпасть с последней миграцией релиза, под — быть `Running`,
   health — отвечать `ok`, очереди — разгружаться.

### Откат

Ошибка в манифестах или переменных откатывается revert'ом PR: схема 1.17
аддитивная, и предыдущий образ работает поверх неё. Полное восстановление из
дампа нужно, только если испорчены данные, и делать его следует на остановленном
сервисе, предварительно сняв текущее состояние ещё раз.

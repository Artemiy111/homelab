# Element Admin

Официальная админ-панель Element для стека Synapse + MAS: пользователи, комнаты,
устройства, сессии, OAuth-клиенты и политики в одном UI.

## Зачем она здесь

После перевода Synapse на MAS админ-API из Element Web недоступен: Element Web
входит compatibility-сессией, а такой сессии MAS никогда не выдаёт скоуп
`urn:synapse:admin:*`. Element Admin — штатный UI для этой схемы: он сам
регистрируется в MAS как OAuth-клиент и просит админские скоупы у пользователя,
которому они разрешены.

## Как устроена

Панель — статическая SPA (React) в nginx. Серверной части у неё нет, API она не
проксирует: браузер сам ходит в **Synapse Admin API** и **MAS Admin API**, а
nginx только отдаёт файлы. Единственная настройка образа — имя серверной части
Matrix; всё остальное панель находит через discovery.

Цепочка discovery при `SERVER_NAME` = apex-домен: `/.well-known/matrix/client` на
apex → `m.homeserver.base_url` → `/_matrix/client/v1/auth_metadata` → issuer MAS.
Дальше — динамическая регистрация клиента в MAS, authorization code + PKCE и
запрос скоупов `urn:synapse:admin:*`, `urn:mas:admin`,
`urn:matrix:org.matrix.msc2967.client:api:*`. Поэтому apex обязан отдавать
well-known (иначе панель не найдёт homeserver), а MAS — регистрацию клиентов.

Названия «Synapse Admin API» и «MAS Admin API» здесь означают публичные хосты:
`element.<домен>/_synapse/admin` и `mas.<домен>/api/admin`. MAS отдаёт второй
только если в его публичном листенере включён ресурс `adminapi` — без него на
`/api/admin` ответ `404`, и половина панели пустая.

## Почему нет CORS-middleware

Изначально вопрос стоял так: браузер ходит с хоста панели на два чужих хоста,
значит нужен либо CORS в Traefik, либо маршруты, которые заводят эти API под
хост панели. Не понадобилось ни то, ни другое:

- Synapse отвечает `Access-Control-Allow-Origin: *` на Admin API, на
  `/_matrix/*` и на well-known — проверено preflight-запросом с
  `Origin: https://element-admin.<домен>`;
- MAS ставит `CorsLayer` с `allow_origin(Any)` на роутер Admin API, то есть
  тоже разрешает любой origin.

Вариант с проксированием API через хост панели отпадает и по другой причине:
адреса панель берёт из well-known и auth_metadata, а не из своей конфигурации,
так что подменить их маршрутом нельзя, не подменяя discovery.

## Что решено неочевидно

**oauth2-proxy перед панелью.** Своей аутентификации у панели нет: это
публичная статика, а вход — отдельный OAuth-поход в MAS. Forward-auth закрывает
сам UI (как у Argo CD, Grafana и Longhorn), но **не** защищает Admin API: они
публичны и гейтятся скоупами MAS. То есть oauth2-proxy — это защита от
любопытных, а не граница прав.

**Права администратора живут в MAS.** Признак админа — `can_request_admin` у
пользователя MAS, а не флаг `admin` в таблице Synapse. Флаг в Synapse больше
никуда не проецируется: панель получает токен со скоупом от MAS и уже с ним
ходит в Synapse.

**Проверка здоровья — внутренняя.** Публичный хост закрыт forward-auth и на
`/health` отвечает редиректом на логин, поэтому Gatus ходит на `/health`
сервиса внутри кластера.

## Ограничения

- Одна реплика: состояния у панели нет, но и вторая ничего не даёт — токены
  живут в браузере.
- Панель бесполезна без MAS Admin API: до включения `adminapi` открывается, но
  данные MAS не показывает.
- Пользователь без `can_request_admin` получит отказ MAS на запрос скоупа
  `urn:synapse:admin:*`, а не «пустую панель».
- Токены и сессия OAuth-клиента лежат в `localStorage` браузера: выход из
  панели не отзывает токен в MAS, это делается отдельно.

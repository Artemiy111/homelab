# ntfy (UnifiedPush)

Свой UnifiedPush-дистрибьютор для push-уведомлений Element X на Android. Стенд
обходится без Google: уведомление идёт от homeserver'а прямо на телефон, FCM и
Sygnal в этой схеме не участвуют.

## Как устроено

Участников четверо, и Sygnal среди них нет.

1. Приложение ntfy на телефоне — дистрибьютор UnifiedPush. Оно подписывается на
   топик на этом сервере и держит с ним постоянное соединение.
2. Element X берёт у дистрибьютора endpoint вида
   `https://ntfy.<домен>/up<идентификатор>` и регистрирует в Synapse pusher
   `kind: http` с этим адресом.
3. Synapse при новом событии делает обычный POST на endpoint. `http`-pusher
   Synapse отправляет сам: Sygnal нужен только для протоколов `apns` и `gcm`,
   где требуются credentials Apple и Google.
4. ntfy отдаёт сообщение подписанному дистрибьютору, тот — в Element X, и уже
   клиент рисует уведомление.

Топик — это адрес уведомлений одной установки приложения, `up` плюс случайный
идентификатор, который дистрибьютор придумывает сам. ntfy о Matrix не знает
ничего: принимает POST на топик и передаёт его подписчику. Полезная нагрузка —
стандартный Matrix push JSON (идентификаторы события и комнаты, счётчики), без
текста переписки: push здесь служит сигналом «проснись и сходи за событием», а не
каналом доставки сообщений.

## Модель доступа

Экземпляр закрытый: по умолчанию запрещено всё. Открыта ровно одна дверь —
анонимная запись в топики с префиксом `up`. Иначе нельзя: endpoint приложению
выдаёт дистрибьютор, приложение передаёт его Synapse, и Synapse публикует без
учётных данных — администратор этот адрес заранее не знает. Шаблон `up*` вместо
перечисления конкретных топиков нужен потому, что префикс — соглашение
UnifiedPush, а сами топики появляются на телефоне и в git не попадают.

Чтение анонимно закрыто: открытый read означал бы, что любой, кто узнал топик,
видит поток уведомлений. Поэтому приложение-дистрибьютор входит под учётной
записью ntfy, а её хеш пароля — секрет и в репозитории не лежит.

Открытая анонимная запись — осознанный компромисс: кто знает топик, может
прислать в него произвольное уведомление, и только в `up*`. Топик случаен и
известен лишь телефону и Synapse, поэтому цена ниже, чем у FCM-схемы, где
push-трафик и метаданные уходят третьей стороне.

## Ограничения

- Одна реплика и стратегия `Recreate`. Состояние — SQLite-файл с ACL и
  пользователями — лежит в `emptyDir` и пересоздаётся при рестарте. Терять
  нечего: ACL объявлен декларативно, сообщения не персистятся. Второй под и не
  нужен: подписчик держит соединение с одним.
- Вложения, e-mail и Web Push выключены: для UnifiedPush они не нужны и только
  увеличивают радиус поражения.
- Наружу сервер не ходит, egress разрешён только DNS. Следствие для доставки:
  сообщение ждёт подписчика в памяти ограниченное время, и если телефон офлайн
  дольше, уведомление теряется — Synapse его не повторяет.
- iOS не поддерживается: UnifiedPush там недоступен, нужен APNs и Sygnal.

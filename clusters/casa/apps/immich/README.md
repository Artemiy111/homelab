# Immich

Фотографии и видео. Пароль БД приходит из Vault через External Secrets Operator.

## Системный конфиг: файл в git, а не Terraform

Настройки Immich (OIDC, параллелизм джоб, формат превью, шаблон хранилища, модель
OCR, парольный вход) читаются из файла: `IMMICH_CONFIG_FILE` указывает на
ConfigMap, который kustomize собирает из `manifests/config/system-config.yaml`.
В git лежат только отличия от дефолтов — `defaults` и схема живут в образе, файл
мержится поверх них и проверяется `AdminConfigDto.schema` при старте.

До этого конфиг жил в БД приложения (`system_metadata`), и смена домена стенда
прошла мимо него: `oauth.issuerUrl` остался на выведенном из эксплуатации домене,
вход отвалился при полностью корректных манифестах, а починить его через
интерфейс было нельзя — без OIDC в интерфейс не войти.

Почему не Terraform и не `PUT /system-config`:

- запрос принимает `AdminConfigDto` целиком — 22 обязательных блока
  (`backup`, `ffmpeg`, `image`, `job`, `map`, `oauth`, `server`, `theme`,
  `trash`, ...). Отправка только `oauth` затрёт остальные настройки, поэтому
  пришлось бы держать в конфиге весь системный конфиг Immich;
- авторизация — только API-ключ админа, у него доступ ко всей библиотеке;
- весь системный конфиг попадал бы в state и в plan открытым текстом, а правила
  обращения со значениями — в `docs/agents/information-handling.md`.

Чего это стоит:

- настройки в интерфейсе становятся read-only: Immich помечает конфиг файловым и
  `PUT /system-config` отклоняет, поэтому правки идут только через git;
- Immich читает файл только при старте, поэтому правка конфига — это перезапуск
  пода. Руками его делать не нужно: kustomize собирает имя ConfigMap вместе с
  хешем содержимого файла, ссылка в деплойменте меняется вместе с ним, и под
  перекатывается обычной синхронизацией Argo;
- ошибка в YAML — сервер не стартует вообще, поэтому файл стоит проверять схемой
  из образа до применения.

Секретов в файле нет и быть не может: `oauth.clientSecret` не используется —
приложение `immich` объявлено в Zitadel public-клиентом
(`OIDC_AUTH_METHOD_TYPE_NONE`).

## Роль `admin` из Zitadel

`roleClaim: role` заставляет Immich читать claim `role` из токена Zitadel.
Claim кладёт action `addRole` (`infra/terraform/zitadel/actions.tf`) на триггере
`POST_AUTHENTICATION` — при входе в Zitadel, а не при выдаче токена.

Значение `admin` даёт админ-права в Immich, `user` — обычный доступ.
`autoRegister` создаёт пользователя при первом входе.

Действие на `POST_AUTHENTICATION` нужно именно Immich: этот триггер срабатывает
при входе в Zitadel и кладёт claim в профиль. Headlamp использует другой
триггер, `PRE_USERINFO_CREATION`, потому что apiserver проверяет подпись и
читает claim из самого токена.

## Ревизия ML-моделей

`MACHINE_LEARNING_MODEL_REVISION=v2` выбирает ветку в HF-репозиториях
`immich-app/<модель>`, откуда ML-сервис скачивает ONNX-модели: ревизия уходит в
`snapshot_download`, то есть это не версия образа, а ветка модели. `v2` — тот же
каталог моделей, перевыпущенный в оптимизированном формате: вендор обещает меньше
памяти и времени на инференс при численно совпадающих выводах, поэтому
перезапускать задачи после переключения не нужно. Снять переменную — вернуться на
дефолт `main`.

У OCR на `main` другой источник загрузки: там работает код для старых экспортов, и
модель тянется реестром `rapidocr`, а на `v2` — из HF. Поэтому пустая ветка `main`
в OCR-репозиториях ни о чём не говорит. Проверено на стенде: на `v2` модель
`ESLAV__PP-OCRv5_mobile` ложится в `/cache/ocr/<модель>/v2/`, и задача OCR
возвращает распознанный текст.

Кэш моделей живёт в `/cache`: `MACHINE_LEARNING_CACHE_FOLDER` задан в образе, а
том — `emptyDir` из манифеста. Путь включает ревизию, поэтому её смена тянет
модели заново, а пересоздание пода стирает кэш целиком. Отдельного тома под кэш
нет.

## Ресурсы: VPA в режиме наблюдения

Для `immich-server` и `immich-machine-learning` объявлены
`VerticalPodAutoscaler` с `updateMode: "Off"`: рекомендатор собирает статистику
потребления, поды при этом не меняются.

Наблюдение, а не активный режим — потому что requests здесь подобраны руками:
у machine-learning 320Mi стоят по замеру фактического потребления, а шаблонный
1Gi держал бюджет памяти узла впустую. Смысл наблюдения — увидеть, что
рекомендация скажет про уже настроенные значения, прежде чем что-то менять
автоматически. Цена ошибки в активном режиме выше обычной: сервер ходит под
стратегией `Recreate` (RWO-том `library` нельзя монтировать двум подам), то есть
применение рекомендации — это простой сервиса, а не незаметная подстройка.

Под наблюдение не попало:

- `immich-valkey` — датасторм: его память определяется конфигурацией
  (`maxmemory`), а не потреблением процесса, и рестарт по рекомендации означал бы
  потерю кэша;
- CNPG-кластер `immich-db` — ресурсы инстанса Postgres задаёт оператор, и VPA
  вторым владельцем того же поля быть не должен.

Вход и диагностика — в `RUNBOOK.md`.

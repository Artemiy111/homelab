# Samba

Раздаёт тома внешнего NTFS-диска по SMB. Живёт в кластере, тома монтирует
хост.

Подключение: `smb://smb.example.com`, учётка `storage`, пароль — тот же, что
в Vault по пути `kv/samba/storage`.

## Что где лежит

| Что | Где |
|---|---|
| Конфиг шар (`smb.conf`) | `manifests/config/smb.conf` |
| Скрипты инициализации | `manifests/config/*.sh` |
| Роль хоста (монтирования, TCP) | `infra/ansible/roles/ntfs_samba/` |

Конфиг и скрипты лежат файлами и собираются в ConfigMap'ы через
`configMapGenerator`. Kustomize добавляет к имени хэш содержимого и
переписывает ссылку в Deployment, поэтому правка конфига сама запускает
rollout — ручной рестарт не нужен.

Монтированиями тома занимается systemd, а не кластер: у `hostPath` нет опций
`uid`/`gid`/`context`, которые нужны ntfs3, и только systemd умеет ждать
появления USB-устройства, не вводя узел в emergency. Поэтому записи в
`/etc/fstab` на хосте управляются ролью `infra/ansible/roles/ntfs_samba`: она
осталась ради монтирований и TCP — того, что через Kubernetes сделать нельзя.
ntfs3 принимает `uid`/`gid`/`umask`/`context` только в опциях монтирования, а у
`hostPath` таких полей нет; systemd умеет ждать появления USB-устройства и
переживать отсутствие диска при загрузке. Роль не обслуживает Samba на хосте —
ни пакета, ни юнита, ни конфига шар, ни учётки.

## Почему initContainer проверяет тома

`hostPath` в Kubernetes не знает про монтирования хоста. Если том не
смонтирован, точка монтирования — пустой каталог на корневом разделе: под
стартует, `smbd` работает, шара открывается **пустой**, без единой ошибки в
логах. Клиент решит, что данные пропали. Это худший вид поломки, поэтому
initContainer проверяет каждую точку и валит под, если хоть одна не на месте.

Проверяются три признака, каждый по отдельности недостаточен:

1. **`fstype == ntfs3`.** Точка без тома видна в `/proc/self/mounts` как `xfs`
   — это каталог корневого раздела хоста, то есть ровно тот случай, который
   надо поймать.
2. **Режим `ro`/`rw` совпадает с описанием тома.** `read only = yes` в секции
   шары само по себе не спасает: клиент получит ошибку ввода-вывода вместо
   внятного «read-only resource».
3. **Серийный номер тома совпадает с UUID из `fstab`.** Другой диск даёт тот
   же `fstype` и тот же режим — отличает только номер.

Номера томов и ожидаемые UUID лежат в `config/verify-mounts.sh` и продублированы
в `infra/ansible/roles/ntfs_samba/defaults/main.yml`. При замене диска менять
нужно оба места.

Дополнительно в кластере точка `ntfs2` смонтирована в под как `readOnly: true`.
Это не дублирование `read only = yes`: режим монтирования тома в грязном
состоянии трогать нельзя, и под не должен получать такую возможность. `ntfs1`
пересоздан `mkntfs` и смонтирован на запись, поэтому и в под он на запись.

`ntfs1` после пересоздания получил новый серийный номер: `4E17FFBC5209D652`.
Прежний `36447F8E447F4F9B` в репозитории не остался — `mkntfs` не сохраняет
идентификатор, а вывести его из старого нельзя.

### Тест проверки

Логика `verify-mounts.sh` покрыта `tests/verify-mounts.test.sh`. Тест
исполняет скрипт как есть, подменяя в копии пути и `stat`, и проверяет пять
поломок: отсутствующий том, `xfs` вместо `ntfs3`, расхождение режима с
`fstab`, чужой серийник и отказ на последнем томе.

Он написан после реального дефекта: проверка читала список томов через
конвейер, флаг ошибки выставлялся в подпроцессе и наружу не доходил, скрипт
возвращал ноль. initContainer пропускал под, `smbd` поднимался и отдавал
пустую шару — та самая поломка, ради которой проверка написана. Сценарий
«каталога нет» ловится и той версией случайно, поэтому тест нацелен на ветку
«каталог есть, но смонтировано не то».

## Пароль

Пароль лежит в Vault по пути `kv/samba/storage`, доезжает через
`VaultStaticSecret` и попадает в под как переменная `SMB_PASSWORD`. Учётку
заводит initContainer: `smbpasswd -s -a storage` читает пароль из stdin, и в
списке процессов он не остаётся.

Ротация: обновить значение в Vault, затем рестартнуть под. `emptyDir` с базой
паролей переживает рестарт контейнера, но не удаление пода, а initContainer
пересоздаёт учётку при каждом старте.

## Проверка

Подняться и убедиться, что обе части на месте:

```sh
kubectl -n samba get pods
kubectl -n argocd get application samba
```

Шары видны клиенту:

```sh
smbclient -L //smb.example.com -U storage
```

Порт отвечает с клиента:

```sh
nc -z smb.example.com 445
```

Режим записи соответствует монтированию — в `ntfs2` запись отклоняется, в
`ntfs3` проходит:

```sh
smbclient //smb.example.com/ntfs2 -U storage -c 'put /etc/hostname .probe'
smbclient //smb.example.com/ntfs3 -U storage -c 'put /etc/hostname .probe'
```

### Тест отсутствующего диска

Главная проверка: под должен упасть с внятной ошибкой, а не раздать пустую
шару. Отмонтировать том и перезапустить под:

```sh
sudo umount /mnt/ntfs3
kubectl -n samba delete pod -l app=samba
kubectl -n samba logs -l app=samba -c provision --previous
```

Ожидается отказ initContainer'а с сообщением о несмонтированном томе.
Смонтировать том обратно:

```sh
sudo mount /mnt/ntfs3
```

Проверка не требует правды о том, что диск «иногда отваливается»: она
объясняет, почему под не поднимется с пустой шарой, и что именно он скажет.

## Ручной вход

Внутрь пода:

```sh
kubectl -n samba exec deploy/samba -c smbd -- sh
```

Проверить эффективный конфиг — `testparm` проверяет синтаксис, но не
показывает, какие секции реально получились:

```sh
kubectl -n samba exec deploy/samba -c smbd -- testparm -s /etc/samba/smb.conf | grep '^\['
```

Должны быть `ntfs1`, `ntfs2`, `ntfs3`.

## За пределами задачи

Скорость по SMB — около 800 КБ/с: сервер в другом городе, Tailscale даёт
прямой путь с 0.5% потерями. Диск отдаёт 41 МБ/с локально, упирается канал.
Ускорение возможно только сменой провайдера либо раздачей через CDN/Seafile
вместо монтирования.

Том `ntfs2` в грязном состоянии: для записи нужен `chkdsk` в Windows и
`shutdown /s /t 0` после, либо пересоздание `mkntfs`. Linux не должен
переигрывать журнал NTFS на нём.

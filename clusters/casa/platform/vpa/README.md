# VPA

Vertical Pod Autoscaler — контроллер вертикального масштабирования. Он считает,
сколько CPU и памяти поду нужно на самом деле, и умеет проставлять эти числа в
requests и limits вместо значения, подобранного на глаз.

Это ответ на другой вопрос, чем у HPA: HPA меняет **число реплик** по метрике,
VPA — **размер одной реплики** по фактическому потреблению. На одном workload'е
их не включают вместе: HPA считает утилизацию от requests, а VPA эти requests
меняет, и они начинают двигать друг друга.

## Устройство

Три компонента в namespace `vpa`:

| Компонент | Роль |
|---|---|
| recommender | держит историю потребления и считает рекомендации |
| updater | применяет рекомендации, перезапуская поды (`Recreate`) или меняя requests на месте (`InPlaceOrRecreate`) |
| admission-controller | проставляет requests подам при создании; в режиме `Off` не участвует |

Сами объекты — `VerticalPodAutoscaler` в namespace сервиса. Этот юнит ставит
только контроллер и ни на один сервис его не натравливает: без VPA-объектов
контроллер не делает ничего. Разумный первый шаг для сервиса — режим `Off`,
то есть рекомендации без изменений в подах.

## Почему официальный чарт, а не Fairwinds

Оба чарта разворачивают один и тот же VPA, различия в упаковке. Здесь
официальный — `vertical-pod-autoscaler` из `kubernetes.github.io/autoscaler`:

- CRD лежат в `templates/`, а не в `crds/`: релиз и CRD обновляются одним
  синком, ручного шага «обнови CRD» при апгрейде нет;
- есть режим cert-manager: сертификаты вебхука выпускает cert-manager, без
  job'а `kube-webhook-certgen` и без чужого образа;
- он живёт в репозитории апстрима рядом с кодом VPA.

Community-чарт Fairwinds `vpa` — обёртка над `hack/vpa-up.sh`: тот же набор
манифестов, но CRD в `crds/` (Helm их при обновлении релиза не трогает), плюс
сабчарт metrics-server, который здесь не нужен: Metrics API уже даёт
metrics-server из k0s.

## Сертификаты вебхука

Вебхук подписан cert-manager'ом, а не job'ом `kube-webhook-certgen`: чарт
создаёт в namespace собственный self-signed `Issuer`, промежуточный CA и
сертификат на имена `vpa-webhook[.vpa[.svc[.cluster.local]]]`, а CA в
`MutatingWebhookConfiguration` подставляет cainjector по аннотации
`cert-manager.io/inject-ca-from`.

Публичные `ClusterIssuer` стенда для этого не годятся: они выпускают наружные
сертификаты через DNS-01, а вебхуку нужен внутренний сертификат на service-имя.

`caBundle` чарт в манифесте не рендерит вовсе. Именно поэтому здесь
`ServerSideApply`: поле принадлежит cainjector'у, и Argo за него не спорит —
иначе `MutatingWebhookConfiguration` вечно висел бы в `OutOfSync`.

## Почему по одной реплике и без PDB

У чарта по умолчанию две реплики на компонент и включённые PDB с
`minAvailable: 1`. На одноузловом стенде это лишние поды, а PDB с
`minAvailable: 1` при единственной реплике блокирует дренаж узла: eviction
не проходит никогда. Лидер-элекшн чарт включает сам, когда реплик больше одной,
поэтому при `replicas: 1` он не нужен.

## Requests и limits

Дефолт чарта — `resources: {}` на все три компонента. Числа взяты из
апстримных манифестов (`vertical-pod-autoscaler/deploy/`), которые рассчитаны
на кластер с сотнями подов; на стенде их можно снижать.

Память лимитируется, CPU — нет. CPU сжимаемый ресурс, и лимит на control loop
означает троттлинг, а не защиту; память наоборот — разъехавшийся recommender
вытеснит рабочие поды с узла. Цена ошибки в лимите памяти: recommender держит
историю в памяти и при рестарте её теряет, то есть рекомендации пропадают и
набираются заново.

## Сеть

Namespace закрыт: `default-deny-ingress` плюс явные разрешения — внутри
namespace и порт вебхука 8000/TCP открыт всем источникам.

Адреса в политике нет намеренно: правило с `ipBlock` на LAN-подсеть молча
отрезало вебхук. Трафик API-сервера к вебхуку идёт с узла, но за Calico источник
host→pod трафика — не LAN-адрес узла, поэтому политика его не пропускала, а
`failurePolicy: Ignore` превращал это в «поды создаются как обычно, только без
requests». Открытый порт проверен smoke-тестом из `RUNBOOK.md`.

Egress не ограничивается: updater вытесняет поды во всех namespace'ах, а
компоненты ходят в API-сервер.

`failurePolicy` вебхука — `Ignore` (дефолт чарта). Недоступный вебхук не ломает
создание подов, но молча перестаёт проставлять requests, поэтому проверка
вебхука — отдельный шаг в `RUNBOOK.md`, а не «посмотрели, что поды в `Running`».

## Чего здесь нет

- **Ни одного `VerticalPodAutoscaler`.** Контроллер есть, целей у него нет:
  включение VPA для сервиса — задача по сервису.
- **Метрик в vmagent.** Компоненты отдают Prometheus-метрики (recommender 8942,
  updater 8943, admission-controller 8944), но vmagent собирается статическими
  job'ами, и VPA в них не добавлен.
- **HPA.** Горизонтального масштабирования в репозитории нет.

Эксплуатация — в [`RUNBOOK.md`](RUNBOOK.md).

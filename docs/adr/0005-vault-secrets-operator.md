# Синхронизация секретов из Vault: оператор VSO, а не External Secrets

Ручной деплой Vault заменён официальным чартом `hashicorp/vault-helm`, поверх
сервера поставлен оператор `hashicorp/vault-secrets-operator` (VSO). Решение о
самом операторе принимается здесь; факт «секреты на VSO ещё не перенесены»
фиксируется в issue #305.

## Considered Options

- **External Secrets Operator** — универсальнее: один оператор закрывает Vault,
  AWS, GCP, Infisical, 1Password. Лицензия Apache-2.0, комьюнити заметно
  больше, есть push-режим (`PushSecret`). Проигрывает только тем, что в этом
  репозитории он пока не даёт выигрыша: единственный источник — Vault, а
  мультибэкенд нужен лишь в гипотетическом будущем.
- **VSO от HashiCorp** — выбран. Первая сторона, версируется вместе с Vault, а
  не по отдельности. `VaultAuth` переиспользуем: роль и политика описываются
  один раз, а не дублируются в каждом Store-объекте, как у ESO. Есть
  событийная синхронизация `spec.syncConfig.instantUpdates` (с 1.6.0).
- **Оставить только Sealed Secrets** — отклонено. Sealed Secrets не умеет
  динамические креды, ротацию и не отдаёт секреты вне Kubernetes (CI, Ansible,
  ноутбук). Тогда не отменено; позже снято вместе с SOPS-реестром (#976).
- **CSI-драйвер** — отклонено. В связке с VSO он Enterprise-only, в ESO
  существует ради мультибэкенда, которого нет.

## Миграция на ESO позже — не дорого

VSO и ESO не хранят состояние: данными владеет Vault, оператор stateless.
Поэтому переезд — это переписывание манифестов (`VaultConnection`+`VaultAuth` →
один `ClusterSecretStore`, `VaultStaticSecret` → `ExternalSecret`), а не миграция
данных. Обратная совместимость дешёвая, и потому решение можно пересмотреть,
когда появится второй источник секретов.

Порядок при переезде: поставить ESO и создать `ExternalSecret` с тем же именем
целевого Secret → дождаться `Ready=True` и сверить содержимое → **только потом**
удалять CR VSO. И VSO, и ESO ставят `ownerReferences` на создаваемый Secret
(у ESO это `target.creationPolicy: Owner`), поэтому удаление CR VSO раньше
времени оставит приложения без секретов.

Что при этом теряется: `instantUpdates` (событийная синхронизация) у ESO нет,
останется polling по `refreshInterval`.

## Consequences

- Секреты в кластере доставляет Vault через VSO; Sealed Secrets и SOPS-реестр
  сняты (#974, #976). Момент, когда на VSO поехал первый production-секрет,
  оказался отдельным решением, а не следствием этого.
- **Auto-unseal не решён.** Vault на k0s остаётся с ручным unseal, то есть
  после рестарта пода синхронизация секретов встанет, пока Vault не unsealed.
  Пока секретов на VSO нет, это безопасно; при переходе на production-нагрузку
  ручной unseal становится неприемлемым.
- В кластере осталась одна система доставки секретов — Vault через VSO.
  Sealed Secrets и SOPS+age сняты; Infisical остаётся отдельным тестовым
  сервисом. Исходные значения теперь только в Vault, поэтому его бэкап
  (снапшот raft) — единственная страховка.
- Выход с BSL не достигнут: сервер Vault тоже BSL 1.1, поэтому переезд с VSO на
  Apache-2.0 ESO лицензионного аргумента не даёт.

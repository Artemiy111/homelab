# Конфигурация OpenTofu ограничена возможностями Terraform

Инструмент на хосте — OpenTofu (пакет `opentofu` из Fedora, #316). Конфигурация
пишется только в том подмножестве HCL, которое понимает Terraform: расширения
OpenTofu не применяются. Решение относится к языку, а не к бинарнику — смена
бинарника на Terraform не должна требовать переписывания конфигурации.

## Почему не «только OpenTofu»

Выбор инструмента сделан из-за недоступности Terraform: пакета `terraform` в
репозиториях Fedora нет, `releases.hashicorp.com` и `registry.terraform.io`
отдают гео-блок. Ограничение принимается вместе с этим выбором, а не вместо
него — иначе «переносимость» была бы декларацией без механизма.

Ограничение нужно именно потому, что расширения OpenTofu не выглядят отдельным
пространством имён: их нет в другом синтаксисе, они просто есть. Кто впервые
откроет конфигурацию и не прочитает этот ADR, напишет
`terraform { encryption { ... } }` и обнаружит расхождение только при попытке
перейти на Terraform.

## Considered Options

- **Разрешить OpenTofu-расширения там, где они дают безопасность** (то есть
  разрешить `encryption` и шифровать state штатным способом) — отклонено.
  Расширение само по себе переносимо только в одну сторону, а выигрыш
  достигается другими средствами: state не коммитится (`.gitignore`, #321) и
  шифруется вне OpenTofu, если понадобится.
- **Зафиксировать OpenTofu как основной инструмент и не следить за Terraform**
  — отклонено: тогда ограничение не нужно, но конфигурация навсегда привязана к
  одному бинарнику и его темпу релизов.
- **Проверять переносимость в CI бинарником Terraform** — отклонено: бинарник
  недоступен из сети, где живёт репозиторий (гео-блок), а собирать его в
  раннере в этом homelab нечем.
- **Хранить конфигурацию в отдельном репозитории** — отклонено: у нас один
  контекст, и отдельный репозиторий ради одного слоя усложнит доставку без
  выигрыша.

## Consequences

- **Нативное шифрование state и plan использовать нельзя.** Блок
  `terraform { encryption { ... } }` существует только в OpenTofu. Следствие:
  state остаётся незашифрованным на диске и не коммитится — вопрос бэкапа
  state решается отдельно, шифрованием вне OpenTofu (например, SOPS поверх
  выгрузки state), а не блоком в конфигурации.
- **`.terraform.lock.hcl` не переносится на Terraform.** Файл записывает
  источник провайдера как `registry.opentofu.org/hashicorp/vault` (проверено на
  песочнице), а Terraform использует `registry.terraform.io`. При переходе
  lock-файл перегенерируется, версии провайдеров резолвятся заново. Это
  безопасно, но означает, что lock-файл нельзя считать переносимым артефактом.
  Строки `source` в `required_providers` переносимы: они пишутся без хоста.
- **Сверка переносимости — ручная и по документации Terraform.** Автоматической
  проверки нет: `terraform validate` не запустить, а `tofu` не умеет проверять
  себя на совместимость с Terraform. Любая новая возможность проверяется по
  документации Terraform, а не по документации OpenTofu: у OpenTofu они
  расходятся, и именно в сторону OpenTofu.
- **Правило распространяется на конфигурацию, а не на код репозитория.**
  Kubernetes-манифесты, Helm-чарты и Ansible-роли OpenTofu-расширениями не
  пользуются, но и ограничение на них не распространяется.

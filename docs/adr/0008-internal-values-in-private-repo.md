# Внутренние значения для Argo CD: приватный репозиторий вместо файлов на узле

Арго читает желаемое состояние из объекта `Application` в кластере, а приватные
значения в этот объект попадают merge-patch'ем из файла, который лежит только на
узле: `argocd/applications/*.private.yaml`, `platform/homelab/values.private.yaml`,
`platform/k0s/values.private.yaml`. Файлов семь, секретов в них нет — только
«внутреннее» по `docs/agents/information-handling.md`, — а фактов всего три
(apex-домен, адрес узла, issuer Zitadel), и они повторяются восемь раз.

Ссылки вместо значений задачу не решают. Секретный уровень уже решён: значения
приходят из Vault через VSO, и в Application лежат `existingSecret` и
`secretKeyRef`. В приватных файлах лежит другое — идентичность окружения, которую
чарт требует на этапе шаблонизации (`gitea.config.server.ROOT_URL`,
`auth.oidc.issuerURL`). У Argo нет ни `lookup`, ни аналога `valuesFrom`, поэтому
эта строка физически не может прийти из объекта кластера.

Оверлей поверх шаблона — вторая проблема. `--type=merge` это JSON merge patch:
массивы заменяются целиком, поэлементного слияния нет, поэтому приватный файл
обязан повторять весь список `gitea.oauth`, а любое поле, добавленное в шаблон
внутри этого списка, патч затирает молча. Приватный слой к тому же невидим для CI
и для сверки в `docs/status` (`docs/status/README.md`), и именно он стал причиной
инцидента `docs/incidents/0005-forgejo-oidc-wrong-issuer.md`: неверный issuer
прошёл мимо всех проверок и уронил Forgejo.

Третье ограничение решает, какая схема вообще возможна. Приоритет источников
values в Argo: `helm.parameters` > `valuesObject` > `values` > `valueFiles` >
значения чарта. То есть файл из `valueFiles` **не может перекрыть** ключ, который
уже стоит в `valuesObject`, — а плейсхолдер `example.com` в шаблоне Application
именно там. Оверлей «публичный шаблон + приватный valueFiles» не работает
конструктивно: приватное значение просто не применится, и это выглядит как
«Argo сломался». Значит либо приватный файл не оверлей и содержит весь values, либо
приватных значений у Application нет вовсе.

Четвёртое ограничение вынуждает выбрать имя. `spec.sources` требует `repoURL`
второго источника, то есть публичный Application обязан назвать репозиторий
внутренних значений. Настоящий домен называть нельзя — зеркало его опубликует, и
приватный слой перестанет быть приватным.

## Решение

Внутренние значения живут в отдельном приватном репозитории. Argo читает его
декларативно: `spec.sources` + `repoCreds` + `helm.valueFiles: $values/<app>.yaml`.
Публичный репозиторий хранит только факт «приложению нужен values-файл», без
плейсхолдеров.

### Как называется репозиторий

Два адреса, потому что два разных потребителя:

- **service-DNS** — `forgejo-ssh.forgejo.svc.cluster.local`. Читает Argo,
  repo-server, то есть потребитель внутри кластера; резолвит CoreDNS. Раньше
  `*.svc.cluster.local` стоял в `information-handling.md` во «внутреннем» уровне,
  но запрет ничего не защищал: раскладка namespace'ов и так публична —
  `platform/homelab/values.yaml` перечисляет её целиком.
- **hostname в зоне `homelab.internal`** — для потребителей вне кластера, то есть
  для `kubelet`, который тянет образы из внутреннего реестра. Отдельный адрес
  нужен ровно поэтому: service-DNS резолвит только внутри кластера.

Имя зоны — `.internal` (RFC 8375), а не `.local` (RFC 6762): `.local` зарезервирован
под mDNS, а имя, которому доверяет git-клиент или containerd, резолвиться по mDNS
не должно.

### Транспорт

SSH, не http. Подключение к репозиторию лежит в Vault по пути
`kv/forgejo/@argocd/ssh/homelab-values` и доставляется в кластер
`VaultStaticSecret` — тем же каналом, что и остальные 80+ секретов. Почему не http
с токеном: токен идёт по сети в открытом виде, а deploy key уже ограничен
read-only и не имеет области действия в API Forgejo. Пиннинг host key убирает
вопрос подмены ключа целиком.

Два ограничения Argo определили форму хранения. Первое: подключение к
репозиторию Argo читает из Secret с меткой
`argocd.argoproj.io/secret-type: repository` и сопоставляет репозиторий по полю
`url`, поэтому ссылка на Secret в Application не нужна, а `repoCreds` — и вовсе не
применим: поле есть только у одиночного `spec.source`, в `spec.sources[]` его нет.
Второе: имена ключей в этом Secret Argo диктует сам (`sshPrivateKey`, `type`,
`url`), и VSO переносит ключи из Vault один в один. Значит в Vault лежат именно
эти три имени, а метку задаёт `spec.destination.labels` манифеста. Шаблон
трансформации не нужен.

Host key'и лежат в `argocd-ssh-known-hosts-cm` под единственным ключом
`ssh_known_hosts` на все репозитории сразу, а не по одному ключу на хост.

Родной SSH-движок Vault сознательно не используется. Он умеет подписывать
публичные ключи CA и выдавать короткоживущие сертификаты, но приватный ключ он
не хранит и в кластер не доставляет: и то и другое остаётся на нас. Взамен
появляется посредник, который должен переподписывать сертификат по TTL, а
переподписать может только тот, у кого есть право `ssh/sign/*`, — VSO читать
умеет, писать не умеет. Плюс требуется доверие CA на стороне сервера, а SSH
Forgejo — встроенный, не системный sshd. Движок понадобится, если появится
задача «дать доступ в SSH на 15 минут»; для одной машины, читающей один
репозиторий, он лишний.

В приватном репозитории лежат **имена и адреса**. Credentials остаются в Vault и
попадают в кластер только через VSO. Смешивать два уровня в одном хранилище нельзя:
у первого радиус поражения — раскрытие внутренней информации, у второго —
компрометация учётных данных, и лечатся они по-разному.

В приватный репозиторий переезжает **весь values целиком, а не оверлей поверх
шаблона**. Оверлей сохранил бы merge-семантику, array-подмены и молчаливые
затирания полей — то есть ровно то, что делает приватный слой опасным сейчас.

`platform/homelab` и `platform/k0s` пока остаются на `helm template -f`: это другой
seam, доставка вне Argo. Формат файлов кладётся такой же, чтобы перевод на
прикладные сервисы (вариант 2 в #625) не потребовал второго формата.

## Considered Options

- **Ссылки вместо значений** (`existingSecret`, `envFrom`, ConfigMap с доменом) —
  отклонено как основная схема. Для секретов оно уже применено и работает, для
  идентичности окружения неприменимо: чарт требует строку при рендере, а
  `lookup` под Argo не работает (`argocd/README.md`).
- **argocd-vault-plugin** — подставляет значения из Vault при рендере, plaintext
  не появляется нигде. Отклонено по цене: это config management plugin, поэтому
  приложение переезжает с `spec.source.helm` на `spec.source.plugin` и несёт
  собственный `helm template`; в путь рендера добавляется Vault, а unseal у нас
  ручной, значит после ребута рендер этих приложений падает; матрица совместимости
  проекта обрывается на Argo CD 2.1. Вернуться к варианту имеет смысл, если
  внутренние значения появятся там, где values-файлы не нужны вовсе.
- **Отдельный ref в этом же репозитории** — дешевле на один remote, но публикация
  ограничивается дисциплиной: зеркало настроено на репозиторий, а не на ref, и
  приватная ветка легко утекает в публикацию целиком. Отдельный репозиторий
  ограничивает публикацию структурно.
- **Модуль доставки** (читает Vault, материализует приватные файлы, применяет
  шаблон и патч атомарно) — не убирает файлы с узла, зато добавляет второго
  писателя в спеку `Application` рядом с ручным `kubectl apply`. Полезен как
  гейт, но хранилищем не является.
- **Отдельный приватный репозиторий** — выбран.

## Consequences

- В namespace `argocd` появляется `Secret` с read-only учёткой на новый
  репозиторий. Радиус поражения — чтение файла внутренних значений, без
  credentials; ротация — перевыпуск токена. Учётка нужна и агенту на macOS для
  правки значений; альтернатива — правки делает пользователь, и тогда агент
  работает только с публичной частью.
- В `.gitignore` остаются правила на `*.private.yaml` до последней миграции:
  снимать их раньше опаснее, чем держать.
- В публичном репозитории вместо `example.com` остаётся ссылка на values-файл.
  Плата: вместе с `valuesObject` из публичного Application уезжает и несекретная
  часть конфигурации приложения — порты, ресурсы, флаги accessLog. Вектор,
  `chart`, `targetRevision`, `releaseName`, `skipCrds`, `syncPolicy` и
  `destination` остаются видны, но values целиком видны только владельцу
  приватного репозитория. Для учебного и портфолидного репозитория это
  осознанный размен: конфигурация, которую нельзя публиковать, и конфигурация,
  которую можно, делятся границей публикации, а не в одном файле.
- Механизм покрывает **values, но не координаты источника, которые читает не
  Argo**. У `dns01-webhook` внутренние значения — хост реестра в
  `spec.source.repoURL` OCI-чарта и в `image.repository` у контейнера. Первое поле
  не values вовсе, второе резолвит `kubelet` на узле, а не repo-server, поэтому
  service-DNS не годится ни там, ни там. Этот Application переводится отдельно и
  требует hostname в `homelab.internal` плюс решение по TLS реестра: Let's Encrypt
  такое имя не выдаст, нужен внутренний CA, доверенный containerd.
- В пути рендера Argo появляются три новые зависимости: приватный репозиторий,
  Forgejo и DNS, резолвящий service-DNS. Отказ любой из них останавливает рендер
  (sync блокируется, prune не выполняется) — направление отказа безопасное, но
  «штормовка» всех 15 Application в трёх точках возможна.
- `homelab-config` (`DOMAIN`, `TZ`, `DEFAULT_LOCALE`) остаётся источником для
  манифестов, которые читают домен через окружение. Два хранилища одного факта
  допустимы, пока они ссылаются друг на друга явно: файл значений в приватном
  репозитории — источник для чартов, ConfigMap — производная для подов.
- Ключи в приватном репозитории, которые чарт не читает, больше не молчат:
  `helm template` их игнорирует, поэтому проверка «ключ из файла действительно
  попал в рендер» становится частью приёмки миграции, а не вопросом на
  несколько месяцев.

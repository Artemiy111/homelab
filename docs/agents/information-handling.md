# Обращение с информацией на сервере

Правила для агентов, работающих с этим репозиторием. Действуют всегда, но особо
важны сейчас: `origin` — это Forgejo, а репозиторий готовится к публичному
зеркалу на GitHub. Публикация необратима: любой commit, ветка, сообщение commit,
PR, issue и лог CI становятся вечными и публичными, их нельзя «забрать назад».

## Классификация информации

| Уровень | Что это | Как обращаться |
|---|---|---|
| **Публичное** | Код, манифесты, документация, README, **зашифрованный** текст (`*.sealedsecret.yaml`, `SealedSecret`), публичный age-ключ, публичные DNS-имена, service-DNS этого кластера (`*.svc.cluster.local`) и имена внутреннего контура (`*.homelab.internal`) | Можно коммитить |
| **Внутреннее** | Реальный домен и его поддомены, LAN-адреса (`192.168.x.x`), CGNAT/tailnet-адреса (`100.64.0.0/10`), tailnet- и MagicDNS-имена, `*.ts.net`, имена нод, email ACME/Let's Encrypt, имя RFC2136-ключа, порты и то, чем они опубликованы | Не добавлять заново; не выводить в публичные артефакты; уже попавшее — вычистить из истории |
| **Секретное** | Приватные ключи, age-ключ `~artlab/.config/sops/age/keys.txt`, `kubeconfig`, service account token'ы, sealing-ключ SealedSecrets, Tailscale auth key и ACL-policy, пароли, API-токены, webhook-URL, DSN с паролем, **расшифрованные** значения `sops -d` | Никогда не печатать, не логировать, не коммитить |

### Почему service-DNS и `homelab.internal` — публичное

Раньше `*.svc.cluster.local` стоял во «внутреннем» уровне, но это было неверно по
существу: раскладка namespace'ов этого кластера и так публична —
`platform/homelab/values.yaml` перечисляет её целиком, манифесты
`apps/*/k8s/*.namespace.yaml` в git, `docs/status/` по ней считает. Запрет на
имя сервиса не защищал ничего и только мешал: `valueFiles` в Argo требует
`repoURL`, и без внутреннего имени приватный репозиторий нельзя было бы адресовать
из публичного Application.

`*.homelab.internal` — наше собственное имя сегмента, а не адрес чего-либо: вне
LAN оно не резолвится, домен не содержит, адреса не раскрывает. Имя сегмента уже
публично в `webhookGroupName: acme.homelab.local` и `groupName` в Application
webhook'а.

`.local` для этого не годится: он зарезервирован под mDNS (RFC 6762), и имя,
которому доверяет git-клиент, не должно резолвиться по mDNS. Для домашних сетей
есть `.internal` (RFC 8375) — mDNS его не трогает.

Граница «секрет/несекрет» в репозитории — файловая: секреты лежат только в
`sealedsecret.yaml` (пока не переведены на Vault) и в Vault. Всё остальное
секретом не считается и потому в него легко случайно что-то протащить — на это и
направлены правила ниже.

## Где живут внутренние значения

Уровень «внутреннее» отделён от секретного и хранится в **отдельном приватном
репозитории** `homelab-values` (решение — `docs/adr/0008`, работа — #641). В нём
лежат домен, адрес узла, issuer и clientID приложений, ACME-email. Argo читает
его по SSH через `spec.sources` + `repoCreds` + `helm.valueFiles:
$values/argocd/<app>.yaml`.

| Уровень | Где хранится | Как попадает в кластер |
|---|---|---|
| Внутреннее | приватный репозиторий `homelab-values` | Argo как values-файл, `spec.sources` + `repoCreds` |
| Секретное | Vault | `VaultStaticSecret` (VSO), в манифестах ссылки `existingSecret`/`secretKeyRef` |

Транспорт — SSH, не http. Подключение Argo к репозиторию лежит в Vault по пути
`kv/forgejo/@argocd/ssh/homelab-values` (сегмент `@argocd` — правило 3 ADR 0006:
кред выдан отдельному принципалу и отзывается независимо) и доставляется в
кластер `VaultStaticSecret` в namespace `argocd` как Secret с меткой
`argocd.argoproj.io/secret-type: repository`. Ключи в Vault названы как их читает
Argo: `sshPrivateKey`, `type`, `url`. Host key Forgejo лежит в
`argocd-ssh-known-hosts-cm` под единственным ключом `ssh_known_hosts` — именно
там Argo хранит SSH host key'ы, а в `argocd-tls-certs-cm` лежат TLS-сертификаты
для https-репозиториев, и для SSH он не читается. Адрес репозитория — service-DNS,
потому что читает его repo-server, то есть потребитель внутри кластера; `kubelet`
на узле такой адрес не резолвит, поэтому для образов из внутреннего реестра нужен
отдельный hostname в зоне `homelab.internal`.

Правила:

- **`homelab-values` не зеркалируется.** Публичное зеркало на GitHub настроено на
  репозиторий `homelab`; второй репозиторий в него не попадает и не должен
  попасть. Любая публикация внутренних значений в `homelab` — утечка.
- **Только имена и адреса.** Credentials (пароли, токены, ключи) в
  `homelab-values` не кладутся никогда, даже если чарт требует значение в
  values: такое значение берётся из Vault по ссылке. Смешивать два уровня в
  одном хранилище нельзя — у них разный радиус поражения и разный порядок
  ротации.
- **Публичный репозиторий хранит только форму.** В Application остаётся ссылка на
  values-файл, а не плейсхолдер реального значения и не сам файл.
- **Пока перевод не завершён**, внутренние значения лежат в untracked
  `*.private.yaml` на узле (`.gitignore`). Это переходное состояние: файла нет в
  git, поэтому CI и `docs/status` его не видят — см. инцидент
  `docs/incidents/0005-forgejo-oidc-wrong-issuer.md`.

## Правила

1. **Публичный origin = публичная история.** Считать каждый commit и каждое
   сообщение публичными навсегда. Никогда не писать секреты, расшифрованные
   значения, токены и новые внутренние адреса в код, манифесты, документацию,
   тестовые фикстуры, комментарии, имена веток, сообщения commit, тела PR/issue и
   вывод CI.
2. **Сначала прочитать, потом менять.** Сначала read-only проверки от `ai-agent`,
   затем запрашивать разрешение на запись. Ограничения доступа из
   `docs/agents/server-access.md` не обходить.
3. **Никогда не печатать расшифрованное.** Для диагностики выводить только имена
   переменных, не значения:
   ```sh
   kubectl -n <ns> get vaultstaticsecret -o json | \
     jq -r '.items[]|select(.status.conditions[0].status!="True")|.metadata.name'
   ```
   Не выполнять `kubectl get secret -o yaml`, `env`, `docker inspect`,
   `helm get values`, `kubeseal --reveal` и подобное, если результат может
   попасть в чат, коммит или лог. Если результат нужен — маскировать значения.
4. **Не класть секреты в задачу агенту.** Значение секрета не должно попадать в
   текст промпта: агент берёт его из окружения/vault, а не из описания задачи.
5. **Вывод инструментов — канал утечки.** Логи приложений, трейсы, вывод
   `kubectl`, CI-логи считать потенциальным каналом раскрытия; перед
   пересказом/коммитом маскировать токены, адреса и домены.
6. **Только штатные каналы секретов.** Доставка в кластер — только
   `VaultStaticSecret` (Vault + VSO) или, пока не переведено, `SealedSecret`.
   Расшифровываемого реестра значений в репозитории нет. Plaintext-файлы с
   секретами не создавать. Приватный age-ключ не копировать на macOS и не
   добавлять в Git.
7. **Прочитал расшифрованный секрет — доложить немедленно.** Назвать, какой
   именно секрет прочитан, и как его ротировать (см. `AGENTS.md`).
8. **Опасные операции — только с подтверждением.** Удаление, `push`, смена прав,
   сетевые команды — после явного согласия пользователя.
9. **Ротация важнее чистки истории.** Если секрет уже попал в историю: сначала
   отозвать/ротировать значение, и только потом (если нужно) переписать историю.
   Форки, клоны и кешированные представления PR ротацией не отменяются —
   исходить из того, что секрет скомпрометирован.
10. **В примерах и скриптах — только плейсхолдеры.** `.env.example`, `init.sh`,
    README и любые примеры не должны содержать реальных значений (домен, IP,
    токены); реальное — в приватном слое: `homelab-values` для внутреннего,
    Vault для секретного, `*.private.yaml` и `config.env` — пока переход не
    завершён.
11. **Приватный репозиторий — не свалка.** В `homelab-values` нельзя класть
    credentials и нельзя класть значения, которые не относятся к идентичности
    окружения. Если чарт требует секрет в values, это не повод ослаблять правило,
    а повод оставить ссылку на Vault.

## Чек-лист перед коммитом и push

1. `git status` и `git diff` — глазами: нет плейнстектных секретов и новых
   внутренних адресов.
2. `gitleaks dir --config .gitleaks.toml` — рабочее дерево;
   `gitleaks git --config .gitleaks.toml` — история.
3. `trufflehog git file://.` — независимая проверка с верификацией.
4. Убедиться, что `.env`, `kubeconfig`, `*.pem`, `*.key` не в индексе.

## Принуждение

| Слой | Что проверяет | Где |
|---|---|---|
| pre-commit | секреты в staged-изменениях | `.githooks/pre-commit` + `.gitleaks.toml` |
| CI | секреты в новых коммитах (push) и в diff PR | `.forgejo/workflows/secrets.yml` |
| push protection | секрет не попадёт в публичный репозиторий | настройки GitHub (включить при открытии зеркала) |
| branch protection | проверка `secrets` обязательна | настройки репозитория (при открытии зеркала) |
| secret scanning | вся история всех веток | GitHub (бесплатно для public; включить при открытии) |
| mirror | `homelab-values` не публикуется | настройки зеркала Forgejo: указан только `homelab` |

Правило `.gitleaks.toml` исключает шифротекст SOPS/SealedSecrets и известные
плейсхолдеры — иначе сканер ругается на шифротекст. Первоисточники и сравнение
инструментов — в `docs/research/security-audit-standards.md`.

# 0001 — Переполнение тома `dawarich-db` при обновлении Dawarich

Дата: 2026-09-18
Статус: устранено, действия открыты
Среда: однонодный k0s, CNPG 1.30, Longhorn

## Сводка

После обновления Dawarich 1.11.0 → 1.14.5 его кластер баз `dawarich-db` ушёл в
`CrashLoopBackOff`: миграции и фоновый пересчёт истории забили 512-MiB том под
завязку, и instance manager отказался стартовать PostgreSQL
(`no free disk space for WALs`). Том увеличен до 3 GiB, кластер восстановлен.

## Влияние

- **Dawarich недоступен ~5 минут** (`21:12`–`21:17`): `/api/v1/health` отдавал
  `500`, под приложения пережил отказ на liveness-рестарте.
- Sidekiq пересчитывал историю; одна задача (`Places::DeleteIfOrphanJob`) упала
  с `Connection refused` и выполнилась сама после восстановления (retry).
- **Потери данных нет**: `points` 46070 до и после, дамп
  `dawarich-pre1145-2026-09-18-2107.dump` снят перед обновлением.
- Другие сервисы не затронуты — кластер выделенный (docs/adr/0002).

## Первопричина

Три фактора сложились:

1. **Том был рассчитан без запаса под миграции.** 512 MiB брались из «93 МБ
   данных + служебный пол 39 МБ», без учёта того, что обновление с data
   migrations временно раздувает и таблицы, и WAL. README прямо оговаривал
   «на вырост не резервируем» — допущение оказалось неверным для сервиса,
   который пересчитывает историю.
2. **`wal_level=logical` (дефолт CNPG) держит больше WAL.** На это уже
   указывал комментарий в манифестах (`wal_keep_size` опущен до 64MB), но
   размер тома всё равно посчитали по данным, а не по пиковой записи.
3. **Расширение тома в CNPG — не одна операция, а три.** Оператор detecting
   проблему ≠ увеличение PVC ≠ расширение файловой системы. Для
   одноинстансного кластера CNPG PVC не пересоздаёт и не ресайзит; FS
   расширяется только при монтировании, а под в CrashLoop смонтировать не
   мог — замкнутый круг, разорванный удалением пода.

## Что сработало

- **Дамп перед обновлением** — откат был бы полным и бесплатным.
- **Логи instance manager** сразу назвали причину (`no free disk space for
  WALs`), не пришлось гадать про CNI или Longhorn.
- **Резерв по остальным кластерам** не понадобился: инцидент локализован
  выделенным кластером.

## Уроки

- **Data migrations обновляемого приложения — это нагрузка на диск**, а не
  только на CPU. Обновление, которое трогает данные, требует запаса по тому.
- **Размер тома в CNPG не вырастет сам.** Оператор скажет «PVC должен быть
  больше», но увеличивать его — ручная операция, и за ней следует remount для
  FS-resize.
- **«На вырост не резервируем» плохо работает для пересчитываемых данных.**
  Longhorn считает размеры при планировании, но переполнение обходится дороже
  сэкономленного места.

## Действия

- [ ] Проверить размеры остальных кластеров на запас под миграции:
      `shared`, `zitadel-db`, `immich-db` (у immich пересоздание векторных
      индексов при переносе — тот же риск).
- [ ] Записать в `k8s/cnpg/README.md` процедуру расширения тома: патч `Cluster`
      → патч PVC → удаление пода для FS-resize.
- [ ] Рассмотреть `wal_keep_size` и оценку тома по пиковой нагрузке впредь —
      для сервисов с фоновым пересчётом.

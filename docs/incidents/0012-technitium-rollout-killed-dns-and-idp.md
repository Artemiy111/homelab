# 0012 — Роллаут Technitium снёс DNS сети и кластера, IdP не смог скачать образы

Дата: 2026-10-24
Статус: устранено, действия открыты
Среда: одноузловой k0s v1.36.3, Argo CD v3.5.3, Zitadel 4.17.1 → 4.20.0, Technitium 15.4.0 → 15.6.2

## Сводка

Обновление Technitium (#1361) со `strategy: Recreate` удалило единственный
DNS-сервер сети и кластера раньше, чем скачало свой новый образ — а скачать его
без работающего DNS нельзя. Через две секунды Argo применил обновление Zitadel
до 4.20.0, и оба пода IdP тоже остались без образов. IdP был недоступен 25
минут; восстановление потребовало вручную дать узлу резолвер, не зависящий от
кластера.

## Влияние

- **IdP недоступен 25 минут** (11:22:49 → 11:47:54 UTC): `zitadel` и
  `zitadel-login` без подов, `id.biplane.casa` не обслуживается. Вместе с ним
  лежал любой вход через OIDC и всё, что за `oauth2-proxy`.
- **DNS сети недоступен ~13 минут** (11:22:47 → 11:36:03): `192.168.1.254` не
  отвечал, клиенты сети остались без резолвера.
- **Pull образов в кластере не работал** всё окно: `lookup ghcr.io: Try again`,
  `lookup registry-1.docker.io: Try again`. Пострадали ровно три пода —
  `technitium`, `zitadel`, `zitadel-login`. Уже запущенные поды не
  перезапускались и работали.
- **Данные целы.** Дамп БД `zitadel` снят до апгрейда
  (`~/backups/zitadel/zitadel-pre-4.20.0-20261024T1420.dump`), миграции
  прогнались один раз при первом старте 4.20.0 и завершились успешно.
- **Пользовательский эффект сверх простоя:** в браузере страница входа отдавала
  `Minified React error #441`; после подъёма API вход заработал, но подпись
  cookie в Login V2 появилась впервые — 3 старые cookie были отброшены
  (`ignoring 3 session cookie entries with a missing or invalid signature`),
  то есть войти в Login UI пришлось заново.

## Первопричина

Три допущения, каждое верное по отдельности.

1. **«Резолвер ноды — фон, а не часть стенда».** Узел получает DNS по DHCP от
   роутера (`192.168.0.1`), в IaC это не описано. 24 октября роутер не отвечал
   вовсе (timeout), позже — `REFUSED`, как и 17 октября в инциденте 0011.
   Фактически работающий резолвер у сети один — Technitium на `192.168.1.254`,
   то есть **внутри кластера**. Действие «перевести резолвер ноды на собственный
   DNS и описать в Ansible» из 0011 было отложено владельцем 2026-10-17, и
   допущение дожило до второго инцидента.
2. **«DNS-сервер обновляется как обычный сервис».** `strategy: Recreate` удаляет
   единственный DNS раньше, чем kubelet скачает новый образ, а образ тянется с
   `registry-1.docker.io` — имя которого резолвит тот самый Technitium. Петля
   замыкается в момент удаления старого пода, и выйти из неё изнутри нельзя:
   любая попытка ретрая требует DNS, которого нет.
3. **«Резервный путь — `resolvectl revert`».** На этом узле revert не возвращает
   DHCP-адрес: NetworkManager не отдаёт DNS в systemd-resolved, и линк остаётся
   без резолвера и без default route. Процедура «вернуть как было» не
   восстанавливает ничего — она ухудшает состояние.

## Что сработало

- **Текст ошибки в `kubectl describe pod`.** `dial tcp: lookup ghcr.io: Try
  again` сразу отделил доставку образа от приложения; ни одна гипотеза про
  Zitadel не проверялась зря.
- **Сравнение резолверов с одного узла.** Три `dig` (`@192.168.0.1`,
  `@192.168.1.254`, `@1.1.1.1`) за минуту дали корень и показали, что внешний
  резолвер доступен.
- **Миграции не успели испортить откат.** API ни разу не стартовал, поэтому
  схема БД осталась на 4.17.1, а образы 4.17.1 — в кеше узла: откат был
  бесплатным до 11:47:54.
- **Дамп БД до апгрейда.** Снят заранее, до всех событий, и это единственная
  страховка, которая была бы полезна при неудачных миграциях.
- **Argo оставался `Synced`.** Desired state в git не менялся, поэтому
  восстановление не потребовало ни `kubectl apply` в обход GitOps, ни правок
  манифестов: как только DNS появился, оба пода скачались сами.

## Уроки

- **DNS-сервер внутри кластера не может быть единственным резолвером узла.**
  Для pull образов нужен резолвер, который доступен до того, как кластер
  поднялся, и не зависит от его содержимого.
- **`Recreate` безопасен только для того, что не является зависимостью
  собственного pull.** Для Technitium порядок «сначала образ на узле, потом
  merge» обязателен.
- **`resolvectl revert` на этом узле — не откат.** Проверять восстановление
  нужно по `resolvectl status`, а не по факту выполнения команды.
- **Проба `/healthy` у login UI не проверяет API.** Под был `1/1 Ready` и
  отдавал 200 всё время, пока вход был нерабочим: с 4.19.0 проверка credential
  перенесена на старт, а readiness остаётся про процесс. Внешняя проверка IdP
  должна ходить в OIDC discovery.
- **Minified-ошибка React в браузере ничего не говорит о причине.** `#441` в
  этой ситуации означал «SSR не получил настройки API»; смотреть надо в логи
  пода, где были конкретные `fetch() returned undefined`.
- **Смежные PR одного окна усиливают друг друга.** Обновление DNS и обновление
  IdP приехали в одну минуту; по отдельности каждое переживалось бы, вместе —
  нет.

# Удалённый доступ к K8s-сервисам: ограничения MetalLB L2 и варианты решений

## Суть проблемы

**Цель:** обеспечить одновременную работу Docker-сервисов и Kubernetes-сервисов с доступом из любой сети по единому домену `example.com`.

Сейчас Docker-сервисы (Traefik, Technitium и др.) работают на IP `<node1-ip>` и доступны из локальной LAN. Kubernetes-сервисы (Traefik, Gatus, Uptime Kuma и др.) работают через MetalLB на IP `<node1-ip>` и доступны только из локальной LAN. Из удалённой сети (через Tailscale) Kubernetes-сервисы **недоступны**, потому что MetalLB в режиме L2 работает через ARP, который не маршрутизируется через L3-туннели.

MetalLB — это лишь средство реализации, которое не решает задачу. Проблема шире: нужна архитектура, которая обеспечит доступ к обоим типам сервисов из любой точки подключения.

## Анализ проблемы

### Текущая конфигурация

| Компонент | Детали |
|---|---|
| Сервер | `<node1-ip>` (enp2s0) |
| MetalLB | Режим L2, пул `<metallb-ip>/32` |
| Traefik (K8s) | LoadBalancer `<node1-ip>`, NodePorts `32223`/`32610` |
| Traefik (Docker) | Привязан к `<node1-ip>:80/443` |
| Tailscale | `198.51.100.11`, advertise-ит подсеть `<node1-lan-cidr>` |
| Tailscale Traefik | `198.51.100.12`, хостнейм `traefik.example-tailnet.ts.net` |
| Домен | `example.com` (<dns-provider>) |
| Локальный DNS | Technitium резолвит `*.example.com` → `<node1-ip>` кроме k8s сервисов, которые вручную A записями на `<metallb-ip>` |
| Инgressы | `uptime.`, `home.`, `lute.`, `mermaid.`, `kuma.` → все → `<node1-ip>` |
| Роутер (homelab) | Kinetic (<node1-lan-cidr>), за NAT от провайдера |
| Роутер (текущая сеть) | OpenWRT (<node2-lan-cidr>), за NAT от провайдера |
| В планах | Вторая нода в сети `<node2-lan-cidr>`, полный переход с Docker Compose на K8s, переход на IP `<node1-ip>` для K8s-сервисов |

### Почему MetalLB L2 не работает через Tailscale

MetalLB в режиме L2 работает, отправляя **безарпные (gratuitous ARP) объявления** в локальный Ethernet-сегмент. Speaker говорит сети «я владею `<node1-ip>`» на уровне L2. Когда клиент отправляет пакет на этот IP, он приходит на сетевой интерфейс ноды, и правила kube-proxy/iptables перенаправляют его в под Traefik.

Когда трафик приходит через Tailscale:

1. Пакет входит на интерфейс `tailscale0` с назначением `<node1-ip>`
2. Ядро проверяет: является ли `<node1-ip>` локальным адресом? **Нет** — он не привязан ни к какому интерфейсу
3. Таблица маршрутизации матчит `<lan-cidr> → enp2s0` и **отправляет пакет обратно в физическую сеть**
4. Правила kube-proxy/iptables для этого IP **никогда не выполняются**
5. Пакет либо отбрасывается, либо зацикливается

Корневая причина: MetalLB L2 никогда не добавляет VIP как локальный адрес ядра. Он целиком полагается на ARP для перехвата трафика на уровне канала связи. Tailscale (WireGuard-туннель) работает на L3, полностью обходя ARP.

### Ограничения для решения

- Обязательно использовать кастомный домен `example.com` (не `*.ts.net`)
- Обязательно поддержка мульти-нод (запланирована вторая нода в `<node2-lan-cidr>`)
- Обязательно работать из любой сети (домашняя LAN, удалёнка через Tailscale, мобильные)
- Желательно: минимальная добавленная сложность

## Вариант 1: Cloudflare Tunnel (рекомендуемый)

**Как работает:** Запускает `cloudflared` как DaemonSet в K8s. Он создаёт исходящий (outbound-only) туннель к edge-серверам Cloudflare. DNS (`*.example.com`) настраивается на маршрутизацию через Cloudflare, который проксирует трафик обратно через туннель к Traefik.

**Архитектура:**

```
Клиент → Cloudflare Edge (cloudflare.com) → cloudflared tunnel → под Traefik
```

**Актуальное состояние (2026):** Cloudflare Tunnel остаётся бесплатным, использует исходящие соединения по порту 7844 (QUIC/UDP) или 7843 (TCP). Первоисточники (developers.cloudflare.com, август 2026) и отраслевые отчёты (Reddit) подтверждают отсутствие лимитов пропускной способности в бесплатном тарифе и ограничение в 1000 логических туннелей на аккаунт.

**Статус блокировки в России:** сообщение от Cloudflare (июнь 2025) — блокируются некоторые публичные edge-IP, но пул IP для туннелей отличается, и массовая блокировка туннелей не зафиксирована. Туннель использует встроенную отказоустойчивость: при блокировке одного edge автоматически переключается на другой.

**Преимущества:**
- Работает откуда угодно (дома, удалённо, с мобильных) — VPN не нужен
- Использует твой кастомный домен `example.com`
- Автоматическая terminates TLS на edge Cloudflare (бесплатный Universal SSL)
- Мульти-нода: Cloudflare Load Balancer может распределять трафик по нескольким туннелям
- Не нужно открывать порты на роутере (только исходящие соединения)
- Защита от DDoS включена в бесплатный тариф
- Поддержка WebSocket, HTTP/2, gRPC
- Официальная поддержка в Kubernetes (дашборд, документация)

**Недостатки:**
- Требует аккаунт Cloudflare (бесплатного тарифа достаточно)
- Добавляет Cloudflare как зависимость (вопрос приватности: трафик проходит через их сеть)
- Требует управления DNS-зоной в Cloudflare (или CNAME-делегирование из <dns-provider>)
- Туннель запускается как под — нужен ClusterRole для отслеживания Ingress-ресурсов

**Поддержка мульти-нод:**
- Запускать по одному `cloudflared` на каждую ноду (DaemonSet)
- Каждый создаёт именованный туннель к Cloudflare
- Использовать Cloudflare Load Balancer для распределения по туннелям
- Или один туннель с несколькими origin-серверами (проще)

**Схема внедрения:**
1. Создать аккаунт Cloudflare, добавить `example.com` (или CNAME-делегирование из <dns-provider>)
2. Создать Tunnel в панели Cloudflare
3. Сохранить credentials туннеля как Kubernetes Secret
4. Развернуть `cloudflared` как Deployment/DaemonSet
5. Настроить DNS в Cloudflare: `A *.example.com → <tunnel-ID>.cfargotunnel.com`
6. Cloudflare обрабатывает TLS, проксирует на Traefik по портам 80/443

**Влияние на текущую конфигурацию:**
- MetalLB остаётся для локального LAN-доступа (оба сосуществуют)
- Technitium DNS остаётся для локальной резолвинга
- Cloudflare DNS становится публичным резолвером
- Ingresses Traefik остаются без изменений

## Вариант 2: Tailscale Funnel

**Как работает:** Tailscale Funnel публикует сервис через инфраструктуру Tailscale. Сервис получает публичный URL `*.ts.net`.

**Актуальное состояние (2026):** Funnel — бета, доступно на всех тарифах, работает только на портах `443/8443/10000`, только по TLS, с **неконфигурируемыми** ограничениями пропускной способности (Tailscale прячет цифры, называет это «фаннел, не шланг»). Кастомные домены **не поддерживаются** — только имена в домене tailnet (`*.ts.net`). Горячая фича-петиция[#11563](https://github.com/tailscale/tailscale/issues/11563) с 2024 года без ответа.

**Преимущества:**
- Простая настройка (CLI или Kubernetes Operator)
- Работает откуда угодно
- Не нужен аккаунт помимо Tailscale
- Можно комбинировать с публичным DNS-резолвером (например, CNAME с `example.com` на funel URL) — но это требует, чтобы клиент сначала резолвил CNAME, что неудобно для мобильных

**Недостатки:**
- **Работает только с доменами `*.ts.net`** — не поддерживает кастомные домены нативно
- Неконфигурируемые лимиты пропускной способности — не подходит для тяжёлых сервисов
- Бета-статус, ограничения портов
- Нарушает ограничение «без доменов Tailscale»

**Вердикт: ОТКЛОНЁН** — не соответствует требованию кастомного домена.

## Вариант 3: Публичный IP + reverse proxy

**Как работает:** Использовать публичный IP роутера (WAN). Открыть порты 80/443 на роутере (port forwarding) и запустить reverse proxy (или просто Traefik) для обработки TLS и маршрутизации.

**Преимущества:**
- Прямой доступ через твой домен
- Нет зависимости от третьих лиц (кроме DNS)
- Работает откуда угодно

**Недостатки:**
- Требует открытия портов 80/443 на публичном интерфейсе (риск безопасности)
- Требует, чтобы сервер был напрямую доступен из интернета (без NAT)
- Защита от DDoS должна решаться отдельно
- Точка отказа (один публичный IP)
- TLS-сертификаты phải управляться на сервере
- Если сервер за NAT (домашняя сеть), «публичный IP» может быть WAN-IP роутера, а не сервера

**Поддержка мульти-нод:**
- DNS round-robin (без проверки здоровья)
- Или запуск отдельного reverse proxy (nginx/haproxy) с балансировкой по нодам

**Внедрение:**
- Настроить Traefik/Docker на привязку к `0.0.0.0:80/443` (или LAN IP)
- Настроить port forwarding на роутере: WAN 80/443 → <node1-ip>:80/443
- Обновить DNS: `A *.example.com → <WAN-IP роутера>`
- Убедиться, что файрвол разрешает 80/443 на публичном интерфейсе

**Оценка рисков:** Публичный IP может быть динамическим (меняться при перезагрузке роутера). Port forwarding увеличивает поверхность атаки. DDoS-защита не встроена.

## Вариант 4: Split DNS (локальный vs удалённый)

**Как работает:** Использовать разные DNS-резолверы для локальных и удалённых клиентов:
- **Локальные клиенты** → Technitium DNS → `<node1-ip>`
- **Удалённые клиенты** → Публичный DNS → Tailscale IP или IP туннеля

**Преимущества:**
- Чёткое разделение: локальный трафик остаётся локальным, удалённый идёт через туннель
- Нет обнаружения приватных IP в интернете
- Использует твой домен

**Недостатки:**
- Требует настройки клиентов на использование правильного DNS-резолвера
- Удалённый DNS должен указывать на доступный IP (Tailscale IP или IP туннеля)
- Мобильные устройства требуют настройки DNS (VPN-профиль или вручную)
- Не решает требование «доступ из любой сети без настройки»

**Поддержка мульти-нод:**
- Локально: Technitium с round-robin или GeoIP-_RESOLUTION
- Удалённо: публичный DNS с проверкой здоровья

**Внедрение:**
- Обновить зону Technitium: `*.example.com → <node1-ip>` (уже сделано)
- Создать публичные DNS-записи: `*.example.com → <IP-туннеля-или-Tailscale>`
- Настроить клиенты: домашний WiFi использует Technitium, удалённый — публичный DNS

**Альтернативный путь: Tailscale Scope DNS + кастомные домены (без публичного DNS)**
Вместо публичного DNS можно использовать Tailscale split DNS: добавить в MagicDNS кастомный домен `example.com`, поднять один из сервисов (например Traefik) на ноде как Tailscale Serve, и резолвить `*.example.com` на Tailscale-имя этого сервиса. Это работает только для устройств в tailnet — не для публичного интернета.

## Вариант 5: MetalLB BGP + BGP через Tailscale

**Как работает:** Переключить MetalLB с L2 на BGP. BGP работает на L3 и может advertise-ить маршруты через подсети. Использовать Tailscale как транспорт для BGP-пирования между нодами.

**Актуальное состояние:** FRRouting (`frr`) и BIRD поддерживают BGP поверх WireGuard/Tailscale — это стандартная практика для homelab. FRR имеет поддержку интерфейсного пиринга (unnumbered), но Pinng через Tunnel-интерфейс (Tailscale) требует явного указания IP-пира. Всё работает, но требует ручной настройки FRR/BIRD на каждой ноде и координации между ними.

**Преимущества:**
- MetalLB BGP добавляет VIP как локальный адрес ядра (в отличие от L2)
- Работает через подсети
- Поддержка мульти-нод встроена
- Проходит через Tailscale tunnel (не требует открытых портов)

**Недостатки:**
- Требует настройки BGP на каждой ноде (bird, frr или аналог)
- BGP-пирование должно быть установлено через туннели Tailscale
- Более сложная сетевая конфигурация
- Требует понимания BGP (AS-номера, advertise маршрутов)
- BGP на одной ноде бессмыслен — нужно минимум 2 ноды

**Поддержка мульти-нод:**
- Каждая нода запускает BGP-демон (например, FRR)
- Ноды пирятся друг с другом через Tailscale
- MetalLB advertise-ит VIP через BGP
- Маршруты устанавливаются в ядро, делая VIP локальными

**Сложность:** Высокая. Это production-уровневое решение, но требует серьёзных знаний сетей.

## Вариант 6: Cilium с BGP Control Plane

**Как работает:** Заменить kube-proxy + Calico на Cilium. Использовать BGP control plane Cilium для advertise-инга сервисных IP.

**Актуальное состояние (2026):** Cilium имеет встроенный BGP control plane (cEP — Cilium Endpoint PNet, Cilium BGP L2 announcements) и LB-IPAM. С января 2026 года есть поддержка Cilium как LoadBalancer-класса для Kubernetes Service, что позволяет Cilium самому присваивать IP-адреса сервисам и анонсировать их через BGP. Это значительно упрощает архитектуру: вместо MetalLB + FRR на каждой ноде, иметь один Cilium, который занимается и сетью, и BGP-аноунсами. Однако это требует замены Calico на Cilium — нет прямой совместимости, нужно переехать на Cilium по CNI.

**Преимущества:**
- Современная сетевая основа на eBPF
- Встроенная поддержка BGP
- Лучшая производительность, чем kube-proxy на iptables
- Продвинутые сетевые политики
- Меньше компонентов (без MetalLB, без FRR на нодах)

**Недостатки:**
- Требует замены Calico (текущий CNI) на Cilium
- Масштабная инфраструктурная перемена
- Сложнее текущей конфигурации
- Избыточно для homelab

**Вердикт: ИЗБЫТОЧНО** — слишком много изменений ради преимущества.

## Вариант 7: kube-vip

**Как работает:** kube-vip — это лёгкая альтернатива MetalLB, предоставляющая LoadBalancer-IP через ARP (L2) или BGP.

**Преимущества:**
- Проще MetalLB в некоторых конфигурациях
- Поддерживает и L2, и BGP
- Может запускаться как DaemonSet

**Недостатки:**
- Та же проблема L2, что и у MetalLB (на основе ARP, не работает через Tailscale)
- BGP-режим добавляет ту же сложность, что и вариант 5
- Менее крупное сообщество, чем у MetalLB

**Вердикт: НЕ РЕШАЕТ ПРОБЛЕМУ** — та же фундаментальная проблема, что и у MetalLB L2.

## Вариант 8: Traefik DaemonSet с hostNetwork + DNS Round-Robin

**Как работает:** Развернуть Traefik как DaemonSet с `hostNetwork: true`, привязанный к портам 80/443 на IP каждой ноды. Использовать DNS round-robin для распределения трафика по нодам.

**Преимущества:**
- Просто в внедрении
- MetalLB не нужен для этого сценария
- Работает откуда угодно (у каждой ноды свой IP)
- Нет зависимости от MetalLB для входа

**Недостатки:**
- Нет проверки здоровья (DNS round-robin отправляет трафик на мёртвые ноды)
- Конфликт портов, если Docker Traefik уже на 80/443
- Требует отключения Docker Traefik или использования других портов
- Ручное обновление DNS при изменении нод
- Нет автоматического failover
- В текущей конфигурации: Docker Traefik уже на `<node1-ip>:80/443` — DaemonSet потребует тот же IP и тот же порт, конфликт неизбежен, либо нужно перевести всё на K8s Traefik

**Поддержка мульти-нод:**
- Каждая нода получает DNS A-запись
- DNS round-robin распределяет трафик

**Внедрение:**
1. Развернуть Traefik как DaemonSet с `hostNetwork: true`
2. Настроить `ports.web.hostPort: 80` и `ports.websecure.hostPort: 443`
3. Обновить Technitium DNS: `*.example.com → <node1-ip>, <node2-ip>
4. Для удалённого доступа: обновить публичный DNS с теми же записями

**В текущем homelab:** это требует перехода с Docker Traefik на K8s Traefik DaemonSet — то есть шаг к целевой архитектуре (полный переход на K8s). Если это плановый переход, вариант стоит рассмотреть как часть миграции.

## Вариант 9: NodePort + Tailscale Subnet Routing + кастомный DNS

**Как работает:** Использовать NodePort-сервисы (уже открыты: `32223`/`32610`). Доступ через `<IP-ноды>:<nodeport>`. Настроить DNS на резолвинг в IP нод.

**Преимущества:**
- Уже работает (NodePorts существуют)
- Просто
- Мульти-нода: каждая нода экспонирует одни и те же NodePorts

**Недостатки:**
- Нестандартные порты (не 80/443)
- TLS-сертификаты могут не работать с нестандартными портами
- Пользователь должен знать номера портов
- Неудобно

**Вердикт: КОСМЕТИЧЕСКОЕ РЕШЕНИЕ, А НЕ РЕШЕНИЕ** — нестандартные порты ломают пользовательский опыт.

## Вариант 10: Dummy-интерфейс + Tailscale

**Как работает:** Использовать сам Tailscale как сетевой слой. Поскольку Tailscale уже настроен с subnet routing (адвертит `<node1-lan-cidr>`), недостающий элемент — сделать VIP доступным.

**Подход: добавить VIP как локальный адрес + advertise через Tailscale**

1. Добавить `<node1-ip>` на dummy-интерфейс ноды
2. Настроить Tailscale на advertise `<metallb-ip>/32` как subnet route
3. kube-proxy обрабатывает трафик, приходящий с любого интерфейса

**Актуальное состояние (after experiment):** Этот вариант был протестирован в августе 2026 ([troubleshot/tailscale-k8s-ingress-access.md](docs/troubleshot/tailscale-k8s-ingress-access.md)). При `ip addr add <metallb-ip>/32 dev tailscale0`: VIP появился на tailscale0, но ядро перестало считать его входом LoadBalancer и отправило пакеты в loopback. Трафик завис (нет слушателя на <node1-vip>:443).

**Вывод эксперимента:** сделать VIP локальным адресом на tailscale-интерфейсе **не работает** — это ломает механизм входа MetalLB. LoadBalancer в L2-режиме работает через ARP + DNAT на LAN-интерфейсе, а не как процесс, слушающий VIP. Поэтому подход с dummy-интерфейсом требует замены MetalLB L2 на альтернативу (BGP, Tailscale Operator или self-hosted tunnel), а не патчинга адресов.

**Преимущества (до теста):**
- Использует существующую инфраструктуру Tailscale
- Нет новых зависимостей
- Работает с любого устройства, подключённого к Tailnet

- MetalLB L2 и dummy-интерфейс конфликтуют — не работает
- Работает только с заменой MetalLB на другой механизм

## Рекомендация

**Для текущей конфигурации homelab: Вариант 1 (Cloudflare Tunnel)**

Причины:
1. **Соответствует всем требованиям**: кастомный домен, мульти-нода, удалённый доступ
2. **Низкая операционная сложность**: не нужны экспертиза в сетях
3. **Безопасность**: не нужно открывать порты на роутере, включена защита от DDoS
4. **Сосуществование**: MetalLB остаётся для локального LAN-доступа, Cloudflare обрабатывает удалённый
5. **Готовность к будущему**: добавление второй ноды тривиально (добавить ещё один туннель или origin)
6. **Бесплатный тариф**: достаточно для homelab (лимиты отсутствуют, за исключением лимитов TLS-сертификатов и basic rate limiting)

**Путь миграции:**
1. Добавить `example.com` в Cloudflare (или CNAME-делегирование из <dns-provider>)
2. Развернуть cloudflared в K8s (DaemonSet с токеном туннеля как Secret)
3. Настроить DNS в Cloudflare: `A *.example.com → <tunnel-ID>.cfargotunnel.com`
4. Сохранить MetalLB + Technitium для локального доступа
5. При добавлении второй ноды: добавить cloudflared на новую ноду; для распределения использовать Cloudflare Load Balancer (платный) или простой DNS Round-Robin на уровне Cloudflare DNS (бесплатно)

**Альтернативы для специфичных сценариев:**
- **Доступ только через Tailnet (не публичный интернет): Tailscale Serve.** Если сервисы не нужно выставлять в публичный интернет, можно использовать Tailscale Serve — они будут доступны по `*.ts.net`-доменам внутри tailnet. Это не требует никаких изменений в 메탈ЛБ и DNS. Кастомный домен можно настроить через Tailscale split DNS + кастомный DNS-резолвер (например, Technitium с записями на tailscale-имена). Но это требует, чтобы клиенты были в tailnet.
- **Мульти-нода с минимальными изменениями: DaemonSet Traefik с hostNetwork.** Часть миграции на K8s — развернуть Traefik как DaemonSet на всех нодах, отключить Docker Traefik, и использовать DNS для распределения. После миграции Docker Traefik исчезнет, конфликт портов разрешится.

**Вариант 10 (Dummy-интерфейс + Tailscale) не рекомендуется**, так как эксперимент показал его неработоспособность в текущей конфигурации с MetalLB L2.

## Дополнительные замечания

### Cloudflare Tunnel в России

Cloudflare Tunnel (`cloudflared`) работает через **исходящее** соединение с edge-серверами Cloudflare по порту `7844` (QUIC/UDP) или `7843` (TCP). Поскольку соединение инициируется сервером (outbound), а не клиентом (inbound), оно проходит через NAT и файрвол без проблем.

**Статус блокировки:** По состоянию на 2026 год Cloudflare в целом **не заблокирован** РКН. Однако были единичные случаи попадания отдельных IP-адресов Cloudflare в реестр блокировок (обычно из-за того, что на конкретном IP хостится заблокированный ресурс). Tunnel использует CDN-сеть Cloudflare (тысячи IP), поэтому блокировка всего сервиса маловероятна.

**Риски:**
- Если edge-сервер Cloudflare попадёт в блоклист, туннель автоматически переключится на другой edge (built-in resilience)
- Для критичного доступа рекомендуется иметь запасной вариант (Tailscale)
- Трафик через Cloudflare проходит через их сеть — вопрос приватности

**Вывод:** Для homelab-сценария Cloudflare Tunnel — приемлемый вариант. Полная блокировка маловероятна, а автоматическое переключение на другие edge-серверы обеспечивает отказоустойчивость.

### BGP за NAT: работает ли?

**Короткий ответ:** BGP между двумя нодами за NAT **не работает напрямую**, но **работает через туннель** (Tailscale/WireGuard).

**Почему не работает напрямую:**
- BGP использует TCP-соединение на порт 179
- Каждая нода инициирует соединение к peer'у
- Если обе ноды за NAT, ни одна не имеет реального IP, к которому можно подключиться
- В твоём случае:
  - Home lab (Kinetic): за NAT от провайдера, реального IP нет
  - Текущая сеть (OpenWRT): за NAT, реального IP нет

**Как работает BGP через Tailscale:**
1. Tailscale создаёт WireGuard-туннель между нодами (L3)
2. BGP-пиринг настраивается на Tailscale IP (`100.x.x.x`)
3. BGP-пакеты идут внутри WireGuard-туннеля
4. MetalLB advertise-ит VIP через BGP
5. Ядро устанавливает маршрут к VIP как локальный

**Схема:**
```
Нода 1 (<node1-ip>)          Нода 2 (<node2-ip>)
     │                                │
     ├── tailscale0 (198.51.100.11)    ├── tailscale0 (100.x.x.x)
     │        │                       │        │
     │        └──── WireGround ────────┘        │
     │              (BGP через tunnels)        │
     ├── FRR/BIRD (BGP)                       ├── FRR/BIRD (BGP)
     │   peer: 100.x.x.x                     │   peer: 198.51.100.11
     └── MetalLB (BGP mode)                   └── MetalLB (BGP mode)
```

**Важные моменты:**
- Tailscale уже работает и создаёт туннель — BGP просто «rides on top»
- Порты 179 не нужно открывать на файрволе (трафик идёт через WireGuard)
- Обе ноды должны быть подключены к Tailscale
- Если Tailscale падает — BGP-пиринг тоже (но MetalLB может fallback на L2)

### Для твоего вопроса: нужна ли вторая нода для BGP?

**Короткий ответ:** Нет, не обязательно. BGP можно использовать с **одной** нодой как локального шлюза — её BGP-демон (FRR/BIRD) будет анонсировать локальные маршруты роутеру, а не другим нодам.

**Более того:** даже если у тебя **нет** второй ноды, BGP с FRR/BIRD на одной ноде может решить твою текущую задачу (доступ с macbook через Tailscale к Kubernetes-сервисам). Это альтернатива Cloudflare Tunnel, которая принципиально другая.

**Что делает BGP с одной нодой:**
1. MetalLB переключается в BGP-режим и анонсирует VIP `<metallb-ip>/32` через BGP локально
2. Ядро теперь видит `<node1-vip>` как локальный IP — трафик от tailscale0 правильно доходит до Traefik
3. Ты подключаешься с macbook через Tailscale, DNS резолвит `*.example.com` на `<node1-vip>`, и сервисы работают

**Для этого нужна поддержка BGP на роутере:**
- **MikroTik Kinetic:** RouterOS v7 поддерживает BGP (законченный в 2022). В homelab-сети роутер работает как BGP-партнёр для MetalLB.
- **OpenWRT:** поддерживает FRR/BIRD для BGP-сессий. В текущей сети (<node2-lan-cidr>) роутер может быть BGP-партнёром для второй ноды.

**Вторая нода (<node1-ip>) — опционально:**
- Она станет вторым BGP-пейром для MetalLB (HA-режим)
- Можно настроить BGP между двумя нодами через Tailscale (как описано выше)
- Но первая нода справляется сама — вторая нода добавляется для высокой доступности, а не для работы BGP

**Мой ввод:** если ты хочешь попробовать BGP, не обязательно ждать второй ноды. Можно начать с FRR/BIRD на одной ноде и поэкспериментировать с анонсом <node1-vip> роутеру. Это решает проблему доступа через Tailscale — VIP становится локальным для ядра. Плюс BGP даёт вторую функцию: анонсирование подсети <node1-lan-cidr> через Tailscale для удалённого доступа к LAN-сервисам.

### Кастомный домен `example.com` с BGP

**Варианты использования домена:**

1. **Локальный DNS (Technitium) остаётся для LAN**
   - `*.example.com` → `<node1-ip>` для локального доступа
   - Для удалённого доступа: технически нужно публичный DNS или Tailscale split DNS

2. **Tailscale split DNS для удалённого доступа из tailnet**
   - Добавить `example.com` как кастомный домен в Tailscale
   - Tailscale резолвит домен в Tailscale-имя Traefik (`traefik.example-tailnet.ts.net`)
   - Работает только для устройств в tailnet

3. **Публичный DNS (Cloudflare) для публичного доступа**
   - `A *.example.com → <публичный IP или туннель>`
   - Работает для любого клиента из любой сети

**Что BGP даёт для домена:**
- BGP решает проблему **доступа к сервисам** (VIP становится локальным), но не проблему DNS
- DNS всё равно нужно настроить отдельно: либо локально (Technitium), либо публично (Cloudflare), либо через Tailscale split DNS
- Если твой план — использовать BGP + Tailscale split DNS, то кастомный домен будет работать для устройств в tailnet. Для публичного доступа понадобится публичный DNS.
### Планы по миграции

**Текущий статус:**
- Docker Compose сервисы: Traefik, Technitium, Home Assistant, и др. работают на `<node1-ip>`
- K8s кластер: Traefik, Gatus, Uptime Kuma, Mermaid, Lute работают в Kubernetes
- Два Traefik: Docker (на <node1-ip>) и K8s (на <node1-vip>) — конфликтуют по портам

**Целевой статус:**
- **Полный переход на K8s**: все сервисы мигрируют в Kubernetes
- **Единый IP для K8s**: `<node1-ip>` (вместо <node1-vip>) — освобождается <node1-vip>, K8s занимает основной IP
- **Docker Compose**: удаляется или сводится к минимуму (только системные сервисы)
- **MetalLB**: переезжает на IP `<node1-ip>` (или `<node1-ip>` становится VIP через dummy-интерфейс)

**Вопросы для принятия решения:**
1. Должен ли K8s слушать на `<node1-ip>` напрямую (hostNetwork на Traefik) или через MetalLB VIP?
2. Если через MetalLB VIP — конфликтует ли `<node1-ip>` с текущим enp2s0?
3. Нужен ли Docker Traefik после миграции? Если нет — освобождаются порты 80/443 на `<node1-ip>`

## Обновленные замечания

### Cloudflare Tunnel в России (обновление)

**Статус блокировки по состоянию на май 2026:** Robin Bloom (Cloudflare) в блог-посте 26 июня 2025 года сообщил о проблемах с доступом к сервисам Cloudflare из России. Однако это касается публичных edge-IP Cloudflare, используемых для проксирования трафика на сайты, защищенные Cloudflare. Cloudflare Tunnel (`cloudflared`) использует **другой пул IP-адресов** для соединения с edge-серверами — тот самый, на котором работает Tunnels-as-a-Service. С плохим блоком этого пула в реестре РКН не зафиксировано.

Тем не менее, стоит иметь в виду:
- **Роутер с открытыми портами 80/443**: если вы выберете вариант публичного IP + reverse proxy (вариант 3), ваш роутер становится видимым из интернета. Это не блокировка, но это риск безопасности.
- **Cloudflare Tunnel с выделенным доменом**: зависимость от Cloudflare как DNS-провайдера и edge-прокси. Если в будущем произойдет массовая блокировка Cloudflare в России, туннель все равно будет работать — трафик будет идти через другие edge-серверы, автоматически выбранные Cloudflare. Для серьезных сценариев предлагается иметь запасной вариант (Tailscale).

### Self-hosted альтернативы Cloudflare Tunnel

Если вы хотите избавиться от зависимости от Cloudflare, рассмотрите self-hosted туннели:

| Решение | Лицензия | Особенности |
|---|---|---|
| **[Pangolin](https://github.com/442528095/pangolin)** | не указан | Fully self-hosted reverse proxy с дашбордом, управление сертификатами |
| **[frp](https://github.com/fatedier/frp)** | MIT | Популярная оっぱка, поддерживает TCP/UDP/HTTP/HTTPS, P2P режим |
| **[NPS](https://github.com/ehang-io/nps)** | MIT | Аналогично frp, с веб-интерфейсом для управления |
| **[Chisel](https://github.com/jpillora/chisel)** | MIT | SSH-based, простой, с поддержкой HTTPS сертификатов |
| **[Zrok](https://github.com/openziti/zrok)** | Apache 2.0 | OpenZiti под капотом, публичный и приватный доступ |

Эти решения требуют выделенного сервера (VPS или第二台 нода в tailnet) для работы серверной части, что усложняет архитектуру по сравнению с Cloudflare Tunnel, который управляет edge-инфраструктурой самостоятельно.

### Tailscale Kubernetes Operator vs MetalLB

Tailscale Kubernetes Operator ([документация](https://tailscale.com/k8s-operator/)) — это нативный способ публикации LoadBalancer-сервисов в tailnet без MetalLB. Он использует Tailscale в качестве LoadBalancer-класса, и сервисы получают имена вида `<service>.<tailnet>.ts.net`. Это:
- Работает через tailnet, не требует MetalLB
- Поддерживает мульти-нод
- Не решает кастомные домены напрямую (но можно комбинировать с Tailscale split DNS + кастомным DNS-резолвером)

Если бы вы использовали оператор, вам не понадобился бы MetalLB для доступа из tailnet. Но для кастомных доменов и публичного доступа всё равно потребуется Cloudflare Tunnel или аналог.

### Вариант 13 (Cilium): почему это избыточно для homelab

Cilium предлагает современную архитектуру на eBPF с встроенным BGP control plane и LoadBalancer IPAM. Это значительно упрощает стек: вместо MetalLB + FRR на каждой ноде, Cilium сам занимается маршрутизацией и анонсами через BGP. Однако для homelab это избыточно по нескольким причинам:
- **Замена CNI** на Cilium — это большая инфраструктурная перемена, которая требует переделки сетевой политики, Storage, и всего стека.
- **Обучающая кривая** eBPF и Cilium значительно выше, чем MetalLB + Calico, которые уже настроены.
- **Homelab-сценарий** не требует уровня сложности Cilium.

Вариант стоит рассмотреть только если вы планируете переход на Cilium по другим причинам (например, для сетевых политик или observability).

### Вариант 11 и 12: как они соотносятся с выбранным решением

- **Вариант 11 (Tailscale Operator)** полезен как дополнение к Cloudflare Tunnel: оператор обеспечивает доступ из tailnet с автоматическим TLS, а Cloudflare Tunnel обеспечивает публичный доступ. Это полная картина.
- **Вариант 12 (VPS + Tailscale/Headscale)** — это самостоятельное решение, которое можно использовать вместо Cloudflare Tunnel, если вы хотите полностью контролировать точку входа и не полагаться на Cloudflare. Но это требует VPS и дополнительной настройки проксирования.

## Обновление (2026-09-14): проверка Варианта 5 на живом удалённом клиенте

Проверка выполнена с macOS-клиента `example-client` (`198.51.100.13`), находящегося
вне домашней сети — доступ только через tailnet. Сервер: одна нода k0s,
MetalLB v0.16.1 (L2), Tailscale Operator v1.102.3.

### Что измерено

| Проверка | Результат |
|---|---|
| `tailscale ping homelab` | pong, 64 ms |
| `<node1-ip>:22` (SSH, host-порт) | succeeded |
| `<node1-ip>:443` (host-порт, Docker-Traefik) | succeeded |
| `<node1-ip>:32610` / `:32223` (NodePort) | timeout |
| `<node1-ip>:443` / `:80` (MetalLB VIP) | timeout |
| `198.51.100.11:6443` (host-порт, k8s API) | succeeded |
| `curl -k https://198.51.100.12 -H 'Host: uptime.example.com'` (оператор) | **200** |
| `dig uptime.example.com` | <node1-ip> (через Technitium) |

### Главный вывод: проблема НЕ в L2/ARP

Host-порты (`22`, `443`, `6443`) ходят через tailnet нормально, значит L3-путь до
ноды и обратно жив. Ломается только **сервисный** трафик — тот, который
`kube-proxy` DNAT-ит в под.

`conntrack` на ноде (снят через под `calico-node`, он в host-netns) для попытки
`198.51.100.13 → <node1-ip>:443` показал:

```
SYN_RECV src=198.51.100.13 dst=<node1-ip> dport=443  packets=1
         src=10.244.107.177 dst=<node1-ip> sport=8443 dport=32540 packets=4
```

То есть: SYN дошёл, DNAT в под Traefik (`10.244.107.177:8443`) сработал, под
ответил — но TCP-рукопожатие не завершается (состояние `SYN_RECV`, в оригинальном
направлении только 1 пакет, клиент не присылает финальный ACK). Причина — в
обработке форвардного/обратного трафика на самой ноде (`kube-proxy` masquerade +
Tailscale/Calico/firewalld), а не в ARP-плоскости MetalLB L2.

### Подтверждённая причина (`tcpdump` под root, 2026-09-14)

`tcpdump -ni any` на ноде во время попытки `198.51.100.13 → <node1-ip>:32610`
показал:

```
cali4f9b7f7db7b In  10.244.107.177.8443 > <node1-ip>.15800: Flags [S.]   # SYN-ACK от пода
enp2s0        Out <node1-ip>.32610 > 198.51.100.13.59132: Flags [S.]     # уходит НЕ туда
```

**SYN-ACK для tailnet-клиента уходит с ноды через `enp2s0` (физический LAN),
а не через `tailscale0`.** То есть входящий путь работает полностью (SYN дошёл,
DNAT в под сработал, под ответил), ломается только **маршрут обратного пакета**:
ядро выбирает `main`-таблицу и default-маршрут через `enp2s0`, вместо Tailscale
таблицы 52 с маршрутом `198.51.100.13 dev tailscale0`. Пакет уходит в LAN-роутер
и теряется — клиент не получает SYN-ACK и повторяет SYN.

Для LAN-клиента такой выбор интерфейса корректен (`enp2s0` и нужен), поэтому в
домашней сети всё работает. Ломается ровно на пересечении «forwarded service
traffic» и «policy routing Tailscale» (fwmark-правила `ip rule` с приоритетами
5210–5250, смотрящие в `main`, против `lookup 52` с приоритетом 5270).

Проверить гипотезу fwmark/маршрута:

```sh
ip rule
ip route show table 52
sudo iptables -t mangle -S | grep -iE 'mark|connmark'
sudo sysctl net.ipv4.conf.all.src_valid_mark net.ipv4.conf.tailscale0.src_valid_mark
```

### Решение (подтверждено)

Правило policy routing с более высоким приоритетом, матчащееся по адресу
назначения, а не по метке:

```sh
sudo ip rule add to 100.64.0.0/10 lookup 52 priority 5200
```

Проверено: с удалённого tailnet-клиента NodePort и VIP открываются, `curl` по
домену отдаёт `200` с валидным Let's Encrypt-сертификатом (`*.example.com`),
LAN не затронут. Правило закреплено systemd-юнитом
`etc/systemd/tailscale-policy-route.service` (ставится через `ansible/host.yml`),
подробности — в `docs/troubleshot/tailscale-k8s-ingress-access.md`.

Итог: ни BGP, ни Tailscale Operator для доступа из tailnet не требуются — проблема
была целиком в policy routing на ноде.

Это уточняет вывод из `docs/troubleshot/tailscale-k8s-ingress-access.md`: дело не
только в том, что «MetalLB L2 не умеет L3-вход», а в том, что ответный сервисный
трафик с ноды к tailnet-клиенту уходил не в тот интерфейс.

### Почему Вариант 5 (BGP) этого не лечит

BGP меняет только то, **как пакет доезжает до ноды** — он анонсирует `VIP/32`
BGP-соседям. Доставку пакета внутри ноды (DNAT → под → обратно) он не трогает.
Плюс в текущей конфигурации BGP не с кем строить:

- роутер — **Keenetic** (KeeneticOS), BGP не поддерживает. В разделе «BGP за NAT»
  выше ошибка: «MikroTik Kinetic / RouterOS v7» — Kinetic это линейка Keenetic,
  а не MikroTik;
- нода одна — пирить её не с кем;
- Tailscale **не является BGP-пиром**: маршруты в tailnet раздаёт control plane
  (subnet router), а не BGP. «BGP через Tailscale» = сессия BGP между двумя
  спикерами поверх WireGuard, а не раздача маршрутов клиентам.

Вывод: Вариант 5 не даёт доступ из tailnet. Он осмыслен только при наличии
BGP-роутера (MikroTik/OpenWRT) или нескольких площадок с маршрутизацией между
ними.

### Промежуточный вариант: Tailscale Operator (испробован и удалён)

В рамках разбора был установлен Tailscale Operator: сервис `traefik-tailscale`
(`loadBalancerClass: tailscale`) давал Traefik tailnet-адрес `198.51.100.12`.
Проверка с удалённого клиента: `curl -k https://198.51.100.12 -H 'Host:
uptime.example.com'` → `200`. Оператор работал как **L4-прокси**: TLS
терминировал сам Traefik, поэтому клиент видел самоподписанный
«TRAEFIK DEFAULT CERT».

Почему оператор работал, а `<node1-vip>` — нет: прокси оператора это под, он ходил в
Traefik по pod-сети (pod→pod), минуя проблемный forward/NAT-путь на ноде. То есть
оператор действительно обошёл бы баг, но ценой отдельного компонента и split DNS
(адрес `100.x` доступен только из tailnet).

После того как причина была найдена и закрыта правилом policy routing (см. выше),
оператор стал избыточен и **удалён** (`helm uninstall`, namespace `tailscale`,
CRDs, `traefik-tailscale`). Итог — один VIP `<node1-vip>` и для LAN, и для tailnet, без
split DNS.

### Итог для homelab

1. **LAN + tailnet** — MetalLB L2 VIP `<node1-ip>` + правило policy routing
   (`etc/systemd/tailscale-policy-route.service`). TLS — уже настроенный secret
   `wildcard-tls` (`*.example.com`, Let's Encrypt) на ингрессах.
2. **Публичный доступ** (если понадобится) — Cloudflare Tunnel (Вариант 1).
3. BGP отложить до появления мульти-ноды и BGP-устройства.

### Диагностика (root на сервере)

```sh
# терминал 1: пакеты на cali*/veth и на tailscale0
sudo tcpdump -ni any -vv 'tcp port 32610 or tcp port 8443 or icmp'

# терминал 2: события conntrack
sudo conntrack -E -p tcp 2>&1 | grep -E '32610|8443'
```

с macOS во время трассировки:

```sh
nc -vz <node1-ip> 32610
```

Интерпретация: если на `cali*`/veth видно SYN и SYN-ACK от пода, а на `tailscale0`
SYN-ACK не выходит или выходит с чужим source/port — проблема в NAT/фильтре на
ноде; если SYN-ACK выходит корректно — проблема на стороне клиента.

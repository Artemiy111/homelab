# Декларативная конфигурация Uptime Kuma 2.x

Дата проверки: 2026-08-14.

## Вывод

Uptime Kuma 2.x не имеет штатной декларативной модели мониторов: она не читает
YAML/JSON с желаемым состоянием при запуске, не создаёт мониторы из переменных
окружения и не предоставляет поддерживаемый записывающий REST API. Запрос на
конфигурационный файл остаётся открытым feature request
[#1354](https://github.com/louislam/uptime-kuma/issues/1354), без milestone и
связанной реализации.

Поэтому текущая связка `monitors.json` + `sync-monitors.mjs` не использует
«официальный декларативный режим» — такого режима нет. Это собственный
идемпотентный reconciler поверх внутреннего Socket.IO API. Для сохранения Uptime
Kuma такой подход является разумным GitOps-компромиссом, но его нужно считать
совместимым только с проверенной версией Kuma и сопровождать тестами.

## Какие механизмы поддерживает Uptime Kuma

### Конфигурационный файл и first-boot provisioning

Штатного файла с описанием мониторов и механизма начального provisioning нет.
Именно такую возможность — смонтировать JSON/YAML при старте и сразу применить
его — просит всё ещё открытый
[#1354](https://github.com/louislam/uptime-kuma/issues/1354). Следовательно,
смонтированный `monitors.json` сам по себе ничего не делает: его читает только
наш `sync-monitors.mjs`.

Постоянное состояние официального контейнера хранится в `/app/data`; в
[официальной установке](https://github.com/louislam/uptime-kuma#-how-to-install)
этот каталог подключается как volume. Это сохранение состояния приложения, а не
декларативное создание отдельных ресурсов.

### Переменные окружения

[Официальный список environment variables](https://github.com/louislam/uptime-kuma/wiki/Environment-Variables)
содержит параметры запуска сервера, хранилища/БД, TLS, сети и логирования, но не
описание мониторов. Это соответствует правилам самого проекта: настройки должны
задаваться во frontend, а environment variables не приветствуются, кроме
параметров запуска вроде `DATA_DIR`
([CONTRIBUTING, Project styles](https://github.com/louislam/uptime-kuma/blob/master/CONTRIBUTING.md#project-styles)).

Таким образом, Compose `environment:` годится для подключения и запуска Kuma,
но не является путём декларативно определить её мониторы.

### REST API и Socket.IO

Записывающего публичного REST API для CRUD мониторов нет. Официальное описание
[Internal API](https://github.com/louislam/uptime-kuma/wiki/Internal-API)
показывает, что UI управляет мониторами через Socket.IO события `add`,
`editMonitor` и `deleteMonitor`. Там же прямо сказано, что этот API предназначен
для внутреннего использования, не поддерживается для сторонних интеграций и
может меняться без предупреждения.

Открытый feature request
[#7150](https://github.com/louislam/uptime-kuma/issues/7150) предлагает добавить
записывающие REST endpoints и отдельно фиксирует текущее положение: REST API
является read-only для этого сценария, а изменения выполняются через Socket.IO.
Реализацию событий можно проверить непосредственно в исходном коде Kuma 2.x:
[`add` и `editMonitor`](https://github.com/louislam/uptime-kuma/blob/2.5.0/server/server.js).

Socket.IO поэтому позволяет построить reconciler, но не даёт контракт
стабильности, который обычно ожидается от IaC provider API. Сторонние библиотеки
и Terraform providers поверх него наследуют тот же риск совместимости.

### JSON export/import и резервная копия

JSON Backup/Restore не является способом provisioning в 2.x: функция удалена.
Официальное руководство
[Migration From v1 To v2](https://github.com/louislam/uptime-kuma/wiki/Migration-From-v1-To-v2)
называет единственным поддерживаемым способом резервного копирования копию всего
каталога `data`.

Копирование `data` восстанавливает всю базу вместе с идентичностью instance и
историей. Оно не умеет вычислять diff, сливать отдельные мониторы или безопасно
применяться поверх работающего экземпляра, поэтому это disaster recovery, а не
IaC.

### Прямое изменение SQLite/MariaDB

Редактировать таблицы напрямую не следует. Это не документированный интерфейс:
такой способ обходит серверную валидацию и побочные действия, зависит от схемы и
миграций конкретной версии и может конфликтовать с работающим процессом. Сам
проект рекомендует резервировать весь `data`, а не использовать базу как API;
даже перенос SQLite в MariaDB официально не поддерживается
([Migration From v1 To v2](https://github.com/louislam/uptime-kuma/wiki/Migration-From-v1-To-v2#can-i-migrate-my-existing-sqlite-database-to-mariadb)).

## Сторонние варианты IaC

Официальная wiki относит инструменты автоматизации к
[3rd Party Addons/Apps](https://github.com/louislam/uptime-kuma/wiki/3rd-Party-Addons-Apps),
включая AutoKuma, CLI и API wrappers. Это полезные проекты, но не встроенные и не
поддерживаемые API-контракты Uptime Kuma.

- **Собственный reconciler через Socket.IO.** Наиболее прозрачный вариант для
  этого небольшого homelab: manifest хранится рядом с Compose, поддерживается
  только нужное подмножество типов, а поведение можно тестировать. Цена — ручное
  сопровождение при обновлениях Kuma.
- **AutoKuma и Docker labels.** Удобны для обнаружения Docker-контейнеров, но
  добавляют сторонний controller. Labels также хуже выражают проверки внешнего
  HTTPS-пути, локального DNS, сертификата и не-Docker endpoints, которые нужны
  этому репозиторию.
- **Community Terraform provider.** Даёт state/plan/lifecycle, но добавляет ещё
  один слой и обычно всё равно зависит от внутреннего Socket.IO API. Это имеет
  смысл, только если Terraform уже является общей системой управления и
  выбранный provider явно поддерживает закреплённую версию Kuma. Официального
  provider от Uptime Kuma нет; такие проекты следует оценивать и закреплять как
  стороннюю зависимость.
- **Система с нативным file-based config.** Если стабильная декларативность —
  обязательное требование, правильнее выбрать инструмент, у которого manifest
  является штатным интерфейсом, а не пытаться превратить БД Kuma в него. Kuma
  тогда можно оставить лишь как UI/status page либо заменить целиком.

## Оценка текущего `sync-monitors.mjs`

### Что сделано правильно

- `monitors.json` является version-controlled desired state, а секреты логина не
  попадают в него.
- Повторный запуск идемпотентен для поддерживаемых полей: скрипт читает список,
  создаёт отсутствующее и обновляет отличающееся.
- Запись выполняется через те же Socket.IO handlers, что использует UI, а не
  напрямую в SQLite.
- Есть валидация manifest, безопасные defaults и unit-тесты сравнения.
- Скрипт намеренно не удаляет неизвестные/убранные мониторы. Это снижает риск
  потери истории и ручных настроек, хотя означает не полную декларативность.

### Ограничения и риски

- Скрипт использует внутренний, нестабильный API и запускается из плавающего
  образа `louislam/uptime-kuma:2`. Любой новый 2.x может изменить payload или
  обязательные поля. Для воспроизводимости образ следует закрепить хотя бы на
  проверенном minor/patch или digest и обновлять после тестового прогона.
- Идентификатор ресурса — изменяемое `name`. Переименование воспринимается как
  создание нового монитора; старый остаётся. Дубли имён требуют ручного
  вмешательства. Надёжнее иметь стабильный внешний ключ, например управляемый
  tag, если API выбранной версии позволяет однозначно его читать и изменять.
- Reconciliation неполный: управляется только часть полей и четыре типа
  (`http`, `dns`, `ping`, `port`); notifications, tags, parents/groups,
  credentials, status pages и удаление вне модели. Изменения остальных полей в
  UI намеренно сохраняются, но Git не является полным source of truth.
- Нет `plan`/`dry-run`, явного отчёта о drift и политики удаления. Перед
  расширением до delete нужна отдельная ownership-маркировка, чтобы никогда не
  удалять ручные ресурсы, а также явный opt-in и сохранение истории/backup.
- Скрипт входит паролем пользователя и не поддерживает 2FA. API keys Uptime Kuma
  не дают CRUD-доступ к мониторам; это следствие отсутствия публичного write API,
  а не недостаток, исправляемый другой переменной Compose.
- Тесты проверяют parser/diff, но не контракт с реальной закреплённой версией
  Kuma. Нужен integration smoke test на временном instance при обновлении образа.

## Рекомендация для репозитория

Оставить JSON + reconciler, но честно называть его локальным controller поверх
internal API, а не официальной функцией Uptime Kuma. Это не лишний костыль, а
изоляция неизбежного workaround в одном небольшом компоненте. Улучшать его стоит
в таком порядке:

1. закрепить версию/digest образа и описать процедуру обновления;
2. добавить `--check`/dry-run и integration test против этой версии;
3. ввести ownership и стабильный ключ, не зависящий от отображаемого имени;
4. явно определить authoritative поля и политику удаления;
5. только затем расширять типы, notifications и status pages.

Если нужна полная, официально стабильная декларативность без собственного
controller, ограничение находится в выборе Uptime Kuma, а не в формате текущего
скрипта.

# Файловые сетевые протоколы и сетевые ФС: параметры протоколов

Дата проверки: 2026-10-13.

Глава исследования «Протоколы разделяемого (сетевого) хранилища». Обзор,
сводные таблицы по всем категориям и выводы для homelab — в
[`overview.md`](overview.md).

Документ разбирает **протоколы** (не продукты): SMB/CIFS и SMB 2/3, NFS v2/v3/v4.0/v4.1/v4.2, AFP, WebDAV, FTP/FTPS, SFTP, SSHFS, 9P/9P2000.L, virtiofs, NBD, rsync-daemon, HTTP-файловые сервисы, а также клиентские прослойки (`davfs2`, `rclone mount/serve`) и серверные реализации (`Samba`, ядерный `knfsd`, `nfs-ganesha`, `wsdd`, `virtiofsd`).

Для каждого класса разобраны 8 осей: поддержка ОС (клиент/сервер), потребление ресурсов (ядро vs userspace), транспорт и порты, разграничение доступа, **прозрачность на диске**, шифрование/целостность, производительность и масштаб, лицензия/статус. Все утверждения — со ссылкой на первоисточник (RFC, официальная документация проекта/вендора, man-страницы, исходный код). Где официальных цифр нет, так и написано; сводка таких мест — в разделе «Не подтверждено».

## Вывод

1. **Прозрачность на диске максимальна у NFS и 9P/virtiofs, минимальна у WebDAV/FTP/SFTP-как-шар.** NFS-сервер (`knfsd`) и 9P-сервер отдают локальную ФС «как есть»: kernel-экспортёр — это pass-through в VFS, отдельного хранилища метаданных нет (единственная оговорка — делегирования и локальный доступ, см. ниже). SMB же при использовании Windows-ACL/потоков складывает их в xattr (`security.NTACL`, `user.DosStream.*`) либо в TDB, а WebDAV хранит «dead properties» и блокировки **в своей базе/индексе**, которых на диске не видно.
2. **Разграничение доступа неоднородно по природе.** SMB несёт в протоколе security descriptors (пользователи/группы SID, DACL/SACL) и умеет NTLM/Kerberos по SMB2+; NFSv4.1 **обязан** реализовывать RPCSEC_GSS (krb5/krb5i от обоих, krb5p от сервера), но исторически по умолчанию ездит на AUTH_SYS с uid/gid. FTP/SFTP/rsync/9P — аутентификация уровня сессии (или её отсутствие), per-file авторизация делегирована ОС сервера.
3. **Шифрование транспорта «из коробки» есть у SMB3, SFTP/SSHFS, WebDAV/FTP-over-TLS; у NFS оно появилось поздно** (RPC-with-TLS, `xprtsec=`; плюс `sec=krb5p`), а у 9P и rsync-daemon в протоколе отсутствует вовсе (diod прямо пишет про прослушивание даже с MUNGE; rsync — только аутентификация MD4-челленджем).
4. **SMB Direct (RDMA) и SMB Multichannel — это разные вещи**: multichannel обязателен для Direct, Direct без него не работает; в Samba multichannel включён по умолчанию с 4.15 (Linux/FreeBSD), а RDMA-транспорта нет — в `smb.conf(5)` нет ни одного параметра RDMA-транспорта.
5. **NFSv2 де-факто выведен**: в ядре Linux серверная поддержка помечена «(DEPRECATED)», по умолчанию выключена; `rpc.nfsd` умеет только major-версии 3 и 4. SMB1 тоже выключен по умолчанию: Samba `server min protocol = SMB2_02`, в Windows SMBv1 не устанавливается с версии 1709.
6. **LOCALIO (Linux 6.12+) — единственное место, где есть официальные цифры производительности NFS**: kernel-документация приводит замеры fio «с/без» обхода RPC для клиента и сервера на одном хосте; это замеры авторов патча, а не универсальный бенчмарк.
7. **WAN/интернет**: по-настоящему про NAT/интернет спроектированы только WebDAV/HTTP(S), SFTP, SMB over QUIC (UDP/443) и rclone-серверы. FTP в активном режиме требует входящего соединения к клиенту, NFS/SMB — прямых портов (445/2049 + rpcbind/вспомогательные сервисы), 9P не шифруется и не восстанавливает соединение.
8. **«Второй диск для сервисов» ≠ «файловый шаринг»**: монтируемые ФС (NFS/SMB/9P/virtiofs) дают POSIX-семантику, а rsync-daemon/NBD — нет (первый — синхронизация, второй — блочное устройство). Это ключевое различие для выбора.
9. **Из десктопных протоколов вымирают AFP и SMB1**: AFP-сервер исчез из macOS (Big Sur), клиент объявлен deprecатед и вырезан в macOS 27; Netatalk продолжает развивать AFP (4.6.0) для legacy/архивов. SMB1 выключен у Samba и Microsoft, а для discovery Samba-хостов в современной сети нужен `wsdd` (WSD: udp/3702 + tcp/5357), поскольку NetBIOS-обнаружение Windows не поддерживает.

## Как читать таблицы

- «Ядро / userspace» — где реально живёт data-path: копирования, контекстные переключения и FUSE/RPC-накладные отсюда.
- «Прозрачность на диске» — можно ли править файлы локально (мимо протокола) и сразу видеть их по сети; что протокол хранит отдельно.
- «WAN» — работает ли через NAT/интернет без дополнительных туннелей.
- Все номера портов — из реестра IANA, если не указано иное ([IANA service-names-port-numbers](https://www.iana.org/assignments/service-names-port-numbers/service-names-port-numbers.xhtml)).

## SMB/CIFS и SMB 2/3

### 1. Диалекты и совместимость

SMB-диалекты в Samba перечислены в `smb.conf(5)`: `LANMAN1`, `LANMAN2`, `NT1` (он же CIFS, SMB1), затем `SMB2_02`, `SMB2_10`, `SMB3_00`, `SMB3_02`, `SMB3_11`; по умолчанию `server max protocol = SMB3` («By default SMB3 selects the SMB3_11 variant») и `server min protocol = SMB2_02`, т. е. **SMB1 выключен из коробки** ([smb.conf(5)](https://manpages.debian.org/bookworm/samba-common-bin/smb.conf.5.en.html)). У Microsoft: SMBv2 появился в Vista/WinSrv2008, SMBv3 — в Windows 8/WinSrv2012; SMBv1 «isn't installed by default in any edition of Windows 11 or Windows Server 2019 and later» и не устанавливается начиная с 1709 ([MS «detect, enable and disable SMBv1, SMBv2, SMBv3»](https://learn.microsoft.com/en-us/windows-server/storage/file-server/troubleshoot/detect-enable-and-disable-smbv1-v2-v3)).

По спеке Microsoft (её нет в виде RFC) диалект/шифрование/подпись описаны в `[MS-SMB2]` ([MS-SMB2](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-smb2/)), RDMA-обёртка — в `[MS-SMBD]` ([MS-SMBD](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-smbd/)), legacy SMB1/CIFS — в `[MS-CIFS]` ([MS-CIFS](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-cifs/)).

### 2. Потребление ресурсов

- Сервер Samba — userspace; модель — процесс на сессию: «Each client gets a copy of the server for each session» ([smbd(8)](https://manpages.debian.org/bookworm/samba/smbd.8.en.html)). Данные между сервером и локальной ФС копируются через page cache ядра (сервер — обычный процесс); между сервером и сетью — через сокеты ядра.
- Windows-сервер — драйвер в ядре (`srv2.sys`), поэтому накладные другого класса; клиент Linux — `cifs.ko`.
- **Официальных цифр RAM/CPU нет ни у Samba, ни у Microsoft** для SMB-сервера как такового. Единственная официальная качественная оценка — про SMB Direct: «full speed with lower latency without compromising CPU utilization» ([MS SMB Direct](https://learn.microsoft.com/en-us/windows-server/storage/file-server/smb-direct)).

### 3. Транспорт и порты

- Классика: TCP 445 (`microsoft-ds`) и TCP 139 (`netbios-ssn`), плюс 137/138 для NetBIOS-обнаружения ([IANA](https://www.iana.org/assignments/service-names-port-numbers/service-names-port-numbers.xhtml)); Samba по умолчанию `smb ports = 445 139` ([smb.conf(5)](https://manpages.debian.org/bookworm/samba-common-bin/smb.conf.5.en.html)).
- Мультиплексирование: SMB2+ несёт несколько запросов в одном соединении (compounding) и мультиплексирует сессии/деревья; отключение SMBv2 отключает «Request compounding» ([MS](https://learn.microsoft.com/en-us/windows-server/storage/file-server/troubleshoot/detect-enable-and-disable-smbv1-v2-v3)).
- SMB Multichannel: несколько TCP/RDMA-соединений на одну сессию; «creates multiple RDMA connections for that single session (two per interface)»; выключение Multichannel выключает SMB Direct ([MS SMB Direct](https://learn.microsoft.com/en-us/windows-server/storage/file-server/smb-direct)).
- SMB Direct (RDMA): требует RDMA-адаптеры с обеих сторон; с WinSrv2022/Win11 поддерживает шифрование (раньше включение шифрования отключало direct data placement) ([MS SMB Direct](https://learn.microsoft.com/en-us/windows-server/storage/file-server/smb-direct)).
- SMB over QUIC: транспорт поверх UDP/443 с TLS 1.3, «SMB VPN» для интернета; по умолчанию выключен, клиент Windows всё равно сначала пробует TCP; требует PKI-сертификат и домен/local-аккаунт ([MS SMB over QUIC](https://learn.microsoft.com/en-us/windows-server/storage/file-server/smb-over-quic)).
- SMB compression: XPRESS (LZ77), XPRESS Huffman, LZNT1, PATTERN_V1; в WinSrv2025 добавлен LZ4 ([MS SMB compression](https://learn.microsoft.com/en-us/windows-server/storage/file-server/smb-compression)).
- **Samba**: multichannel добавлен в 4.4, до 4.14 считался экспериментальным, включён по умолчанию с 4.15, работает только на Linux и FreeBSD («Due to dependencies to kernel APIs of Linux or FreeBSD»); параметра RDMA-транспорта в `smb.conf(5)` нет, `capability=RDMA` встречается только в описании `interfaces` — там это bookkeeping для multi-channel ([smb.conf(5)](https://manpages.debian.org/bookworm/samba-common-bin/smb.conf.5.en.html)).

### 4. Разграничение доступа

- Аутентификация сессии: NTLM/NTLMv2, Kerberos через SPNEGO, guest/anonymous. Windows 11 24H2 Enterprise/Pro/Education требует SMB signing и для входящих, и для исходящих соединений, WinSrv2025 — только исходящих ([MS SMB signing](https://learn.microsoft.com/en-us/windows-server/storage/file-server/smb-signing)).
- Авторизация — **security descriptors** (владелец, DACL, SACL; идентификаторы — SID). Формат определён в `[MS-DTYP]` ([MS-DTYP](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-dtyp/7d4dac05-9cef-4563-a058-f108abecce1d)); общее описание — [Win32 ACL documentation](https://learn.microsoft.com/en-us/windows/win32/secauthz/access-control-lists). Это часть протокола/модели SMB, а не «надстройка».
- Linux-клиент и Samba мапят SID ↔ POSIX uid/gid (identity mapping) и хранят NT ACL отдельно от POSIX ACL (см. ось «прозрачность») ([smb.conf(5)](https://manpages.debian.org/bookworm/samba-common-bin/smb.conf.5.en.html), [vfs_acl_xattr(8)](https://manpages.debian.org/bookworm/samba-vfs-modules/vfs_acl_xattr.8.en.html)).
- LDAP/AD: надстройка реализации (Samba AD DC, winbind) — сам SMB несёт только SID/ACL и Kerberos-билеты.
- Аудит: у Samba — VFS-модули (`extd_audit`), у Windows — SACL/audit policy; в протоколе переносится SACL, но журналирование — функция реализации ([smb.conf(5)](https://manpages.debian.org/bookworm/samba-common-bin/smb.conf.5.en.html)).

### 5. Прозрачность на диске

- **NT ACL хранятся в xattr**: `vfs_acl_xattr` — «stores NTFS Access Control Lists (ACLs) in Extended Attributes (EAs) … stored in the Extended Attribute `security.NTACL`», причём «This Attribute is not listed by `getfattr -d`»; при `user.NTACL` «any user can potentially access and overwrite this information» ([vfs_acl_xattr(8)](https://manpages.debian.org/bookworm/samba-vfs-modules/vfs_acl_xattr.8.en.html)). Альтернатива — `acl_tdb` (ACL в TDB-базе, на диске не видны вовсе).
- **DOS-атрибуты и кодировка прав**: `acl_xattr:ignore system acls = yes` отключает маппинг в POSIX ACL и заставляет Samba выставлять `create mask = 0666`, `directory mask = 0777`, `map * = no`, `store dos attributes = yes` ([vfs_acl_xattr(8)](https://manpages.debian.org/bookworm/samba-vfs-modules/vfs_acl_xattr.8.en.html)).
- **Alternate Data Streams**: `vfs_streams_xattr` кладёт потоки в `user.DosStream."ADS-NAME"`; «most file systems have severe limitations on the size of xattrs», типично 4К, поэтому большие ADS работать не будут ([vfs_streams_xattr(8)](https://manpages.debian.org/bookworm/samba-vfs-modules/vfs_streams_xattr.8.en.html)). Про размеры xattr см. также `ea support`: «limits … typically 4K … the same 4K space is often used to store system metadata such as POSIX ACLs, or Samba's NT ACLs» ([smb.conf(5)](https://manpages.debian.org/bookworm/samba-common-bin/smb.conf.5.en.html)).
- **Persistent Handles (Samba 4.25, экспериментально) требуют отказа от локального доступа**: `kernel oplocks = no`, `kernel share modes = no`, `posix locking = no`, и «These settings disable interoperability with local POSIX file access and NFS clients on the affected share» — прямая плата за прозрачность ([Samba 4.25.0 release notes](https://git.samba.org/?p=samba.git;a=blob_plain;f=WHATSNEW.txt;hb=samba-4.25.0)).
- Локальная правка файла «мимо SMB» доступна всегда, но NT-ACL/потоки останутся в xattr и не будут видны приложениями, которые их не читают; наоборот, POSIX-права могут быть вторичными, если включён `acl_xattr:ignore system acls`.

### 6. Шифрование и целостность

- SMB3.0 — AES-128-CCM; SMB3.1.1 — AES-128-GCM; WinSrv2022/Win11 — AES-256-GCM/CCM; «Windows automatically negotiates this more advanced cipher method» ([MS SMB security](https://learn.microsoft.com/en-us/windows-server/storage/file-server/smb-security)).
- В Windows включение шифрования на шаре/сервере по умолчанию **отвергает** клиентов, не умеющих шифровать (`RejectUnencryptedAccess = $true`), включая SMB1 ([MS SMB security](https://learn.microsoft.com/en-us/windows-server/storage/file-server/smb-security)).
- Samba: `server smb encrypt` со значениями `off|if_required|desired|required`, по умолчанию `if_required` («enable negotiation of encryption but will not turn on data encryption globally or per share»); `server smb3 encryption algorithms` по умолчанию `AES-128-GCM, AES-128-CCM, AES-256-GCM, AES-256-CCM` ([smb.conf(5)](https://manpages.debian.org/bookworm/samba-common-bin/smb.conf.5.en.html)).
- Подпись: SMB2 нельзя отключить («For the SMB2 protocol, by design, signing cannot be disabled»); `server signing = default` — required на AD DC, иначе disabled; клиент Windows 11 24H2 Pro/Enterprise — signing обязателен ([smb.conf(5)](https://manpages.debian.org/bookworm/samba-common-bin/smb.conf.5.en.html), [MS SMB signing](https://learn.microsoft.com/en-us/windows-server/storage/file-server/smb-signing)). Алгоритмы подписи SMB3.1.1: AES-128-CMAC и HMAC-SHA256 ([smb.conf(5)](https://manpages.debian.org/bookworm/samba-common-bin/smb.conf.5.en.html)).
- Preauthentication integrity (3.1.1) не даёт откатить соединение к SMB2.x, но **не** защищает от отката к SMB1.0 ([MS SMB security](https://learn.microsoft.com/en-us/windows-server/storage/file-server/smb-security)).

### 7. Производительность и масштаб

- Сильная сторона — семантика Windows/Linux: oplocks/leases, кэш метаданных, компрессия, multichannel, RDMA, persistent handles. `smb2 leases = yes` по умолчанию ([smb.conf(5)](https://manpages.debian.org/bookworm/samba-common-bin/smb.conf.5.en.html)); отключение SMBv2 убирает «Client oplock leasing model: Limits the data transferred between the client and server, improving performance on high-latency networks» ([MS](https://learn.microsoft.com/en-us/windows-server/storage/file-server/troubleshoot/detect-enable-and-disable-smbv1-v2-v3)).
- Слабые стороны: сервер Samba — userspace, шифрование «reduces throughput as smaller packet sizes must be used … as well as the overhead of encrypting and signing all the data» ([smb.conf(5)](https://manpages.debian.org/bookworm/samba-common-bin/smb.conf.5.en.html)); persistent handles «incur a significant performance cost» ([Samba 4.25.0](https://git.samba.org/?p=samba.git;a=blob_plain;f=WHATSNEW.txt;hb=samba-4.25.0)).
- Официальных бенчмарков пропускной способности SMB нет ни у Samba, ни у Microsoft (есть только качественные утверждения).

### 8. Лицензия и статус

- Samba — GPLv3 (COPYING репозитория), активная разработка: 4.25.0 (24.09.2026), 4.26 — pre-release ([git tags](https://git.samba.org/?p=samba.git;a=tags), [WHATSNEW](https://git.samba.org/?p=samba.git;a=blob_plain;f=WHATSNEW.txt)).
- Альтернатива серверу — `ksmbd`, SMB3-сервер **в ядре** Linux: «KSMBD is a linux kernel server which implements SMB3 protocol in kernel space», открывает порт 445, операции open/read/write/close выполняются в ядре, а DCE/RPC и управление пользователями — в userspace-компоненте `ksmbd.mountd` ([kernel ksmbd doc](https://docs.kernel.org/filesystems/smb/ksmbd.html)).
- SMB1 — deprecated у всех: не ставится в Windows по умолчанию с 1709, у Samba выключен через `server min protocol = SMB2_02`.
- Для discovery в сети нужен `wsdd`: «Since NetBIOS discovery is not supported by Windows anymore, wsdd makes hosts … visible to Windows»; требования — Python 3.7+, Linux/FreeBSD/OpenBSD; слушает udp/3702 (multicast) и требует входящий tcp/5357 ([wsdd README](https://github.com/christgau/wsdd)).

## NFS (v2, v3, v4.0, v4.1, v4.2)

### 1. Версии и статус каждой

- **NFSv2** — [RFC 1094](https://www.rfc-editor.org/rfc/rfc1094) (1989). В ядре Linux клиент есть, но `CONFIG_NFS_V2` «default n» ([fs/nfs/Kconfig](https://raw.githubusercontent.com/torvalds/linux/master/fs/nfs/Kconfig)); серверный `NFSD_V2` помечен «(DEPRECATED)», `default n`, с текстом «Unless you are hosting ancient (1990's era) NFS clients, you don't need this» ([fs/nfsd/Kconfig](https://raw.githubusercontent.com/torvalds/linux/master/fs/nfsd/Kconfig)). `rpc.nfsd` из nfs-utils умеет только major-версии 3 и 4 и minor 4.0/4.1/4.2 ([rpc.nfsd(8)](https://man7.org/linux/man-pages/man8/rpc.nfsd.8.html)).
- **NFSv3** — [RFC 1813](https://www.rfc-editor.org/rfc/rfc1813) (1995), stateless, отдельный MOUNT-протокол; серверная поддержка в ядре «always available when CONFIG_NFSD is selected» ([fs/nfsd/Kconfig](https://raw.githubusercontent.com/torvalds/linux/master/fs/nfsd/Kconfig)).
- **NFSv4.0** — [RFC 7530](https://www.rfc-editor.org/rfc/rfc7530) (obsoletes RFC 3530); **NFSv4.1** — [RFC 8881](https://www.rfc-editor.org/rfc/rfc8881) (obsoletes RFC 5661, 2020); **NFSv4.2** — [RFC 7862](https://www.rfc-editor.org/rfc/rfc7862) (2016). Возможности 4.1: сессии, exactly-once semantics (execution order/тривиальные слоты), backchannel, pNFS, delegations. Возможности 4.2 по аннотации RFC: «Server-Side Copy, Application Input/Output (I/O) Advise, Space Reservations, Sparse Files, Application Data Blocks, and Labeled NFS» ([RFC 7862, Abstract](https://www.rfc-editor.org/rfc/rfc7862)).
- В ядре Linux клиент по умолчанию собирает NFSv3 (`CONFIG_NFS_V3 default y`), а NFSv4.0/4.1/4.2 — отдельными опциями ([fs/nfs/Kconfig](https://raw.githubusercontent.com/torvalds/linux/master/fs/nfs/Kconfig)).

### 2. Потребление ресурсов

- Data-path в ядре: `nfsd` — kernel threads, userspace (`rpc.nfsd`) «merely specifies what sort of sockets the kernel service should listen on, what NFS versions it should support, and how many kernel threads it should use» ([rpc.nfsd(8)](https://man7.org/linux/man-pages/man8/rpc.nfsd.8.html)); клиент — `nfs.ko`. Копирования: page cache → сетевой стек (без userspace-перекопирования), что и делает NFS самым дешёвым из сетевых ФС.
- **Единственные официальные цифры производительности NFS** — в документации LOCALIO: замеры fio (directio, qd=8, 16 libaio-потоков) «With LOCALIO: 4K read: IOPS=979k … 128K read: IOPS=402k, BW=49.1GiB/s» против «Without LOCALIO: 4K read: IOPS=79.2k … 128K read: IOPS=33.9k, BW=4234MiB/s» ([NFS LOCALIO](https://docs.kernel.org/filesystems/nfs/localio.html)). Это измерения авторов патча на конкретном стенде, а не универсальные требования.
- Про RAM официальных цифр нет (FUSE в NFS-пути не участвует; estimates из академических работ по FUSE к NFS не применимы).

### 3. Транспорт и порты

- Порт 2049/TCP (IANA `nfs`), rpcbind 111; «auxiliary services such as the NLM service can choose any unused port number at random» — отсюда проблемы с фаерволом ([nfs(5)](https://man7.org/linux/man-pages/man5/nfs.5.html)). `rpc.nfsd -p` меняет порт, `-r` включает RDMA на порту `nfsrdma` 20049 ([rpc.nfsd(8)](https://man7.org/linux/man-pages/man8/rpc.nfsd.8.html), [IANA](https://www.iana.org/assignments/service-names-port-numbers/service-names-port-numbers.xhtml) — 20049 зарегистрирован по [RFC 8267](https://www.rfc-editor.org/rfc/rfc8267)).
- Мультиплексирование: NFSv4 несёт все операции (включая mount/lock) одним протоколом; клиент Linux умеет несколько TCP-соединений на маунт — `nconnect=` ([nfs(5)](https://man7.org/linux/man-pages/man5/nfs.5.html)).
- NFS over RDMA: RPC-over-RDMA v1 ([RFC 5666](https://www.rfc-editor.org/rfc/rfc5666)); для NFSv4.1 с сессиями нужен двунаправленный RPC по одной RDMA-связи ([RFC 8167](https://www.rfc-editor.org/rfc/rfc8167)).
- pNFS: layout-типы file (в RFC 5661/8881), block ([RFC 5663](https://www.rfc-editor.org/rfc/rfc5663)), object, flexfile ([RFC 8154](https://www.rfc-editor.org/rfc/rfc8154)); требования к layout-типам — [RFC 8434](https://www.rfc-editor.org/rfc/rfc8434). Клиент Linux имеет отдельные опции ядра `PNFS_FILE_LAYOUT`, `PNFS_BLOCK`, `PNFS_FLEXFILE_LAYOUT` ([fs/nfs/Kconfig](https://raw.githubusercontent.com/torvalds/linux/master/fs/nfs/Kconfig)).
- Через NAT/интернет NFS не работает «сам по себе»: rpcbind/случайные порты, отсутствие шифрования в базовом протоколе, чувствительность к задержкам и разрывам; для файрвола документация советует фиксировать порты и/или использовать `xprtsec=tls` ([nfs(5)](https://man7.org/linux/man-pages/man5/nfs.5.html), [exports(5)](https://man7.org/linux/man-pages/man5/exports.5.html)).
- NFS LOCALIO (Linux 6.12+; `CONFIG_NFS_LOCALIO` определён в `fs/Kconfig` — в v6.11 его ещё нет, в v6.12 есть: [v6.11](https://raw.githubusercontent.com/torvalds/linux/v6.11/fs/Kconfig), [v6.12](https://raw.githubusercontent.com/torvalds/linux/v6.12/fs/Kconfig)) — вспомогательный RPC `UUID_IS_LOCAL` (program 400122) по тому же соединению; после handshake клиент **обходит RPC/XDR** для read/write/commit и работает с локальной ФС напрямую. «This protocol isn't part of an IETF standard»; работает только с AUTH_UNIX ([NFS LOCALIO](https://docs.kernel.org/filesystems/nfs/localio.html)).

### 4. Разграничение доступа

- **AUTH_SYS** (по умолчанию на v3 и часто на v4 при `sec=sys`): «relies on sending local UID and GID numbers to identify users»; сервер верит, что uid/gid проверены клиентом, «This is an easy system to spoof, but on a trusted physical network between trusted hosts, it is entirely adequate» ([nfs(5)](https://man7.org/linux/man-pages/man5/nfs.5.html)).
- **RPCSEC_GSS** ([RFC 2203](https://www.rfc-editor.org/rfc/rfc2203)): NFSv4.1 «clients and servers MUST implement RPCSEC_GSS» (но не обязаны использовать); krb5 и krb5i — MUST для обоих, krb5p — MUST для сервера и SHOULD для клиента; AUTH_NONE/AUTH_SYS «MAY be implemented» ([RFC 8881 §2.2.1.1](https://www.rfc-editor.org/rfc/rfc8881)). NFSv4.0 в этом вопросе слабее — там мандаты на более слабые алгоритмы Kerberos ([там же](https://www.rfc-editor.org/rfc/rfc8881)).
- Выбор flavor: `sec=` в экспорте и в mount; порядок в списке определяет приоритет ([exports(5)](https://man7.org/linux/man-pages/man5/exports.5.html), [nfs(5)](https://man7.org/linux/man-pages/man5/nfs.5.html)).
- Маппинг uid: `root_squash` по умолчанию («chooses a uid and gid of 65534 for squashed access»), `all_squash`, `no_root_squash` ([exports(5)](https://man7.org/linux/man-pages/man5/exports.5.html)). NFSv4 использует строки `user@domain` (rpc.idmapd/nfsidmap) ([nfsv4(4) FreeBSD](https://man.freebsd.org/cgi/man.cgi?query=nfsv4&sektion=4&manpath=FreeBSD+14.3-RELEASE)).
- ACL: POSIX mode bits + POSIX ACL (через локальную ФС); NFSv3 ACL — нестандартное расширение Solaris «NFSACL», «never became a standard part of the NFS version 3 specification» ([nfs(5)](https://man7.org/linux/man-pages/man5/nfs.5.html), опции ядра `NFS_V3_ACL`/`NFSD_V3_ACL` в [Kconfig](https://raw.githubusercontent.com/torvalds/linux/master/fs/nfsd/Kconfig)); NFSv4 ACL — «semantically richer than POSIX ACLs … not fully compatible … some translation between the two is required» ([nfs(5)](https://man7.org/linux/man-pages/man5/nfs.5.html)). В свежем ядре есть экспериментальная поддержка draft `draft-ietf-nfsv4-posix-acls` — `NFSD_V4_POSIX_ACLS`, default n ([fs/nfsd/Kconfig](https://raw.githubusercontent.com/torvalds/linux/master/fs/nfsd/Kconfig)).
- LDAP/AD/FreeIPA: надстройка (idmap-домены, LDAP-каталог имён, Kerberos KDC); сам протокол несёт только flavor и принципала.
- Аудит: вне протокола (auditd/syslog на сервере).

### 5. Прозрачность на диске

- NFS-сервер **не хранит отдельного слоя метаданных**: экспортируется существующая локальная ФС; «filesystem operations … need a different way to refer to a particular dentry … filehandle fragment» — то есть отображение в VFS, а не копия ([Making Filesystems Exportable](https://docs.kernel.org/filesystems/nfs/exporting.html)). Файлы, созданные по сети, сразу видны локально (с точностью до клиентских кэшей и NFSv4 delegations).
- Оговорки, которые протокол накладывает:
  - `subtree_check` ломается при переименованиях; в nfs-utils по умолчанию он не включён: «explicitly requested with no_subtree_check» и «no_subtree_check as subtree checking tends to cause more problems» ([exports(5)](https://man7.org/linux/man-pages/man5/exports.5.html)).
  - NFSv4 ACL не совпадает с POSIX ACL — при смешивании возможны потери/трансляция ([nfs(5)](https://man7.org/linux/man-pages/man5/nfs.5.html)).
  - Delegations: клиент работает с файлом локально, поэтому серверу приходится отзывать делегирование при локальном доступе; FreeBSD прямо требует не выдавать делегирования, если ФС трогают локально, NLM или Samba («Note that Samba server access would be considered "local access"»), а `vfs.nfsd.enable_locallocks = 0` запрещает локальные byte-range locks ([nfsv4(4) FreeBSD](https://man.freebsd.org/cgi/man.cgi?query=nfsv4&sektion=4&manpath=FreeBSD+14.3-RELEASE)).
  - `root_squash` делает root-пользователя «nobody» — файлы, записанные контейнером от root, на диске будут принадлежать 65534 ([exports(5)](https://man7.org/linux/man-pages/man5/exports.5.html)).
- LOCALIO меняет картину радикально: клиент открывает файл через `nfsd_open_local_fh()` и «issue reads, writes and commits directly to the underlying local filesystem», то есть RPC-слой исчезает полностью ([NFS LOCALIO](https://docs.kernel.org/filesystems/nfs/localio.html)).

### 6. Шифрование и целостность

- В базовом протоколе шифрования нет: только `sec=krb5i` (целостность) и `sec=krb5p` (шифрование каждого RPC), «expect some performance impact» ([nfs(5)](https://man7.org/linux/man-pages/man5/nfs.5.html)).
- RPC-with-TLS: [RFC 9289](https://www.rfc-editor.org/rfc/rfc9289) («opportunistic TLS» для ONC RPC, обновляет RFC 5531); на клиенте `xprtsec=none|tls|mtls`, «If tls is specified, the client uses RPC-with-TLS to provide in-transit confidentiality», по умолчанию обычно `none` ([nfs(5)](https://man7.org/linux/man-pages/man5/nfs.5.html)); на сервере `xprtsec=` в `exports(5)`, значения `none:tls:mtls` ([exports(5)](https://man7.org/linux/man-pages/man5/exports.5.html)).
- Целостность без Kerberos/TLS не обеспечивается (UDP-контрольные суммы — не защита).

### 7. Производительность и масштаб

- Сильные: стриминг близко к линейному (ядро-ядро), read-ahead/writeback, клиентский кэш атрибутов и данных (close-to-open coherency описана в [nfs(5)](https://man7.org/linux/man-pages/man5/nfs.5.html)), `nconnect=` для агрегации, pNFS для распараллеливания данных, RDMA для латентности, LOCALIO для колокации.
- Слабые: метаданные на высокой латентности дороги — каждая операция это минимум один round-trip; в NFSv4 это частично смягчается COMPOUND (несколько операций в одном запросе), в v2/v3 такого механизма нет. Блокировки/leases требуют state-recovery; `hard`-маунт на пропавшем сервере подвешивает процессы (классика — описана в [nfs(5)](https://man7.org/linux/man-pages/man5/nfs.5.html) в части про таймауты/retrans).
- NFSv3 stateless → легче через NAT/фаервол, но sideband-протоколы (NLM/MOUNT) усложняют.

### 8. Лицензия и серверные реализации

- `knfsd` — GPLv2, часть ядра; nfs-utils — userspace-утилиты (GPL). Развивается: 4.2, RDMA, nfsd v4.1 sessions, RPC-with-TLS, LOCALIO (6.12+), экспериментальный NFSv4 POSIX ACLs.
- **nfs-ganesha** — userspace-сервер: «NFS-Ganesha is an NFSv3,v4,v4.1 fileserver that runs in user mode … also supports the 9p.2000L protocol» ([README](https://github.com/nfs-ganesha/nfs-ganesha)); официальный сайт: «supports NFSv3, NFSv4.0, NFSv4.1, and NFSv4.2 … NFSv3 with integrated NLM (lock manager) and MNT (mountd) services … supports NFSv4 including pNFS (v4.1) and a subset of V4.2 commands» ([nfs-ganesha.github.io](https://nfs-ganesha.github.io/)); версия 4.0; FSAL-бэкенды в дереве — VFS, CEPH, GLUSTER, GPFS, LIZARDFS, SAUNAFS, RGW, PROXY_V3/V4, MEM, PSEUDO ([src/FSAL](https://api.github.com/repos/nfs-ganesha/nfs-ganesha/contents/src/FSAL)). RDMA-абстракция (mooshika) — «has not been worked on in quite some time and is not currently tested or supported» ([nfs-ganesha.github.io](https://nfs-ganesha.github.io/)).
- Клиенты/серверы ОС — см. Таблицу 3: Windows Server for NFS (v2/v3/v4.1), Client for NFS (v2/v3) ([MS](https://learn.microsoft.com/en-us/windows-server/storage/nfs/nfs-overview)); macOS до NFSv4.1 ([mount_nfs](https://keith.github.io/xcode-man-pages/mount_nfs.8.html)); FreeBSD v4.1/4.2 + RFC 8276 xattrs + flexfile pNFS ([nfsv4(4)](https://man.freebsd.org/cgi/man.cgi?query=nfsv4&sektion=4&manpath=FreeBSD+14.3-RELEASE)).

## AFP (Apple Filing Protocol)

- **Что это**: протокол файлового доступа Apple; официальное описание — архивный Apple-гайд [Apple Filing Protocol Programming Guide](https://developer.apple.com/library/archive/documentation/Networking/Conceptual/AFP/Introduction/Introduction.html); Netatalk: «AFP … the protocol used for file sharing on Apple II, Classic Mac OS, and Mac OS X» ([netatalk.io/docs](https://netatalk.io/docs/)).
- **ОС**: клиент был встроен в macOS; сервер AFP из macOS удалён (macOS 11 Big Sur), а в macOS 27 клиент вырезан — Netatalk 4.6.0 фиксирует: «Apple is withdrawing AFP support in macOS Golden Gate» ([Netatalk NEWS](https://github.com/Netatalk/netatalk/blob/main/NEWS.md)). Netatalk предоставляет сервер (Linux/*BSD/Solaris/macOS) и сторонние клиенты (GNOME Files, kio-afp, FUSE-клиент Netatalk, `afpcmd`) ([netatalk.io/docs](https://netatalk.io/docs/)). Точные Apple-release-notes (когда именно объявлен deprecation) машинно-читаемо подтвердить не удалось — см. «Не подтверждено».
- **Транспорт**: AFP поверх TCP, порт 548 (`afpovertcp` в [IANA](https://www.iana.org/assignments/service-names-port-numbers/service-names-port-numbers.xhtml)); шифрования транспорта в протоколе нет (см. «Не подтверждено»); аутентификация — UAM-модули; Netatalk документирует собственные UAM, включая [SRP UAM Community Specification](https://netatalk.io/docs/) ([Netatalk docs](https://netatalk.io/docs/)).
- **Разграничение доступа**: AFP-сессии и «volumes», классически — AppleShare-права (владелец/группа/everyone + «privileges»), на POSIX-серверах практически всё мапится в POSIX-права Netatalk; встроенные AFP-ACL в 3.x поддерживаются частично (ACL в AFP 3.x — Apple's «Access Control Lists» extensions; в Netatalk — через POSIX ACL).
- **Прозрачность на диске**: данные — обычные файлы; часть метаданных macOS (FinderInfo, resource forks) и база CNID хранятся **вне самого файла** (расширенные атрибуты/AppleDouble-схема, CNID-backend), поэтому локальная правка расходится с ними; в Netatalk 4.x удалён deprecated Berkeley DB backend CNID (`dbd`), остались другие схемы ([Netatalk NEWS](https://github.com/Netatalk/netatalk/blob/main/NEWS.md)).
- **Статус**: протокол фактически legacy (Apple уходит), но сервер развивается: Netatalk 4.6.0 — «the fastest and most capable AFP» с новым FUSE-клиентом, `afpcmd`, поддержкой AFP 2.x/3.4 и планами по SMB-интеропу ([Netatalk NEWS](https://github.com/Netatalk/netatalk/blob/main/NEWS.md)). Лицензия Netatalk — GPLv2 (COPYING репозитория).

## WebDAV и «HTTP-файловые сервисы»

### WebDAV

- **Спецификация**: [RFC 4918](https://www.rfc-editor.org/rfc/rfc4918) (обновляет RFC 2518) — методы PROPFIND/PROPPATCH/MKCOL/COPY/MOVE/LOCK/UNLOCK, свойства, compliance-классы «1, 2, 3» ([§18](https://www.rfc-editor.org/rfc/rfc4918)). Расширения: ACL ([RFC 3744](https://www.rfc-editor.org/rfc/rfc3744)), версионирование/DeltaV ([RFC 3253](https://www.rfc-editor.org/rfc/rfc3253)), упорядоченные коллекции ([RFC 3648](https://www.rfc-editor.org/rfc/rfc3648)), квоты ([RFC 4331](https://www.rfc-editor.org/rfc/rfc4331)), bindings ([RFC 5842](https://www.rfc-editor.org/rfc/rfc5842)), коллекционная синхронизация ([RFC 6578](https://www.rfc-editor.org/rfc/rfc6578)), монтирование в Windows Explorer ([RFC 4709](https://www.rfc-editor.org/rfc/rfc4709)).
- **Транспорт/порты**: это HTTP поверх TCP (по умолчанию 80/443); TLS — стандартный HTTP-over-TLS. Мультиплексирование — на уровне HTTP (keep-alive, HTTP/2/3: [RFC 9113](https://www.rfc-editor.org/rfc/rfc9113), [RFC 9114](https://www.rfc-editor.org/rfc/rfc9114)); семантика методов и Range-запросов — [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110).
- **Аутентификация**: часть HTTP. RFC 4918 прямо требует: «Basic authentication … MUST NOT be used … unless the connection is secure», а «WebDAV applications MUST support the Digest authentication scheme» ([RFC 4918 §20.1](https://www.rfc-editor.org/rfc/rfc4918)). Kerberos/Negotiate/OAuth/OIDC — **надстройки реализации** (например, Nextcloud/IIS), не часть RFC 4918.
- **Авторизация**: по умолчанию — политика сервера вне протокола; ACL-метод и свойство `DAV:acl` определены в [RFC 3744](https://www.rfc-editor.org/rfc/rfc3744), но его поддержка опциональна и к POSIX-правам отношения не имеет: «Access Control Protocol … specifies a principal and a set of privileges that are either granted or denied» (RFC 3744 §1).
- **Прозрачность на диске — ключевая слабость**: протокол различает live- и dead-свойства; dead properties «has its syntax and semantics enforced by the client» и хранятся сервером ([RFC 4918 §4.3](https://www.rfc-editor.org/rfc/rfc4918)); блокировки (LOCK/UNLOCK, `DAV:lockdiscovery`) — состояние сервера, не ФС ([RFC 4918 §6](https://www.rfc-editor.org/rfc/rfc4918)). Поэтому локальная правка файла «мимо WebDAV» не обновит свойства/локи, а часть серверов хранит их в БД/индексе, а не в xattr. Отдельно отмечу deprecated-механизм: «lock-null resources» объявлены устаревшими и заменены «locked empty resources» ([RFC 4918, Appendix D](https://www.rfc-editor.org/rfc/rfc4918)).
- **Ограничения файловой семантики**: нет владельца/прав POSIX, нет атомарного rename в общем случае, нет жёстких ссылок; `davfs2` прямо пишет: «as the file system interface and the WebDAV protocol are quite different, this is not possible without losses» ([davfs2 README](https://git.savannah.nongnu.org/cgit/davfs2.git/plain/README)).
- **Статус**: RFC 4918 — Proposed Standard 2007, актуален и активно реализуется (Nextcloud, IIS, Apache mod_dav, `rclone serve webdav`).

### HTTP-файловые сервисы (plain HTTP/HTTPS)

- Read-only (или почти read-only) отдача файлов по HTTP: методы GET/HEAD, Range-запросы ([RFC 9110 §14](https://www.rfc-editor.org/rfc/rfc9110)), кэширование ([RFC 9111](https://www.rfc-editor.org/rfc/rfc9111)), листинги — не часть HTTP (autoindex у nginx/Apache — фича сервера).
- Нет блокировок, нет атомарного rename, PUT создаёт файл целиком; «файловая система» клиентом не монтируется. Для homelab подходит для скачивания ISO/медиа, не для шары с записью.

## FTP и FTPS

- **База**: [RFC 959](https://www.rfc-editor.org/rfc/rfc959) (STD 9, 1985). Два соединения: control (порт 21) и data. В активном режиме «The server-process default data port is the port adjacent to the control connection port (i.e., L-1)», т. е. 20, и сервер **сам** подключается к клиенту; в пассивном клиент слушает ([RFC 959](https://www.rfc-editor.org/rfc/rfc959)). Порты в реестре: `ftp` 21, `ftp-data` 20, `ftps` 990, `ftps-data` 989 ([IANA](https://www.iana.org/assignments/service-names-port-numbers/service-names-port-numbers.xhtml)).
- **Аутентификация/авторизация**: USER/PASS (в базовом RFC — открытым текстом), «anonymous FTP»; авторизация — средствами ОС сервера. Расширения безопасности: AUTH/ADAT/PROT/PBSZ/CCC/MIC/CONF/ENC ([RFC 2228](https://www.rfc-editor.org/rfc/rfc2228)); FTPS (implicit и explicit) — [RFC 4217](https://www.rfc-editor.org/rfc/rfc4217), причём «None of the above commands are required to be implemented» ([RFC 2228](https://www.rfc-editor.org/rfc/rfc2228)).
- **Расширения**: FEAT ([RFC 2389](https://www.rfc-editor.org/rfc/rfc2389)), EPRT/EPSV для IPv6 и NAT ([RFC 2428](https://www.rfc-editor.org/rfc/rfc2428); «The EPSV command requests that a server listen on a data port and wait for a connection»), MLST/MLSD/SIZE/MDTM/REST STREAM ([RFC 3659](https://www.rfc-editor.org/rfc/rfc3659)).
- **WAN/NAT**: активный режим требует входящего соединения от сервера к клиенту — за NAT не работает без port forward/ALG; пассивный требует диапазона портов на сервере. Именно поэтому появились EPSV/EPRT ([RFC 2428](https://www.rfc-editor.org/rfc/rfc2428)) и [RFC 1579 «Firewall-Friendly FTP»](https://www.rfc-editor.org/rfc/rfc1579), на который RFC 2428 прямо ссылается («RFC 1579 recommends using the passive command when [behind] NATs»).
- **Прозрачность на диске**: полная (обычные файлы), но у протокола нет модели атрибутов: никаких ACL, xattr, владельца в базовом протоколе; RFC 3659 добавляет «facts» (в т.ч. `perm` и OS-specific) — они не эквивалентны POSIX-правам ([RFC 3659](https://www.rfc-editor.org/rfc/rfc3659)).
- **Статус**: протокол не развивается (расширения 1994–2007), средства защиты — TLS-обвязка; `vsftpd` 3.0.5 (2015) — фактически maintenance ([vsftpd](https://security.appspot.com/vsftpd.html)). Браузеры убрали ftp:// (Chrome 88+, Firefox 90+), но это про браузеры, не про протокол.

## SFTP и SSHFS

- **SFTP** — подсистема SSH; транспорт и аутентификация — из SSH: [RFC 4251](https://www.rfc-editor.org/rfc/rfc4251), [RFC 4252](https://www.rfc-editor.org/rfc/rfc4252), [RFC 4253](https://www.rfc-editor.org/rfc/rfc4253), [RFC 4254](https://www.rfc-editor.org/rfc/rfc4254); мультиплексирование каналов в одном TCP-соединении (порт 22), `MaxSessions` по умолчанию 10 ([sshd_config(5)](https://man7.org/linux/man-pages/man5/sshd_config.5.html)).
- **Сам протокол SFTP так и остался черновиком**: последняя ревизия — [draft-ietf-secsh-filexfer-13](https://datatracker.ietf.org/doc/html/draft-ietf-secsh-filexfer-13) (2006); OpenSSH реализует версию 3 ([draft-ietf-secsh-filexfer-02](https://datatracker.ietf.org/doc/html/draft-ietf-secsh-filexfer-02)) плюс расширения (например, `copy-data` с OpenSSH 9.0) ([openssh.com/specs.html](https://www.openssh.com/specs.html)); `-Q protocol_feature` перечисляет поддерживаемое ([sftp-server(8)](https://man7.org/linux/man-pages/man8/sftp-server.8.html)).
- **Разграничение доступа**: аутентификация — SSH (ключи/пароль/keyboard-interactive/GSSAPI-kerberos/сертификаты); авторизация — средствами сервера: `ChrootDirectory`, `Subsystem sftp internal-sftp`, `sftp-server -R` (read-only), `-u umask`, `-P/-p` (фильтрация запросов), `-d` (стартовый каталог) ([sftp-server(8)](https://man7.org/linux/man-pages/man8/sftp-server.8.html), [sshd_config(5)](https://man7.org/linux/man-pages/man5/sshd_config.5.html)). Внутри SFTP нет ACL-модели — атрибуты файла включают только права/uid/gid/времена по версии 3.
- **Прозрачность на диске**: полная — сервер работает с обычной ФС; никаких отдельно хранимых метаданных (chroot не меняет файлы). SFTP не отдаёт xattr/ACL; права видны как mode+uid/gid.
- **Производительность**: архитектурно — прикладной request/response поверх SSH: каждый stat/open/read — round-trip; нет серверного data-path и нет параллельных каналов на файл; официальных цифр нет. SSH-шифрование и MAC добавляют CPU-стоимость на оба конца (userspace).
- **SSHFS**: FUSE-клиент, монтирующий SFTP; на сервере **ничего ставить не нужно**, кроме sshd («there's nothing to do on the server-side»). Статус проекта — фактически maintenance: «at present SSHFS does not have any active, regular contributors … has no capacity to do any development beyond addressing high-impact issues» ([SSHFS README](https://github.com/libfuse/sshfs)). Есть `directport`/`vsock` — прямое подключение к `sftp-server` **без шифрования** («this is insecure as connection will happen without encryption») ([SSHFS README](https://github.com/libfuse/sshfs)).
- **WAN**: SFTP рассчитан на интернет, в отличие от NFS/9P — один порт, шифрование, восстановление каналов.
- **Лицензия**: SSHFS — GPLv2 ([COPYING](https://github.com/libfuse/sshfs)); OpenSSH распространяется под BSD-подобной лицензией (файл LICENCE в поставке; я его не проверял — см. «Не подтверждено»).

## 9P (Plan 9 File Protocol) и его варианты

- **Протокол**: транзакции T/R, теги, строка версии в `version`; сообщения little-endian; NUL запрещён в строках ([Plan 9 man 5 intro](https://9p.io/magic/man2html/5/intro), [man 5 version](https://9p.io/magic/man2html/5/version)). Варианты: `9P2000` (legacy), `9P2000.u` (Unix-расширения), `9P2000.L` (Linux-ориентированный) ([kernel 9p doc](https://docs.kernel.org/filesystems/9p.html), [diod protocol.md](https://github.com/chaos/diod/blob/master/protocol.md)).
- **Аутентификация в самом протоколе**: сообщение `auth` создаёт `afid`, который затем передаётся в `attach`; «If the server does not require authentication, it returns Rerror to the Tauth message»; сам протокол аутентификации «definition is not part of this manual» ([Plan 9 man 5 attach](https://9p.io/magic/man2html/5/attach)). 9P2000.L использует `attach`/`auth` из 9P2000.u с `n_uname` ([diod protocol.md](https://github.com/chaos/diod/blob/master/protocol.md)).
- **Транспорт**: TCP (IANA 564, `9pfs`), unix-сокет, virtio, fd, usbg ([kernel 9p doc](https://docs.kernel.org/filesystems/9p.html), [IANA](https://www.iana.org/assignments/service-names-port-numbers/service-names-port-numbers.xhtml)). diod по умолчанию слушает 564 или указанный `--listen`; «Only bob can attach and access files as bob»/«Anyone can attach and access files as themselves» в зависимости от `--no-auth` ([diod README](https://github.com/chaos/diod)).
- **Клиент**: v9fs в ядре Linux; опции `trans=`, `version=`, `uname=`, `access=user|any|client`, `cache=none|loose|fscache|…`; «loose caches (and by extension at the moment fscache) do not necessarily validate cached values on the server» ([kernel 9p doc](https://docs.kernel.org/filesystems/9p.html)).
- **Честные ограничения diod** (лучший первоисточник по 9P-эксплуатации): «If the server restarts or the client loses its connection, the client will need to be remounted. There is no automatic recovery»; «there is no mechanism in 9P to allow the server to invalidate a cached object»; «Even when securely authenticated with MUNGE, connections are not protected against eavesdropping or other attacks»; «File locking may not work as expected» ([diod README](https://github.com/chaos/diod)).
- **Прозрачность на диске**: полная — сервер (diod) отдаёт локальное дерево; отдельного хранилища метаданных нет (CNID-подобных сущностей в 9P нет). Плата — «interactive performance is poor» без кэша и отсутствие invalidation ([diod README](https://github.com/chaos/diod)).
- **virtio-9p** (QEMU) — 9P поверх virtio (`trans=virtio` в примерах kernel-документации v9fs), транспорт без сети ([kernel 9p doc](https://docs.kernel.org/filesystems/9p.html)). Утверждение «9p-транспорт вытесняется virtiofs» — оценочное: официального deprecation-заявления QEMU я не нашёл (страницы QEMU по 9pfs/virtiofs в docs/master сейчас отдают 404).
- **Серверные реализации**: `diod` (GPL-2.0-or-later, [README](https://github.com/chaos/diod)), `nfs-ganesha` (9p.2000L, [ganesha](https://nfs-ganesha.github.io/)), сервер Plan 9/9front. Лицензия самого протокола — спецификация, свободная к реализации.

## virtiofs

- **Архитектура**: паравиртуализированное устройство virtio «virtio-fs»; «The virtio-fs device uses the FUSE protocol for file system requests … The guest acts as the FUSE client while the host acts as the FUSE server. The `/dev/fuse` interface … is replaced with the virtio-fs device interface»; FUSE-запросы идут в virtqueue, для приоритетных запросов есть отдельная очередь `hiprio` ([kernel virtiofs doc](https://docs.kernel.org/filesystems/virtiofs.html)).
- **Сеть не используется вообще**: «providing file system access without networking» ([kernel virtiofs doc](https://docs.kernel.org/filesystems/virtiofs.html)) — то есть по определению нет NAT/шифрования транспорта/WAN; область применения — гость на том же хосте.
- **DAX**: shared memory region ID 0 — окно DAX; «The device MAY provide the DAX Window to memory-mapped access to file contents. If present, the DAX Window MUST be shared memory region ID 0»; маппинг через FUSE_SETUPMAPPING; «The driver MUST NOT access DAX window areas that have not been mapped» ([virtio spec 1.2, §5.11.6.4](https://docs.oasis-open.org/virtio/virtio/v1.2/virtio-v1.2.html)).
- **atime**: «The atime-related mount options … are ignored … the same as the underlying filesystem of the directory that has been exported on the host» ([kernel virtiofs doc](https://docs.kernel.org/filesystems/virtiofs.html)).
- **Разграничение доступа и безопасность**: гостю не нужен аутентификатор — доверие обеспечивается виртуализацией; на стороне хоста `virtiofsd` изолируется: «The ability to invoke syscalls is limited using seccomp(2)», режимы `--sandbox namespace|chroot|none`, pid/net/mount-namespace, `pivot_root` ([virtiofsd README](https://gitlab.com/virtio-fs/virtiofsd/-/raw/main/README.md)). Важно: `--posix-acl` и `--security-label` по умолчанию `never` — ACL и SELinux-метки гостю по умолчанию **не** экспонируются ([virtiofsd README](https://gitlab.com/virtio-fs/virtiofsd/-/raw/main/README.md)).
- **Прозрачность на диске**: полная — экспортируется каталог хоста как есть; сам virtiofsd работает от хостового пользователя (или в user namespace).
- **ОС**: клиент — ядро Linux 5.4+ (гость), сервер — `virtiofsd` на хосте (Linux, а также macOS через Virtualization.framework в гостях; QEMU/Kata/Cloud Hypervisor). Rust-реализация `virtiofsd` требует libcap-ng и libseccomp ([virtiofsd README](https://gitlab.com/virtio-fs/virtiofsd/-/raw/main/README.md)).
- **Статус**: virtio-спека 1.2 включает устройство; Rust-virtiofsd активно развивается; официальных цифр производительности в документации ядра/спеки нет (кроме качественного «increase performance and provide semantics that are not possible with network file systems»).

## NBD (Network Block Device)

- **Что это**: блочное устройство по сети, не файловая ФС; «every time the client computer wants to read, e.g., /dev/nb0, it sends a request over TCP to the server»; «Unlike NFS, it is possible to put any filesystem on it» ([kernel NBD doc](https://docs.kernel.org/admin-guide/blockdev/nbd.html)). Включён в обзор как «сетевое хранилище», но по семантике это аналог iSCSI, а не файловый шаринг.
- **Транспорт/порт**: TCP/10809 — «The IANA-reserved port for NBD» ([NBD protocol](https://github.com/NetworkBlockDevice/nbd/blob/master/doc/proto.md), [IANA](https://www.iana.org/assignments/service-names-port-numbers/service-names-port-numbers.xhtml)). Три варианта negotiate: oldstyle, newstyle, fixed newstyle ([NBD protocol](https://github.com/NetworkBlockDevice/nbd/blob/master/doc/proto.md)).
- **Где живёт код**: клиент — модуль ядра (`nbd`, параметры `max_part` default 0, `nbds_max` default 16); «the nbd-server is completely in userspace. In fact, the nbd-server has been successfully ported to other operating systems, including Windows» ([kernel NBD doc](https://docs.kernel.org/admin-guide/blockdev/nbd.html)). Сервер `nbdkit` — отдельный проект ([nbdkit(1)](https://libguestfs.org/nbdkit.1.html)).
- **Аутентификация**: в базовом протоколе нет; TLS — опциональная фаза handshake (`NBD_OPT_STARTTLS`) ([NBD protocol](https://github.com/NetworkBlockDevice/nbd/blob/master/doc/proto.md)). Многие серверы полагаются на loopback/фаервол/ssh-туннель.
- **Прозрачность**: блочное устройство — ни файлов, ни метаданных; локально ничего «не видно» без монтирования ФС поверх; зато примонтированная ФС ведёт себя как локальный диск.
- **Ограничения WAN**: сырой блочный доступ чувствителен к потерям/задержкам и требует ровно одного писателя; официальных предупреждений в proto.md нет (это архитектурный факт, а не цитата).
- **Статус/лицензия**: протокол документирован в репозитории, IANA-регистрация 2010 (обновлена 2024); `nbd-server`/`nbd-client` — GPLv2 ([COPYING репозитория](https://raw.githubusercontent.com/NetworkBlockDevice/nbd/master/COPYING)), `nbdkit` — BSD-подобная лицензия Red Hat ([nbdkit(1), LICENSE](https://libguestfs.org/nbdkit.1.html)).

## rsync-daemon (rsync://)

- **Форма**: служба rsync в режиме `--daemon`, URL `rsync://[USER@]HOST[:PORT]/MODULE`, порт 873 (IANA `rsync`) ([rsync(1)](https://man7.org/linux/man-pages/man1/rsync.1.html), [rsyncd.conf(5)](https://man7.org/linux/man-pages/man5/rsyncd.conf.5.html)). Это не монтируемая ФС — только синхронизация файлов.
- **Аутентификация и шифрование — главная слабость**: «The authentication protocol used in rsync is a 128 bit MD4 based challenge response system. This is fairly weak protection»; «the rsync daemon protocol does not currently provide any encryption of the data … Use ssh as the transport if you want encryption»; TLS — только через внешний прокси (haproxy/nginx), примеры приведены в man-странице ([rsyncd.conf(5)](https://man7.org/linux/man-pages/man5/rsyncd.conf.5.html)).
- **Авторизация**: модули с `path`, `auth users`, `secrets file`, `hosts allow`, `read only`, `uid`/`gid`, `use chroot` (по умолчанию «tries to enable a chroot but allows the daemon to continue») ([rsyncd.conf(5)](https://man7.org/linux/man-pages/man5/rsyncd.conf.5.html)).
- **Прозрачность**: файлы и каталоги обычные; rsync умеет переносить POSIX-метаданные (права, владельца, времена, ACL/xattr флагами `--acls`/`--xattrs`) ([rsync(1)](https://man7.org/linux/man-pages/man1/rsync.1.html)) — но это не «общая ФС», а копирование.
- **WAN**: рекомендованный путь — rsync-по-ssh: «rsync -av --rsh=ssh host::module /dest», при этом демон запускается через ssh и config читается из home ([rsync(1)](https://man7.org/linux/man-pages/man1/rsync.1.html)).
- **Статус**: GPLv3 ([COPYING](https://github.com/RsyncProject/rsync)), активно развивается и поддерживает современные TLS-обвязки через прокси.

## Клиентские прослойки: davfs2 и rclone mount/serve

### davfs2

- WebDAV как ФС: «davfs2 is a Linux file system driver that allows you to mount a WebDAV resource into your Unix file system tree» (монтирование `mount.davfs`), поддерживает «SSL and proxy, HTTP authentication (basic and digest) and client certificates» ([davfs2 README](https://git.savannah.nongnu.org/cgit/davfs2.git/plain/README)).
- Явно **не** замена сетевой ФС: «davfs2 is not intended as a replacement for distributed file systems like nfs, coda, cifs»; «davfs2 does not handle different WebDAV users within one mount» ([davfs2 README](https://git.savannah.nongnu.org/cgit/davfs2.git/plain/README)).
- Кэш обязателен: «davfs2 will store a local copy of all open files in its cache», «always needs local copies of all open files»; перед открытием — conditional GET; запись откладывается (по умолчанию 10 с) и «mount.davfs may block quite some time» при массовой загрузке ([davfs2 README](https://git.savannah.nongnu.org/cgit/davfs2.git/plain/README)).
- Прозрачность: dead properties/локи живут на сервере; davfs2 не может показать место на диске без RFC 4331 и «can't help but lie» ([davfs2 README](https://git.savannah.nongnu.org/cgit/davfs2.git/plain/README)).
- Статус: GPLv3 ([COPYING](https://git.savannah.nongnu.org/cgit/davfs2.git/plain/COPYING)), 1.6.0 (2020) — «личное использование», без заявленной высокой производительности.

### rclone mount / serve

- `rclone mount` — FUSE (на Windows — WinFsp/cgofuse, на macOS — macFUSE или FUSE-T); VFS-кэш режимами `--vfs-cache-mode off|minimal|writes|full`, рекомендуют `full` для записи ([rclone mount](https://rclone.org/commands/rclone_mount/)); официальное предупреждение: «File systems expect things to be 100% reliable, whereas cloud storage systems are a long way from 100% reliable» ([rclone mount](https://rclone.org/commands/rclone_mount/)).
- `rclone serve` умеет отдавать хранилище по nfs/ftp/sftp/webdav/http/s3/dlna/docker ([rclone serve](https://rclone.org/commands/rclone_serve/)).
- `rclone serve nfs` — NFSv3-сервер, помечен «Experimental» (добавлен в v1.65), и **без аутентификации**: «This server does not implement any authentication so any client will be able to access the data»; по умолчанию слушает loopback и случайный порт; AUTH_UNIX объявляется только ради BSD-клиентов, но per-user контроля нет ([rclone serve nfs](https://rclone.org/commands/rclone_serve_nfs/)).
- Прозрачность: rclone — «виртуальная» ФС поверх объектного хранилища; атрибуты POSIX синтезируются, что видно по поддержке метаданных/`--vfs-cache-mode` ([rclone mount](https://rclone.org/commands/rclone_mount/)). Детальный разбор s3fs, rclone и объектных протоколов — в главе [`object-storage-and-cloud-drives.md`](object-storage-and-cloud-drives.md).

## Разграничение доступа — сравнительная сводка

| Модель | Кто её несёт | Где живёт состояние | Что реально проверяет доступ | Аутентификация |
|---|---|---|---|---|
| POSIX (uid/gid + mode bits) | NFSv2/v3, 9P, SFTP, FTP, rsync, 9P2000.L | ФС сервера (inode) | Сервер по локальным правам; ID приходит из RPC/сессии | AUTH_SYS (uid/gid) — NFSv2/v3; вообще без протокольной аутентификации — FTP/9P |
| POSIX ACL | NFSv3 (частично), NFSv4 (через трансляцию), Samba (маппинг) | xattrs ФС сервера (`system.posix_acl_*`) | Сервер/ядро | Как выше |
| NFSv4 ACL | NFSv4.0/4.1/4.2 (RFC 7530/8881) | Атрибут `acl` в ФС (если ФС умеет) либо трансляция в POSIX ACL | Сервер | Обязателен RPCSEC_GSS (krb5/krb5i/krb5p) ([RFC 8881](https://www.rfc-editor.org/rfc/rfc8881)) |
| Solaris NFSACL (v3) | Нестандартное расширение | На ФС сервера | Сервер | AUTH_SYS на v3 |
| SMB security descriptor (DACL/SACL, SID) | SMB2/3 (модель Windows, [MS-DTYP](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-dtyp/7d4dac05-9cef-4563-a058-f108abecce1d)) | xattr `security.NTACL` (Samba `acl_xattr`) или TDB | Сервер SMB по ACE; POSIX-права — отдельный, вторичный слой (можно отключить маппинг) | NTLM/NTLMv2, Kerberos, guest |
| WebDAV ACL (`DAV:acl`) | RFC 3744 (опционально), поверх HTTP | База/индекс WebDAV-сервера (не ФС) | Сервер WebDAV | HTTP: Digest; Basic — только по TLS ([RFC 4918 §20.1](https://www.rfc-editor.org/rfc/rfc4918)) |
| LDAP/AD/FreeIPA/OIDC | Надстройка реализации | Каталог/IdP | Через mapping модули (winbind, idmapd, nsswitch, OAuth-модуль сервера) | Kerberos/OIDC/OAuth поверх базовой схемы протокола |

Что важно различать:

- **Протокол vs надстройка.** SMB *несёт* SID/DACL/SACL и Kerberos-билеты; LDAP/AD-интеграция в Samba — надстройка (winbind), но она обязательна для «настоящей» доменной модели. NFSv4 *несёт* flavor и принципала; каталог имён (`user@domain`) — idmap-надстройка. WebDAV *несёт* только HTTP-аутентификацию; OIDC/SSO — целиком надстройка.
- **ID-маппинг — источник ошибок.** NFSv4 использует строки, NFSv2/v3 — числа; без согласованных пространств имён получаются «nobody/nogroup» ([nfsv4(4) FreeBSD](https://man.freebsd.org/cgi/man.cgi?query=nfsv4&sektion=4&manpath=FreeBSD+14.3-RELEASE)). Samba мапит SID↔POSIX через `idmap`/`winbind`.
- **Аудит.** Ни один из разобранных протоколов не является системой аудита: события пишут серверы (Samba audit VFS, auditd, журналы nfsd). SACL переносится по SMB, но его исполнение — функция сервера.

## Прозрачность на диске — сводка

| Схема | Видны ли локальные правки по сети | Хранит ли протокол метаданные отдельно | Что теряется/ломается при «неправильном» пути |
|---|---|---|---|
| NFS (knfsd/ganesha) | Да (в пределах кэшей и delegations) | Нет (pass-through в VFS); исключение — pNFS-компоненты и state | При локальном доступе ограничиваются делегирования; ACL-трансляция POSIX↔NFSv4; root_squash меняет владельца |
| 9P (diod/ganesha) | Да | Нет | Нет invalidation кэша на клиенте; локальная правка при закэшированном файле может «не дойти» ([diod](https://github.com/chaos/diod)) |
| virtiofs | Да (каталог хоста как есть) | Нет | ACL/SELinux-метки не экспонируются без `--posix-acl`/`--security-label` ([virtiofsd](https://gitlab.com/virtio-fs/virtiofsd/-/raw/main/README.md)) |
| SMB (Samba, Windows-модель) | Да, но NT-ACL/потоки — в xattr/TDB | Да: `security.NTACL`, `user.DosStream.*`, DOS-атрибуты; persistent handles — в on-disk/ctdb БД ([Samba 4.25](https://git.samba.org/?p=samba.git;a=blob_plain;f=WHATSNEW.txt;hb=samba-4.25.0)) | Локальные приложения не видят NT-ACL; `security.NTACL` не виден `getfattr -d`; большие ADS не влезают в 4К xattr |
| AFP (Netatalk) | Частично: данные видны, resource forks/CNID — вне файла (xattr/AppleDouble + CNID-backend) | Да | Прямая правка ломает resource fork/FinderInfo и синхронизацию CNID |
| WebDAV | Данные — да, свойства/локи — нет | Да: dead properties и locks в БД/индексе сервера ([RFC 4918 §4.3](https://www.rfc-editor.org/rfc/rfc4918)) | Правка мимо WebDAV оставляет устаревшие свойства/локи; нет владельца/POSIX-прав |
| FTP/FTPS/SFTP | Да | Нет | Атрибуты не переносятся: SFTP — mode/uid/gid, FTP — только «facts» ([RFC 3659](https://www.rfc-editor.org/rfc/rfc3659)) |
| rsync-daemon | Да (файлы как есть) | Нет | Без `--acls`/`--xattrs` метаданные не переносятся (но это копирование, а не общая ФС) |
| NBD | Н/Д (блочное устройство) | Нет | ФС внутри видна только после монтирования; два писателя = порча ФС |

Практический вывод для homelab: если нужен «второй диск, который сервисы видят как обычный каталог», подходят NFS, 9P и virtiofs (pass-through). Если Windows-клиентам нужны «настоящие» Windows-ACL, придётся принять, что ACL/потоки уедут в xattr, а локальная правка будет их игнорировать, а включение persistent handles в Samba прямо ломает локальный доступ.

## Потребление ресурсов — сводка (только то, что подтверждено)

|---|---|---|
| NFS (knfsd) | ядро↔ядро (RPC/XDR в ядре) | RAM — нет; пропускная способность — только замеры LOCALIO в kernel-doc ([ссылка](https://docs.kernel.org/filesystems/nfs/localio.html)) |
| SMB (Samba) | userspace-сервер (`smbd` процесс/сессия) + ядерный клиент | нет (только качественные утверждения MS про SMB Direct и шифрование) |
| SMB (Windows) | ядро (srv2.sys / ksmbd) | нет; ksmbd: «The subset of performance related operations belong in kernelspace» ([ksmbd](https://docs.kernel.org/filesystems/smb/ksmbd.html)) |
| 9P | ядерный клиент v9fs + userspace-сервер | нет; diod: «By default, there is no caching so interactive performance is poor» ([diod](https://github.com/chaos/diod)) |
| virtiofs | ядерный FUSE-клиент-гость + userspace `virtiofsd` | нет (спека/док ядра цифр не приводят) |
| WebDAV | HTTP-стек + приложение или `davfs2` (обязательный локальный кэш) | нет; README davfs2 производительности не обещает, но кэш обязателен |
| FTP/SFTP | userspace оба конца | нет |
| rsync | userspace | нет |
| NBD | ядерный клиент + userspace-сервер | нет |

## Не подтверждено / «официальных цифр нет»

1. **AFP-история deprecation у Apple.** Apple делает release notes JS-страницами: `developer.apple.com/documentation/macos-release-notes/...` отдаёт только оболочку, извлечь текст AFP-предупреждения не удалось. Поэтому конкретика «сервер AFP удалён в macOS 11, клиент deprecатед в macOS 15.5, удалён в macOS 27» опирается на [Netatalk NEWS](https://github.com/Netatalk/netatalk/blob/main/NEWS.md) и архивный [Apple AFP Programming Guide](https://developer.apple.com/library/archive/documentation/Networking/Conceptual/AFP/Introduction/Introduction.html); **прямой Apple-цитаты с URL дать не могу**.
2. **Версия ядра, где появился ksmbd** — в kernel-doc [ksmbd](https://docs.kernel.org/filesystems/smb/ksmbd.html) версия не указана, поэтому «5.15» я не утверждаю.
3. **RDMA-транспорт в Samba.** Я утверждаю «нет» на основании отсутствия параметров RDMA-транспорта в `smb.conf(5)` и того, что `capability=RDMA` относится лишь к multi-channel. Прямого заявления «Samba не поддерживает SMB Direct» в доступных мне первоисточниках нет (wiki.samba.org недоступен из сети этой сессии). Это **аргумент от отсутствия**, а не цитата.
4. **SMB over QUIC в Samba** — то же: в `smb.conf(5)` параметров нет; официального «не поддерживаем» не найдено.
5. **SMB Direct в Linux-клиенте (`cifs.ko`)** — официальной документации «не поддерживается» нет; в документации ядра RDMA-транспорт для CIFS/SMB не упоминается.
6. **SMB-производительность** — официальных цифр пропускной способности/RAM нет ни у Samba, ни у Microsoft.
7. **Метрики производительности 9P/WebDAV/SFTP/FTP/rsync/NBD** — официальных цифр нет; накладные описаны архитектурно (userspace, FUSE, RTT на операцию).
8. **Цифры LOCALIO** — официальные (в kernel-doc), но это замеры авторов патча на конкретном стенде (fio, directio, qd=8), не универсальный бенчмарк.
9. **SMB на iOS/iPadOS** — факт «Files.app умеет SMB» подтверждается практикой, но официальной страницы Apple с описанием протокола/версии я не нашёл; в таблице это помечено.
10. **Windows `Client for NFS` версии** — по официальной странице v2/v3 ([MS](https://learn.microsoft.com/en-us/windows-server/storage/nfs/nfs-overview)); поддержка NFSv4.1 только на стороне сервера, клиентских деталей в этом документе нет. Туда же — наличие NFS-сервера (`nfsd`) в macOS и WebDAV-монтирование в Finder: официальных страниц Apple в моей выборке нет.
11. **Лицензии** указаны по файлам `COPYING`/манифестам репозиториев; точные SPDX-идентификаторы вендоры в документации не публикуют. Лицензию OpenSSH (BSD-подобная) я по файлу не проверял.
12. **Версия ядра с LOCALIO.** Часто встречается «Linux 6.7»; по тегам ядра символа `CONFIG_NFS_LOCALIO` в `fs/Kconfig` нет в v6.9–v6.11 и есть начиная с v6.12 (проверено по [v6.11](https://raw.githubusercontent.com/torvalds/linux/v6.11/fs/Kconfig) и [v6.12](https://raw.githubusercontent.com/torvalds/linux/v6.12/fs/Kconfig)), поэтому в документе указано 6.12+. Точный merge-коммит я не искал.
13. **Шифрование AFP и детали ACL** — AFP 3.x формально имеет extensions для ACL, но официальной доступной спеки (кроме архивного Programming Guide) я не нашёл; описание опирается на Netatalk и общее знание архитектуры, в документе помечено как неподтверждённое.
14. **virtiofs и версия ядра** — 5.4 подтверждено наличием `VIRTIO_FS` в [fs/fuse/Kconfig v5.4](https://raw.githubusercontent.com/torvalds/linux/v5.4/fs/fuse/Kconfig) и отсутствием в [v5.3](https://raw.githubusercontent.com/torvalds/linux/v5.3/fs/fuse/Kconfig); точный коммит не искал.

## Вывод

1. **Объектная модель принципиально не файловая.** У S3 нет иерархии (ключ — плоское имя в `bucket + key + version`), нет in-place/частичной записи (только PUT целого объекта или multipart-сборка), запись атомарна в пределах одного ключа, а не транзакции по нескольким ключам ([AWS S3 — How S3 works](https://docs.aws.amazon.com/AmazonS3/latest/userguide/Welcome.html)). Поэтому попытка «просто смонтировать S3 как диск» всегда упирается в семантику, а не в скорость.
2. **Консистентность у разных облаков разная, и это надо знать.** AWS S3 с 2020 г. даёт strong read-after-write для PUT/DELETE во всех регионах, но *конфигурация бакета* (например, только что созданный бакет) эвентуальна ([AWS](https://docs.aws.amazon.com/AmazonS3/latest/userguide/Welcome.html)). Swift в собственной документации про large objects прямо ссылается на eventual consistency листинга ([OpenStack Swift](https://docs.openstack.org/swift/latest/api/large_objects.html)). GCS держит отдельную страницу про consistency ([GCS](https://cloud.google.com/storage/docs/consistency)).
3. **WORM/retention — это функция объектного протокола, а не файловой системы.** S3 Object Lock (compliance/governance + legal hold), Azure immutability policy (time-based/legal hold), GCS Bucket Lock/object holds — все они версионированно-объектные, работают поверх версий. В compliance-режиме S3 объект не удалит даже root (единственный способ — удалить сам аккаунт) ([AWS Object Lock](https://docs.aws.amazon.com/AmazonS3/latest/userguide/object-lock.html)).
4. **MinIO Community остановлен — это факт, а не слух.** Официальный README репозитория `minio/minio` содержит плашку «THIS REPOSITORY IS NO LONGER MAINTAINED», community-версия теперь распространяется только исходниками (без бинарных релизов), а поддержка переведена в AIStor Free/Enterprise ([README `minio/minio`](https://github.com/minio/minio)); по GitHub API репозиторий `archived=true`, последний push — 2026-04-24 ([GitHub API](https://api.github.com/repos/minio/minio)). Альтернативы — RustFS (Apache-2.0, Rust), Garage (AGPLv3, Rust), SeaweedFS (Apache-2.0, Go), Ceph RGW, Zenko CloudServer.
5. **«S3 как ФС» — это всегда компромисс.** s3fs открыто перечисляет, что ломается: нет атомарного rename, случайная запись = перезапись всего объекта, нет координации между монтирующими, inotify не видит чужих правок ([s3fs README](https://github.com/s3fs-fuse/s3fs-fuse)). Mountpoint for Amazon S3 официально не поддерживает rename каталогов, symlink и правку файлов ([Mountpoint README](https://github.com/awslabs/mountpoint-s3)). goofys себя называет «Filey System, not File System» ([goofys README](https://github.com/kahing/goofys)).
6. **Полноценный POSIX поверх S3 даёт только отдельный слой метаданных.** JuiceFS хранит данные чанками в объектном хранилище, а метаданные — в БД (Redis/TiKV/MySQL/PostgreSQL/SQLite), и заявляет full POSIX и strong consistency ([JuiceFS — Introduction](https://juicefs.com/docs/community/introduction/), [Architecture](https://juicefs.com/docs/community/architecture)). Это и есть цена POSIX: появляется внешняя БД, без которой данные в бакете нечитаемы.
7. **«Облачные диски» делятся на два лагеря по прозрачности на диске.** Nextcloud по умолчанию хранит файлы «как есть» и индексирует их в БД, но при primary object storage официально пишет: «All metadata (filenames, directory structures…) is stored in Nextcloud and not in the object store… the object store only holds the file content by unique identifier» — файлы вне Nextcloud нечитаемы ([Nextcloud primary storage](https://docs.nextcloud.com/server/latest/admin_manual/configuration_files/primary_storage.html)). Seafile вообще не хранит файлы как есть: это Git-подобные объекты Commit/FS/Block с content-defined chunking (~8 МБ) и дедупликацией ([Seafile Data Model](https://manual.seafile.com/latest/develop/data_model/)).
8. **E2EE и «прозрачность» несовместимы.** Nextcloud сам противопоставляет SSE (сервер расшифровывает; имена и структура каталогов *не* шифруются) и E2EE (расшифровывает только клиент): для E2EE-файлов веб-интерфейс умеет только чтение/скачивание, чанковые загрузки для веба надо отключать, а мнемоника невосстановима администратором ([Nextcloud SSE](https://docs.nextcloud.com/server/latest/admin_manual/configuration_files/encryption_configuration.html), [E2EE app](https://github.com/nextcloud/end_to_end_encryption)).
9. **Главная ось для homelab — «увидит ли клиент локальную правку на сервере».** Сетевые протоколы (SMB/NFS/WebDAV) и объектные шлюзы отдают живые данные сразу; серверы с индексом/БД (Nextcloud с object store, oCIS `decomposedfs`, Seafile, Syncthing, JuiceFS) требуют, чтобы правка прошла через систему, либо пересканирования. oCIS честно пишет это для PosixFS: «Infinite Scale needs to be notified of changes and has to add required metadata via extended attributes» ([oCIS PosixFS](https://doc.owncloud.com/ocis/8.2/admin/deployment/storage/posixfs.html)).
10. **Разграничение доступа живёт на двух уровнях.** В объектных хранилищах это bearer-токены: pre-signed URL (S3), SAS (Azure), signed URL (GCS), temp URL (Swift) — они *несут* права подписавшего и утекают вместе с ним ([AWS pre-signed URL](https://docs.aws.amazon.com/AmazonS3/latest/userguide/using-presigned-url.html), [Azure SAS](https://learn.microsoft.com/en-us/azure/storage/common/storage-sas-overview)). В «облачных дисках» — share-ссылки/группы/роли + OIDC/SAML/LDAP. E2EE ломает серверный ACL/поиск/шаринг — это заложено в модели угроз.

## Оси сравнения

Для каждой технологии важно смотреть на:

1. **Поддержка ОС и клиенты** — стандартный протокол vs только родной клиент.
2. **Потребление ресурсов** — язык/рантайм, БД, официальные требования (или их отсутствие).
3. **Прозрачность на диске** — что физически лежит на носителе; можно ли править локально и увидеть через протокол; что в БД/индексе; дедуп/шифрование.
4. **Модель доступа** — аутентификация, авторизация, видит ли админ всё, E2EE.
5. **Протоколы наружу** — S3/WebDAV/SFTP/SMB/NFS/HTTP и их ограничения.
6. **Масштаб/квоты/лицензия/статус.**

## Подробный разбор

### 1. Принципиальная разница объектной модели от файловой

Из документации AWS S3 ([How Amazon S3 works](https://docs.aws.amazon.com/AmazonS3/latest/userguide/Welcome.html)):

- объект = «a file and any metadata that describes the file»; «Every object has a *key*… the unique identifier for the object within the bucket»;
- «you can think of Amazon S3 as a basic data map between "bucket + key + version" and the object itself»;
- «Updates to a single key are atomic… you will get either the old data or the new data, but never partial or corrupt data»;
- «Amazon S3 does not support object locking for concurrent writers… the request with the latest timestamp wins»;
- «Updates are key-based. There is no way to make atomic updates across keys».

Следствия:

- **Нет иерархии.** Разделитель `/` в ключе — соглашение, а не каталоги. Исключение — S3 *directory buckets* (S3 Express One Zone), где объекты организованы в иерархические директории; это отдельный тип бакета ([AWS](https://docs.aws.amazon.com/AmazonS3/latest/userguide/Welcome.html)).
- **Нет in-place edit.** Запись — это PUT целого объекта либо multipart-сборка: 3 шага (initiate → upload parts → complete), part numbers 1…10 000, при завершении части «no longer exist» и собираются в объект ([AWS multipart](https://docs.aws.amazon.com/AmazonS3/latest/userguide/mpuoverview.html)). Azure page blob — исключение: туда можно писать страницы 512 Б in-place ([Azure REST](https://learn.microsoft.com/en-us/rest/api/storageservices/understanding-block-blobs--append-blobs--and-page-blobs)), но это уже не «общая» объектная семантика.
- **Атомарность — на объект, не на транзакцию.** Нет multi-object ACID; условные записи (conditional writes) позволяют только не перезаписать существующий ключ ([AWS multipart](https://docs.aws.amazon.com/AmazonS3/latest/userguide/mpuoverview.html)).
- **Консистентность зависит от реализации.** AWS: strong read-after-write для объектов во всех регионах, но конфигурация бакета эвентуальна, и после включения versioning рекомендуется подождать 15 минут перед записью ([AWS](https://docs.aws.amazon.com/AmazonS3/latest/userguide/Welcome.html)). Swift документально упоминает eventual consistency (для container listing в контексте динамических large objects) ([Swift large objects](https://docs.openstack.org/swift/latest/api/large_objects.html)); отдельной страницы «overview_consistency» в актуальной версии документации нет — URL отдаёт 404 на момент проверки.

### 2. AWS S3: ключевые механизмы

**Multipart.** «It's a best practice to use multipart upload for objects that are 100 MB or larger»; части можно грузить параллельно и в любом порядке; ETag завершённого объекта — «checksum of checksums», не обязательно MD5; при использовании checksums номера частей обязаны быть последовательными с 1 ([AWS multipart](https://docs.aws.amazon.com/AmazonS3/latest/userguide/mpuoverview.html)).

**Versioning.** Версии получают уникальный version ID; объекты, существовавшие до включения versioning, имеют версию `null` ([AWS](https://docs.aws.amazon.com/AmazonS3/latest/userguide/Welcome.html)).

**Object Lock / WORM.** «Object Lock works only in buckets that have S3 Versioning enabled»; две оси — *retention period* (fixed или variable; может быть дефолт на бакете) и *legal hold* (без срока). Режимы: **compliance** — «can't be overwritten or deleted by any user, including the root user… The only way to delete an object under the compliance mode before its retention date expires is to delete the associated AWS account»; **governance** — обходится при `s3:BypassGovernanceRetention` + заголовок `x-amz-bypass-governance-retention:true`. Всё применяется **к версии объекта** ([AWS Object Lock](https://docs.aws.amazon.com/AmazonS3/latest/userguide/object-lock.html)).

**Pre-signed URL.** «pre-signed URLs are bearer tokens that grant access to those who possess them»; capabilities ограничены правами того, кто создал URL; IAM-user креды — до 7 дней (SigV4), консоль — 1–12 часов; с временными кредами URL живёт до истечения самих кред. Есть условие `s3:signatureAge` для отказа старым подписям ([AWS pre-signed URL](https://docs.aws.amazon.com/AmazonS3/latest/userguide/using-presigned-url.html)).

**ACL vs bucket policy vs IAM.** По умолчанию Object Ownership = `Bucket owner enforced`, «all ACLs are disabled»; владелец бакета владеет всеми объектами. AWS рекомендует policies (bucket/access point/IAM), а не ACL; bucket policy — resource-based IAM-политика до 20 KB. ACL — механизм, «that predates IAM» ([AWS Object Ownership](https://docs.aws.amazon.com/AmazonS3/latest/userguide/about-object-ownership.html), [AWS](https://docs.aws.amazon.com/AmazonS3/latest/userguide/Welcome.html)).

### 3. Swift, Azure Blob, GCS, CDMI

**Swift.** Один объект по умолчанию не больше 5 ГБ; крупное собирается из сегментов через SLO (статический манифест JSON со списком `path/etag/size_bytes`, ≤1000 сегментов, манифест ≤2 МБ, сегмент ≥1 байт, integrity проверяется) или DLO (`X-Object-Manifest: {container}/{prefix}`, integrity не гарантируется из-за eventual consistency листинга). Есть `X-Newest` — читать самую свежую реплику (дороже) ([Swift large objects](https://docs.openstack.org/swift/latest/api/large_objects.html)). Доступ: `X-Container-Read/Write`, account ACL, temp URL через HMAC и `X-Account-Meta-Temp-URL-Key[-2]`; versioning — через `X-Versions-Location` / `X-History-Location` ([Swift API](https://docs.openstack.org/api-ref/object-store/)).

**Azure Blob.** Block blob: до 50 000 блоков, максимальный блок 4000 MiB, максимальный blob ≈190.7 TiB (v2019-12-12+), одиночный PUT ≤5000 MiB; незакоммиченные блоки живут до одной недели; коммит списка блоков перезаписывает свойства/метаданные и отбрасывает незакоммиченное. Page blob: коллекция страниц 512 Б, in-place запись, максимум 8 TiB. Append blob: до 50 000 блоков по 4 MiB ≈195 GiB, только дозапись. Любой blob можно взять в lease (эксклюзивная запись) и снять snapshot ([Azure REST](https://learn.microsoft.com/en-us/rest/api/storageservices/understanding-block-blobs--append-blobs--and-page-blobs)).

**Azure immutability.** Time-based retention (минимум 1 день, максимум 146 000 дней ≈400 лет) + legal hold; есть container-level и version-level WORM (version-level требует versioning). Политика бывает unlocked (для тестов) и locked (нельзя удалить/сократить; container-level locked — не более 5 увеличений). Immutability несовместима с NFS 3.0 и SFTP-аккаунтами ([Azure immutability](https://learn.microsoft.com/en-us/azure/storage/blobs/immutable-storage-overview)).

**Azure SAS.** Три типа: user delegation (Microsoft Entra, рекомендуется), service, account. Бывает ad hoc (start/expiry/permissions в URI) и service SAS со stored access policy. «It's not possible to audit the generation of SAS tokens» — генерацию токена отследить нельзя; токен — bearer. Есть clock skew ±15 мин ([Azure SAS](https://learn.microsoft.com/en-us/azure/storage/common/storage-sas-overview)).

**GCS.** XML API — S3-совместимый REST с `Authorization`, `x-goog-*`-заголовками и endpoints `BUCKET.storage.googleapis.com` (interoperability/HMAC-ключи) ([GCS XML API](https://cloud.google.com/storage/docs/xml-api/overview)). Object Versioning: `generation`/`metageneration`, noncurrent-версии; при удалении live-версии без generation она становится noncurrent. Google рекомендует soft delete вместо versioning для защиты от потерь ([GCS Object Versioning](https://cloud.google.com/storage/docs/object-versioning)). Bucket Lock: retention-политика применяется ретроактивно; lock неотменяем, максимум 100 лет (3 155 760 000 с), при этом ставится project lien, мешающий удалить проект ([GCS Bucket Lock](https://cloud.google.com/storage/docs/bucket-lock)).

**CDMI.** Стандарт SNIA, он же ISO/IEC 17826 (CDMI 2.0 = ISO/IEC 17826:2022): open, license-free, vendor-neutral, RESTful HTTP-протокол для namespace discovery, provisioning, lifecycle/access management и portability; объекты — data/container/queue. CDMI 3.0 добавляет MCP как peer-протокол ([SNIA CDMI](https://www.snia.org/cdmi)).

### 4. Self-hosted S3-реализации и что случилось с MinIO

**MinIO.** Официальный README репозитория `minio/minio` начинается плашкой: «**THIS REPOSITORY IS NO LONGER MAINTAINED.**», альтернативы — AIStor Free (standalone, free license) и AIStor Enterprise. Далее: «The MinIO community edition is now distributed as source code only. We will no longer provide pre-compiled binary releases for the community version»; старые бинарные релизы «will not receive updates». Лицензия остаётся AGPLv3, и README подчёркивает обязательства AGPLv3 при коммерческом использовании ([README `minio/minio`](https://github.com/minio/minio)). GitHub API подтверждает: `archived=true`, `license=AGPL-3.0`, последний push 2026-04-24, 61 324 ⭐ ([GitHub API](https://api.github.com/repos/minio/minio)). Итого: community-разработка остановлена, развитие — в проприетарном AIStor.

**RustFS.** Apache-2.0, Rust, «broad S3 API compatibility», erasure sets, KMS через Vault (KV2/Transit) и AWS KMS, OIDC/SSO, IAM/Policies, multi-tenancy, bucket quota, audit log, Helm. Отдельно декларируют Swift API и Keystone, SFTP/FTPS/WebDAV (opt-in). Заявлена «MinIO On-Disk Compatibility» (preview, gated feature `rio-v2`), но объекты, зашифрованные MinIO, для RustFS нечитаемы ([README](https://github.com/rustfs/rustfs)). 34 869 ⭐, push 2026-10-13 ([GitHub API](https://api.github.com/repos/rustfs/rustfs)).

**Garage.** «S3-compatible distributed object storage service designed for self-hosting at a small-to-medium scale», узлы в разных физических локациях, локальные реплики, «lightweight, easy to operate». AGPLv3. Используется Deuxfleurs в проде с 2020 ([README](https://github.com/deuxfleurs-org/garage)). Детали метаданных/консистентности в README отсутствуют — **по этим осям официальные источники не собраны**.

**Ceph RGW.** `radosgw` — HTTP-фронт к RADOS через `librados`; поддерживает S3 (large subset) и Swift API в общем namespace, имеет собственную user management, IAM/STS, LDAP/Keystone/OPA, MFA, экспорт по NFS/SMB, full object deduplication. Важно: «Ceph Object Storage does **NOT** use the Ceph Metadata Server» ([Ceph RGW](https://docs.ceph.com/en/latest/radosgw/)).

**SeaweedFS.** Единый `weed` даёт S3 + POSIX + lakehouse. Мастер-серверы (Raft) отслеживают тома, не файлы; volume-серверы хранят блобы в append-only файлах с 16-байтным in-memory индексом; filer добавляет дерево и хранит метаданные в выбранном внешнем store (LevelDB/RocksDB/SQLite/MySQL/PostgreSQL/Redis/etcd/TiKV/…). Заявленные оптимизации: «One disk read per blob», «40 bytes of metadata per file on disk», hot-репликация и warm-erasure-coding, AES256-GCM at rest ([README](https://github.com/seaweedfs/seaweedfs)).

**Zenko CloudServer.** Node.js-реализация S3-фронта над одним или несколькими бэкендами (файловый, memory, multiple, облака). Apache-2.0. Последний релиз 7.10.61 (2026-10-13) — проект активен ([README](https://github.com/scality/cloudserver), [GitHub API](https://api.github.com/repos/scality/cloudserver)).

### 5. Объектное хранилище как ФС

**s3fs-fuse** («native object format») — единственный из набора, который явно сохраняет объект так, чтобы файлы читались другими S3-инструментами вроде AWS CLI. Цена — ограничения из README: «random writes or appends to files require rewriting the entire object», «no atomic renames», «no coordination between multiple clients mounting the same bucket», «no hard links», «inotify detects only local modifications, not external ones» ([README](https://github.com/s3fs-fuse/s3fs-fuse)).

**goofys** прямо позиционируется как «Filey System instead of a File System»: «strives for performance first and POSIX second»; случайные записи «either fail… or faked (no per-file permission)»; нет on-disk кэша; консистентность close-to-open ([README](https://github.com/kahing/goofys)). Последняя активность — июль 2024 ([GitHub API](https://api.github.com/repos/kahing/goofys)).

**Mountpoint for Amazon S3** оптимизирован под «high read throughput to large objects… and to write new objects sequentially from a single client»; прямо не для правок: «don't work on your Git repository or run `vim` in Mountpoint»; официально поддерживает только Amazon S3, совместимость с другими S3 «may inadvertently break» ([README](https://github.com/awslabs/mountpoint-s3)).

**JuiceFS** — пример «правильного» POSIX поверх объектов: данные разбиваются на chunks ≤64 МБ, слайсы (одна непрерывная запись), затем физические блоки ≤4 МБ; метаданные — во внешней БД; заявлены full POSIX, strong consistency, flock/fcntl-локи, компрессия LZ4/Zstd, шифрование at rest ([Introduction](https://juicefs.com/docs/community/introduction/), [Architecture](https://juicefs.com/docs/community/architecture)). Ключевое следствие для прозрачности: «After writing a file to JuiceFS, you cannot find the original file directly in the object storage» — в бакете лежат пронумерованные блоки и `chunks`-каталог ([Architecture](https://juicefs.com/docs/community/architecture)).

**rclone mount** работает через VFS-слой; для нормальной работы с файлами нужен `--vfs-cache-mode writes|full`; без кэша — только последовательная запись; bucket-бэкенды не хранят пустые каталоги (кроме `--xxx-directory_markers`); внешние изменения видны после `--dir-cache-time` (5 мин) либо через polling ([rclone mount](https://rclone.org/commands/rclone_mount/)).

### 6. «Облачные диски» — как хранят данные

**Nextcloud.** По умолчанию — файлы в `nextcloud/data`, метаданные в БД. При primary object storage Nextcloud **требует эксклюзивного доступа к бакету**, и: «All metadata (filenames, directory structures, etc) is stored in Nextcloud and not in the object store. The metadata is only stored in the database and the object store only holds the file content by unique identifier». Прямое следствие: «unable to access the files from outside of Nextcloud» ([Nextcloud primary storage](https://docs.nextcloud.com/server/latest/admin_manual/configuration_files/primary_storage.html)).

**oCIS / OpenCloud.** Архитектура REVA/Go, Apache-2.0. Драйверы: `decomposedfs` (default, private storage: «which is not easily human readable»), `s3ng` (данные в S3, decomposedfs-метаданные на POSIX или в S3) и experimental `posix` (shared storage). Про PosixFS официально: данные и метаданные — на POSIX-ФС, метаданные в extended attributes; нужен inotify/GPFS-уведомления; «Versioning is not supported yet»; нет поддержки CephFS и NFSv3/SMB (NFSv4.2 работает); postprocessing (антивирус) не срабатывает для внешних правок; драйвер «experimental… should not be used in production» ([oCIS PosixFS](https://doc.owncloud.com/ocis/8.2/admin/deployment/storage/posixfs.html)). Протоколы: OCDAV/WebDAV, CS3, Graph API, OCS ([oCIS services](https://doc.owncloud.com/ocis/8.2/admin/deployment/services/services.html)). OpenCloud — форк oCIS (Go, Apache-2.0, 6 149 ⭐) ([GitHub API](https://api.github.com/repos/opencloud-eu/opencloud)).

**Seafile.** Внутри — модель, подобная Git: `Repo`, `Commit`, `FS` (`SeafDir`/`Seafile`), `Block`. «stores file metadata in object storage (or file system), while only stores small amount of metadata about the libraries in relational database». FS-объекты адресуются по содержимому (дедуп между версиями и снапшотами). Файл делится на блоки переменной длины алгоритмом Content Defined Chunking, «On average, a block's size is around 8MB». Commit/FS/blocks лежат в объектном хранилище (`commits`, `fs`, `blocks` бакеты) либо на ФС ([Seafile Data Model](https://manual.seafile.com/latest/develop/data_model/)). Virtual repo — представление на часть библиотеки (при шаринге папки или селективной синхронизации). Лицензии компонентов различаются: сервер core AGPLv3, Seahub Apache-2.0, desktop-клиент GPLv2, Android GPLv3, iOS Apache-2.0 ([Seafile Introduction](https://manual.seafile.com/latest/)). Зашифрованные библиотеки в документации описаны, но конкретику по тому, что они ломают, в рамках этой проверки я не подтвердил первоисточником.

**Pydio Cells.** Go-микросервисы, AGPLv3 ([README](https://github.com/pydio/cells)). Datasource бывает двух форматов: **Structured** («Best for accessing the files directly», человекочитаемое дерево) и **Flat** («Best for performances», непрозрачный формат) ([Datasource Format](https://docs.pydio.com/latest/admin-guide/connect-your-storage/datasource-format/structured-storage-best-for-accessing-the-files-directly/), [Flat](https://docs.pydio.com/latest/admin-guide/connect-your-storage/datasource-format/flat-storage-best-for-performances/)). Метаданные и ACL — в БД; наружу — REST/WebDAV, [Ent] SFTP; внешний SSO/LDAP помечены [Ent] ([Pydio internals](https://docs.pydio.com/latest/admin-guide/advanced/pydio-cells-internals/)).

### 7. Синхронизация

**Syncthing.** Протокол BEP v1: TLS 1.3 для шифрования и аутентификации; аутентификация — по TLS-сертификату, device ID = SHA-256 сертификата; «there is no required order or synchronization among BEP messages»; файлы нарезаются на блоки от 128 KiB до 16 MiB (степени двойки), SHA-256 на блок, размер зависит от размера файла; версии — version vectors; глобальная модель — «union of all files in the local models». Есть delta index exchange (index ID + max sequence) и folder type `RECEIVE_ENCRYPTED` для untrusted-устройств ([BEP v1](https://docs.syncthing.net/specs/bep-v1.html)). Механика сканирования: watcher + полный скан раз в час (случайный интервал 3/4…5/4 от заданного); rehash при изменении mtime/size/permissions; индекс — в БД `index-*` ([Understanding sync](https://docs.syncthing.net/users/syncing.html)). Конфликты: файл переименовывается в `<filename>.sync-conflict-<date>-<time>-<modifiedBy>.<ext>`. Файлы никогда не пишутся напрямую — сначала временный `.syncthing.*.tmp`, затем атомарная замена ([Understanding sync](https://docs.syncthing.net/users/syncing.html)). Версионирование — только для изменений, **полученных от других устройств**: «If Alice changes a file locally on her own computer Syncthing will not and can not archive the old version» ([File Versioning](https://docs.syncthing.net/users/versioning.html)).

**Resilio Sync.** Позиционируется как P2P-платформа; официально упоминается собственный «ZGT protocol» ([Resilio About](https://www.resilio.com/documentation/)). Официальная документация описывает поведение агентов, но **opисания wire-протокола нет** — «официального источника не найдено»; лицензия проприетарная.

**rsync / rsync-daemon.** Классический алгоритм дельта-передачи (rolling checksum + контрольные суммы) описан в официальном tech report ([rsync.samba.org/tech_report/](https://rsync.samba.org/tech_report/); страница в момент проверки не открылась — не подтверждено содержимым). Практически: синхронизация одноразовая/по расписанию, а не постоянная; сервер может работать как rsyncd ([rsync(1)](https://download.samba.org/pub/rsync/rsync.1)).

**rclone sync.** «Make source and dest identical, modifying destination only»; destination обновляется под источник, включая удаление файлов; «Do not use sync as a backup» — прямое предупреждение в документации, рекомендуется сначала `--dry-run` ([rclone sync](https://rclone.org/commands/rclone_sync/)).

**Unison.** Двусторонняя синхронизация с обнаружением конфликтов; «copies data so that already-synchronized data can be read and written while offline»; «user-level program that simply uses normal systems calls»; передача мелких правок в большие файлы оптимизирована «a compression protocol similar to rsync»; есть repeat-режим с FS-монитором ([README](https://github.com/bcpierce00/unison)). Детали архива-fingerprints в README не раскрыты.

**SMB как «шара-источник правды».** SMB2/3 — stateful-протокол удалённой ФС ([MS-SMB2](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-smb2/)); в отличие от sync-систем, содержимое шары — живые файлы на сервере, и правка видна клиенту сразу. Обратная сторона: нет версионирования и дедупликации «из коробки» (VSS/теневая копия — отдельная настройка через модуль `shadow_copy2` в Samba, [smb.conf(5)](https://www.samba.org/samba/docs/current/man-html/smb.conf.5.html)), нет офлайн-работы, конфликтный доступ регулируется блокировками/oplocks. Полный разбор SEMANTICS SMB в этой проверке не проводился.

## Прозрачность на диске (главный раздел)

Это — та ось, из которой вырастает большинство практических проблем: «я поменял файл на сервере руками/через другой инструмент — увидит ли это мой сервис и мой клиент?».

### A. Объектные хранилища

- **Что на носителе.** В базовом S3-бакете — объекты, а не файлы; ключи плоские. В self-hosted реализациях добавляется служебная структура: SeaweedFS — append-only volume-файлы с 16-байтным индексом в памяти ([README](https://github.com/seaweedfs/seaweedfs)); MinIO/RustFS — «separate meta file per drive for each file» (характеристика из README SeaweedFS) ([SeaweedFS](https://github.com/seaweedfs/seaweedfs)); Ceph — объекты в RADOS-пулах, без MDS ([Ceph RGW](https://docs.ceph.com/en/latest/radosgw/)).
- **Правка на диске.** Нет понятия «поправить файл»: изменение = новый PUT объекта (+ версия). Метаданные объекта (content-type, custom, теги, retention) живут в том же объекте/его версии; изменение только тегов/retention может требовать перезаписи метаданных (в SeaweedFS — «Changing only tags or retention rewrites that meta file on all of them») ([SeaweedFS](https://github.com/seaweedfs/seaweedfs)).
- **Дедуп/шифрование.** Ceph RGW умеет full object deduplication ([Ceph RGW](https://docs.ceph.com/en/latest/radosgw/)); AWS/Azure SSE и S3 SSE-C видны протокольно ([Nextcloud SSE-C](https://docs.nextcloud.com/server/latest/admin_manual/configuration_files/primary_storage.html)). Шифрование на диске ломает «читаемость посторонним инструментом»: RustFS прямо предупреждает, что объекты, зашифрованные MinIO, он не прочитает ([RustFS](https://github.com/rustfs/rustfs)).

### B. S3 как ФС

- **s3fs** сохраняет «native object format», поэтому на носителе — обычные объекты, доступные AWS CLI. Это максимум прозрачности среди FUSE-решений ([s3fs README](https://github.com/s3fs-fuse/s3fs-fuse)).
- **JuiceFS** — противоположный полюс: «you cannot find the original file directly in the object storage»; прозрачность нулевая, метаданные — во внешней БД, потеря БД = потеря дерева ([Architecture](https://juicefs.com/docs/community/architecture)).
- **rclone mount** — данные в бакете нативны, но дерево каталогов и «последнее виденное состояние» кэшируются в памяти/на диске; чужие изменения видны только по истечении TTL кэша ([rclone mount](https://rclone.org/commands/rclone_mount/)).

### C. Облачные диски и sync

- **Nextcloud (default FS):** файлы «как есть», но истина — в БД-индексе. Правка мимо Nextcloud либо подхватывается пересканированием, либо (для external storage) её можно вовсе запретить, включив «Check for changes: Never», «preventing unauthorized additions by external storage admins» ([Nextcloud SSE](https://docs.nextcloud.com/server/latest/admin_manual/configuration_files/encryption_configuration.html)).
- **Nextcloud (object storage):** данные лежат в бакете «by unique identifier», метаданные только в БД. Ручная правка контента в бакете не даст ничего осмысленного ([Nextcloud primary storage](https://docs.nextcloud.com/server/latest/admin_manual/configuration_files/primary_storage.html)).
- **oCIS:** private `decomposedfs` — «not easily human readable»; в shared/PosixFS система должна быть уведомлена об изменениях (inotify/GPFS) и сама проставляет метаданные в xattr; versioning не поддерживается; антивирус не сработает для внешних правок ([oCIS PosixFS](https://doc.owncloud.com/ocis/8.2/admin/deployment/storage/posixfs.html)).
- **Seafile:** файлов «как есть» нет вообще — только объекты Commit/FS/Block, адресуемые по содержимому, с CDC-чанками ~8 МБ. Ручная правка «файла на диске» невозможна по определению ([Seafile Data Model](https://manual.seafile.com/latest/develop/data_model/)).
- **Pydio Cells:** наличие прозрачности зависит от формата datasource — Structured даёт читаемое дерево, Flat — перформанс без читаемости ([Pydio Datasource Format](https://docs.pydio.com/latest/admin-guide/connect-your-storage/datasource-format/structured-storage-best-for-accessing-the-files-directly/)).
- **Syncthing:** файлы «как есть», но есть служебная index-БД и `.stversions`; правки, сделанные мимо Syncthing, обнаруживаются сканером (watcher + часовой полный скан); они попадут в синхронизацию, но старая версия не заархивируется локально ([Understanding sync](https://docs.syncthing.net/users/syncing.html), [File Versioning](https://docs.syncthing.net/users/versioning.html)).
- **SMB/«шара»:** максимальная прозрачность — данные и есть файлы на сервере; но нет версий/дедупа/офлайна (нужны внешние механизмы).

**Практическое правило:** чем прозрачнее хранилище на диске (голые файлы), тем меньше оно даёт (версии/дедуп/atomные транзакции/E2EE). Чем богаче функции, тем сильнее данные зависят от БД/индекса или от клиента, шифрующего контент.

## Разграничение доступа

### 1. Bearer-токены объектных хранилищ

- **S3 pre-signed URL** — «bearer tokens» с правами подписавшего; ограничиваются `s3:signatureAge` и сетевыми условиями (`aws:SourceIp`, `aws:SourceVpc`) ([AWS](https://docs.aws.amazon.com/AmazonS3/latest/userguide/using-presigned-url.html)).
- **Azure SAS** — user delegation/service/account; ad hoc или stored access policy (до 5 на контейнер); генерация SAS не аудируется ([Azure SAS](https://learn.microsoft.com/en-us/azure/storage/common/storage-sas-overview)).
- **GCS signed URL V4** ([GCS](https://cloud.google.com/storage/docs/access-control/signed-urls)); **Swift temp URL** (HMAC на ключе аккаунта/контейнера) ([Swift API](https://docs.openstack.org/api-ref/object-store/)).
- **Retention/object lock** — отдельный механизм защиты от изменений/удаления: S3 Object Lock (governance/compliance + legal hold) ([AWS](https://docs.aws.amazon.com/AmazonS3/latest/userguide/object-lock.html)); Azure immutability ([Azure](https://learn.microsoft.com/en-us/azure/storage/blobs/immutable-storage-overview)); GCS Bucket Lock/object holds ([GCS](https://cloud.google.com/storage/docs/bucket-lock)); GCS Object Retention Lock ([GCS](https://cloud.google.com/storage/docs/object-lock)).

### 2. Облачные диски

- **Share-ссылки и группы/роли** — типичный уровень «облачного диска» (публичные/внутренние ссылки, пароль, срок — реализуются приложением, а не протоколом хранения). Подтверждающие страницы для конкретных продуктов в этой проверке не пересобирались — см. раздел про неподтверждённое.
- **OIDC/SAML/LDAP.** Нативные/подключаемые IdP: oCIS/OpenCloud (встроенный IdP + внешние), Pydio (SSO/LDAP помечены [Ent]) ([oCIS services](https://doc.owncloud.com/ocis/8.2/admin/deployment/services/services.html), [Pydio SSO](https://docs.pydio.com/latest/admin-guide/connect-your-users/single-sign-on-features/)).

### 3. Что именно ломает E2EE

По материалам Nextcloud (самый документированный в собранных источниках):

- **SSE vs E2EE.** SSE делает сервер («Who Can Decrypt? Admins & users»), E2EE делает клиент («Users only»). SSE не защищает от скомпрометированного сервера/админа — для этого нужен E2EE ([Nextcloud SSE](https://docs.nextcloud.com/server/latest/admin_manual/configuration_files/encryption_configuration.html)).
- **Метаданные не шифруются (SSE).** Явное предупреждение: «SSE does **not** encrypt filenames or folder structures, only file contents»; также не шифруются thumbnails, previews, full-text search index ([Nextcloud SSE](https://docs.nextcloud.com/server/latest/admin_manual/configuration_files/encryption_configuration.html)).
- **E2EE ломает веб-функции.** «E2EE files can currently only be read (using the viewer app) and downloaded from the Nextcloud Web UI»; «When the web interface is used for end-to-end encryption then chunked uploads have to be disabled!»; «Since all encryption is handled by the clients… all client versions in-use be kept relatively aligned» — то есть серверный поиск/превью/совместная работа и «тонкий» веб-клиент страдают ([Nextcloud E2EE](https://github.com/nextcloud/end_to_end_encryption)).
- **Админ не спасёт.** «The mnemonic is *not* recoverable by a server administrator. If you lose your mnemonic you *will* lose access to your encrypted data»; E2EE нельзя включить на root-папку синхронизации и на папку с уже существующим контентом ([Nextcloud E2EE](https://github.com/nextcloud/end_to_end_encryption)).
- **E2EE vs WebDAV/FS-доступ.** Раз файл шифрует клиент, серверный WebDAV/FS-доступ к контенту лишён смысла — это фундаментальный конфликт threat model, а не баг (формулируется в README E2EE: «Some functions will never be supported because they are inherently incompatible with the threat model of E2EE») ([Nextcloud E2EE](https://github.com/nextcloud/end_to_end_encryption)).

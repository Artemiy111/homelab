# Runbook: нода тормозит — большой load и iowait

Когда открывать: сервисы отвечают медленно, поды долго висят в
`Pending`/`ContainerCreating`, `top` показывает `wa` выше 20 %, а load average
заметно больше числа CPU.

Два правила, которые экономят время:

- Смотреть надо **в момент проблемы**. Если сейчас тихо, `avg300` в PSI покажет,
  что буря была минуты назад, а `avg10` будет уже нулевым.
- Не искать виноватый процесс в `top`: он показывает мгновенный срез и не
  отвечает, кто создал очередь на диске.

## Порядок действий

### 1. Это CPU или ожидание

```sh
uptime
mpstat 1 3
```

`uptime` даёт три load average: за 1, 5 и 15 минут. Сравнивать с числом CPU
(`nproc` на этом стенде — 16). `mpstat` даёт проценты по всем ядрам, читать три:
`%usr`, `%iowait`, `%idle`.

- load больше 16, `%iowait` больше 20 — ждём диск, идти к шагу 3.
- load больше 16, `%iowait` меньше 5, `%usr` больше 80 — не хватает CPU, искать
  процессы в `top` по `%CPU`.
- load большой, а `%iowait` маленький — так бывает: `iowait` растёт только когда
  ядро простаивает, а если остальные ядра работают, ожидание в нём не видно.
  Точный ответ даёт шаг 2.

### 2. Задачи реально стоят?

```sh
cat /proc/pressure/io
cat /proc/pressure/memory
```

PSI — это **проценты времени**, а не байты. `some avg10=4.68` читается как
«4,68 % времени хотя бы одна задача ждала I/O».

- `some` — ждала хотя бы одна задача;
- `full` — ждали все, то есть работа встала целиком;
- `avg10`/`avg60`/`avg300` — окна 10 секунд, 1 минута, 5 минут;
- `total` — микросекунды с загрузки, смотреть не нужно.

Критерий: `io full avg10` больше 5 % — I/O реально тормозит работу. Если сейчас
тихо, смотреть `avg300`: он держит след последних пяти минут.

### 3. Насколько занят диск

```sh
iostat -xmy 1 3 nvme0n1
```

Три ключа: `-x` — подробные поля, `-m` — мегабайты вместо килобайт, `-y` — не
показывать среднее с момента загрузки (иначе первый блок будет огромным и не про
сейчас). `nvme0n1` в конце — только физический диск. В выводе 20 столбцов,
читать нужно шесть:

| Столбец | Что значит |
|---|---|
| `r/s`, `w/s` | операций чтения и записи в секунду |
| `rMB/s`, `wMB/s` | МиБ/с |
| `r_await`, `w_await` | миллисекунд на одну операцию, включая очередь |
| `aqu-sz` | сколько запросов в среднем стоит в очереди |
| `%util` | процент времени, когда диск был занят |

- `%util` 100, `aqu-sz` больше 10, `w_await` больше 50 мс при скромных MB/s —
  диск не справляется задержкой и очередью, а не полосой. Для NVMe это
  аномалия, он умеет на порядки больше.
- `%util` меньше 80 и `w_await` меньше 5 мс — диск не при чём, смотреть шаг 5.

`sd*` в этом выводе не нужны: это не диски, а 59 томов Longhorn, проброшенных
через iSCSI. Их `%util` — занятость очереди тома, а не железа. Физический диск
здесь один: `nvme0n1`, он же `dm-0` через LVM.

### 4. Кто создаёт I/O

```sh
sudo iotop -oPa
```

`-o` — только активные, `-P` — по процессам, `-a` — накопленные байты за время
наблюдения. Читать два столбца: `IO>` (процент времени, который процесс провёл
в ожидании I/O) и `DISK WRITE`/`DISK READ`. Сортировка по `IO>` — стрелками
влево-вправо.

Для подов имя процесса не помогает, там нужен UID из пути cgroup
(`/sys/fs/cgroup/kubepods/**/pod<uid>`) и `io.stat` в том же каталоге:

```sh
kubectl get pods -A -o custom-columns=NS:.metadata.namespace,NAME:.metadata.name,UID:.metadata.uid
```

### 5. Память, если `memory full` больше нуля или растёт `Swap used`

```sh
free -m
cat /sys/block/zram0/mm_stat
```

`free -m` читается сразу: `used`, `available`, `Swap used`. Ориентир — если
`available` меньше 2 GiB, а `Swap used` растёт, память кончилась.

На этом стенде swap — это zram (сжатие в RAM), поэтому рост `Swap used` и
`%si` в `top` означают работу CPU на сжатие, а не запись на диск.

Кто занимает память — в `top`, отсортировать по `%MEM` клавишей `M`.

### 6. Это уже инцидент?

```sh
kubectl get pods -n kube-system
kubectl get events -A --field-selector reason=LeaderElection --sort-by=.lastTimestamp | tail
```

Ожидаемо: лидер-лизы стабильны, рестартов нет. Если `kube-scheduler` и
`kube-controller-manager` теряют lease каждые 30–60 секунд — API-сервер и etcd
не успевают, это инцидент, а не «медленно».

## Единицы измерения

| Где | Поле | Единица |
|---|---|---|
| `iostat` | `kB/s` | КиБ/с (в `-m` — МиБ/с) |
| `iostat` | `await` | миллисекунды на операцию |
| `iostat` | `aqu-sz` | запросов в очереди, среднее |
| `iostat` | `%util` | процент времени |
| `free`, `top` | память | МиБ |
| PSI | `avg10`, `avg60`, `avg300` | процент времени |
| PSI | `total` | микросекунды, не смотреть |

## Ориентиры нормы

Не SLO, а граница «можно не разбираться»:

- load average меньше числа CPU (16);
- `%iowait` меньше 10 %, `io full avg10` меньше 5 %, `memory full avg10` — доли процента;
- `nvme0n1`: `%util` меньше 80, `w_await` меньше 5 мс, `aqu-sz` меньше 5;
- `available` больше 4 GiB, `Swap used` не растёт;
- лидер-лизы `kube-system` не меняются минутами.

## Типовые причины на этом стенде

| Что видно | Причина | Что делать |
|---|---|---|
| Рваные всплески `wa`, в `iotop` — `node`, `tar`, `unzstd`, `trivy` | Renovate, сканы trivy и джобы Forgejo Actions пришли одновременно; CI распаковывает `cache.tzst` | Развести расписание и параллелизм батча |
| Все `sd*` и `nvme0n1` по 100 %, `w_await` сотни мс | 59 томов Longhorn через iSCSI поверх корневой ФС: одна запись = несколько I/O на том же NVMe | Вынести каталог Longhorn на отдельный носитель, ограничить `storageMaximum` |
| `Swap used` растёт, `available` меньше 2 GiB | 28 GiB на 158 подов, постоянный reclaim и zram | Сверить requests/limits с фактом, срезать лишнее или добавить RAM |
| NVMe 100 % при занятости ФС больше 85 % | dirty throttling, риск `DiskPressure` и эвикции (инциденты 0005, 0006) | Чистить образы, журнал, брошенные тома |

## Если сервис надо вернуть прямо сейчас

1. Остановить батч (job Renovate, скан trivy, CI-джобу) — это самый быстрый
   способ снять очередь с диска.
2. Не рестартовать поды «на удачу»: при заполненной очереди рестарт добавляет
   I/O и тормозит остальных.
3. Проверить, что нет эвикции: `kubectl describe node homelab | grep -A5 Conditions`.

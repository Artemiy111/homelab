# Кластер `yc` (Terraform)

Три узла под кластер в Yandex Cloud, внешний сетевой балансировщик на kube-api и
публичная подзона кластера в Cloud DNS. Развёртывание самого кластера — не здесь:
модуль доводит площадку до «машины с публичным адресом, SSH и открытым
6443 за балансировщиком».

## Что создаётся

| Ресурс | Что это |
| --- | --- |
| `yandex_vpc_network.cluster` | сеть кластера `k8s-vm` |
| `yandex_vpc_subnet.node` | по одной подсети на зону из `local.subnets`: `k8s-vm-ru-central1-{d,e}` |
| `yandex_vpc_security_group.node` | SSH и kube-api из разрешённых сетей, проверки доступности балансировщика, весь трафик между узлами, любой исходящий |
| `yandex_compute_instance.node` | по одной ВМ на узел из `local.nodes` (`d1`, `d2`, `e1`): 2 ядра, 2 ГБ, 10 ГБ `network-ssd`, публичный адрес через `nat`, доступ по SSH через OS Login |
| `yandex_vpc_address.api` | статический публичный адрес балансировщика в зоне `ru-central1-e` |
| `yandex_lb_target_group.nodes` | целевая группа из внутренних адресов узлов |
| `yandex_lb_network_load_balancer.api` | внешний балансировщик `nlb-k8s-vm`, TCP `6443`, проверка доступности TCP `6443` |
| `yandex_dns_zone.cluster` | публичная зона `<dns_zone_name>.<parent_domain>` |
| `yandex_dns_recordset.api` | `api.<зона>` A → статический адрес балансировщика |

Ничего не импортируется: сеть, подсети, узлы, балансировщик и его адрес
создаются с нуля, поэтому `terraform destroy` убирает за собой всё.

## Адресация

Подсети узлов и внутренние диапазоны кластера — разные вещи, и пересекаться они
не должны.

| Диапазон | Что это | Где живёт |
| --- | --- | --- |
| `10.133.0.0/24`, `10.134.0.0/24` | подсети узлов в зонах `d`, `e` | VPC, видны облаку |
| `10.244.0.0/16` | `podCIDR` | только таблицы маршрутизации узлов (calico) |
| `10.96.0.0/12` | `serviceCIDR` | только правила kube-proxy на узлах |

`podCIDR` и `serviceCIDR` — не подсети VPC: в облаке таких сетей нет и маршрутов
к ним нет. Они существуют внутри узлов, поэтому жёсткое требование одно — не
пересекаться с адресами VPC, иначе на узле пакет на «адрес пода», совпавший с
адресом в облаке, уйдёт не туда. Значения взяты те же, что в `casa`
(`infra/casa/host/etc/k0s/k0s.yaml`): у стендов должна быть одна картина
адресации.

Сеть своя, поэтому подсети можно было взять любые; выбраны следующие за уже
занятыми в каталоге: сеть `default` держит `10.128.0.0/24`–`10.131.0.0/24`, новая
сеть — `10.133.0.0/24` и `10.134.0.0/24`. Так ни одна пара сетей каталога не
пересекается, и peering между ними возможен без перенумерации; заодно вся
адресация каталога суммируется в `10.128.0.0/20`. По `/24` на зону: 254 адреса,
из них Яндекс держит `.1` (шлюз) и `.2` (DNS); подам адреса из подсети не
выдаются — их даёт calico.

## Почему две зоны, а не три

Зоны `a`, `b`, `c` и `k` в этом облаке недоступны для новых ВМ:

| Зона | Ответ при создании ВМ |
| --- | --- |
| `ru-central1-a` | `ResourceExhausted: Resource allocation is restricted` на любой конфигурации |
| `ru-central1-b` | `Zone ru-central1-b is not available` |
| `ru-central1-c` | `DOWN` в списке зон |
| `ru-central1-k` | `Operation is not permitted in the folder` |
| `ru-central1-d`, `ru-central1-e` | работают |

Проверено перебором: `standard-v1/v2/v3`, 5/20/50/100% vCPU, 1–2 ГБ RAM. Поэтому
зон две, а узлы распределены 2+1: `d1` и `d2` в `d`, `e1` в `e`. Квота `d` под это
поднята ровно впритык (4 ядра, 20 ГБ SSD).

Когда откроется `a`, узел можно добавить в `local.nodes` одной строкой. Пока
раскладка 2+1, отказ зоны `d` уносит два узла из трёх — кворум etcd теряется;
отказ одного любого узла кластер переживает.

## Как работает DNS-зона

Домен стенда `biplane.casa` зарегистрирован в **Spaceship**, и NS домена
указывают на его серверы имён (`launch1.spaceship.net`, `launch2.spaceship.net`) —
публично авторитетен именно Spaceship. Technitium держит ту же зону как
split-horizon: его ответы (wildcard `*.<домен>` на домашний узел) видит только
тот, кто пользуется Technitium как резолвером — домашняя сеть и tailnet.
Снаружи имена стенда не резолвятся вовсе: `forgejo.<домен>` и `foo.<домен>`
отдают `NXDOMAIN`. Тот же факт виден в cert-manager: wildcard-сертификат
`*.<домен>` выпускается через DNS-01 с `provider: spaceship`, то есть
ACME-челлендж ложится в зону Spaceship.

Поэтому зона `yc.clusters.<домен>.` в Cloud DNS сама по себе ничего не включает:
имя начнёт резолвиться, только когда в **авторитетной** зоне появится
делегирование. Делегирование — это разрез дерева имён: родительская зона
объявляет NS-записями, что за имена вида `*.yc.clusters.<домен>` отвечает уже не
она, а серверы имён Cloud DNS. После этого:

- родительская зона перестаёт отвечать за это поддерево, и запрос уходит прямо в
  Yandex DNS;
- промежуточная зона `clusters.<домен>` не нужна ни в Spaceship, ни в Cloud DNS:
  DNS не требует, чтобы у каждого уровня дерева была своя зона;
- имена поддерева резолвятся из интернета одинаково у всех, независимо от
  домашнего стенда — ради этого делегирование и делается.

Зачем имя вообще: адрес балансировщика и так статический, но в TLS-сертификат
apiserver и в `kubeconfig` попадает **имя**, а не адрес. Меняется балансировщик
или адрес — правится одна A-запись, а не все kubeconfig'и и не перевыпуск
сертификата. Дальше на это же поддерево ложатся имена ingress'а и wildcard-
сертификат Let's Encrypt (DNS-01), когда они появятся.

Следствие для сертификатов: после делегирования `_acme-challenge.yc.clusters.<домен>`
спрашивают у Yandex DNS, а не у Spaceship. Значит выпуск сертификатов для имён
внутри `yc.clusters` через существующий вебхук cert-manager (`provider: spaceship`)
не сработает — понадобится солвер, умеющий писать в Cloud DNS. kube-api это не
касается: сертификат apiserver выпускает сам кластер.

Порядок применения и наблюдаемое состояние: пока делегирование есть, а зоны в
Cloud DNS ещё нет, резолверы получают от Yandex `REFUSED` и отдают `SERVFAIL` —
это lame delegation, а не ошибка в записях. Имя начинает резолвиться только после
`apply` этого модуля.

Чего зона не даёт: внутренний DNS кластера (`*.svc.cluster.local`) — это CoreDNS
внутри кластера, к Cloud DNS отношения не имеет.

## Квоты, которые определяют конфигурацию

Значения сняты с `yc quota-manager quota-limit list --service compute --resource-type resource-manager.cloud`
на момент написания. Перед `apply` их стоит перечитать: часть из них — стоп-фактор.

| Квота | Значение | Следствие |
| --- | --- | --- |
| `vpc.networks.count` | 3/3 | сеть `k8s-vm` создана; новую сеть без поднятия квоты не завести |
| `vpc.subnets.count` | 6/12 | две подсети узлов помещаются |
| `compute.instanceCores.count.ru-central1-d` | 2/4 | под `d1` и `d2` нужно ровно 4, запаса нет |
| `compute.instanceCores.count.ru-central1-e` | 2/2 | `e1` занимает зону целиком |
| `compute.ssdDisks.size.ru-central1-d` | 10/20 ГиБ | два диска по 10 гибают квоту ровно в ноль |
| `compute.ssdDisks.size.ru-central1-e` | 10/10 ГиБ | один диск занимает зону целиком |
| `vpc.externalStaticAddresses.count` | 2/2 | занято адресом балансировщика и старым `153.51.118.237`, который пора освободить |
| `compute.instances.count` | 2/12 | не ограничивает |
| `dns.zones.count` | 4/100 | не ограничивает |

Узлы получают **динамический** публичный адрес: он сохраняется при перезагрузке,
но освобождается при остановке ВМ, и после запуска адрес будет другим. Если
адреса узлов нужны фиксированными, нужна квота `vpc.externalStaticAddresses.count`
и `nat_ip_address` вместо `nat` в `instances.tf`.

### Замена узлов при квоте «впритык»

Terraform создаёт новые узлы параллельно с удалением старых. Если квота зоны
занята ровно, на эти секунды потребуется вдвое больше ядер и дисков, и `apply`
упадёт с `ResourceExhausted` — так и случилось при переименовании `d`/`e` в
`d1`/`d2`/`e1`.

Правильно — два apply: сначала убрать старые ключи из `local.nodes` (останется
только удаление), затем добавить новые. Неудачное создание оставляет ресурс в
state с пометкой `tainted`; следующий `apply` его пересоздаст, а если объект в
облаке всё-таки есть — `terraform untaint`.

## Подготовка

1. **Сервисный аккаунт `terraform`.** Примитивную роль `editor` давать не надо:
   она покрывает весь каталог, включая сервисы, которых модуль не касается.
   Минимальный набор — шесть ролей на каталог:

   | Роль | Зачем |
   | --- | --- |
   | `vpc.privateAdmin` | сеть и подсети: создать, удалить |
   | `vpc.publicAdmin` | публичные адреса: `nat = true` у узлов и статический адрес балансировщика. Без неё создание ВМ с публичным IP падает |
   | `vpc.securityGroups.admin` | группа безопасности: создать, править правила, назначить интерфейсам |
   | `compute.editor` | ВМ и загрузочные диски (включает `compute.images.user`, отдельная роль для образов не нужна) |
   | `load-balancer.editor` | балансировщик и целевая группа |
   | `dns.editor` | публичная зона и A-запись |

   `vpc.privateAdmin` + `vpc.publicAdmin` + `vpc.securityGroups.admin` — это ровно
   то, из чего состоит `vpc.admin`, поэтому вместо трёх ролей можно дать одну
   `vpc.admin`: права те же.

   ```sh macOS
   yc iam service-account create --name terraform
   sa_id="$(yc iam service-account get terraform --format json | jq -r .id)"
   folder_id="$(yc config get folder-id)"

   for role in vpc.privateAdmin vpc.publicAdmin vpc.securityGroups.admin \
               compute.editor load-balancer.editor dns.editor; do
     yc resource-manager folder add-access-binding "$folder_id" \
       --role "$role" --subject "serviceAccount:$sa_id"
   done

   mkdir -p ~/.config/yc
   yc iam key create --service-account-name terraform \
     --output ~/.config/yc/terraform-key.json
   chmod 600 ~/.config/yc/terraform-key.json
   ```

   Файл ключа — приватный, в репозиторий и в state не попадает: провайдеру
   передаётся путь. Проверить выданное: `yc resource-manager folder
   list-access-bindings "$folder_id"`.
2. **Включить OS Login в организации и выдать роли.** Без этого внутрь узлов не
   попасть: ключи в метаданные больше не кладутся. Проверить состояние —
   `yc organization-manager oslogin get-settings --organization-id <org-id>`.
   Себе (или тому, кто будет ходить по SSH) нужны `compute.osAdminLogin` на
   каталог, `resource-manager.auditor` и выше, и `compute.operator` для входа
   через `yc compute ssh`. Субъект для федеративного пользователя выглядит как
   `federatedUser:<id>`, для аккаунта на Яндексе — `userAccount:<id>`:

   ```sh macOS
   yc resource-manager folder add-access-binding "$(yc config get folder-id)" \
     --role compute.osAdminLogin --subject "federatedUser:<id>"
   ```

3. **Освободить статический адрес от прежнего балансировщика.** Модуль создаёт
   свой адрес, поэтому старый надо удалить: он занимает слот квоты и
   тарифицируется, даже когда не привязан. Список адресов и их привязки —
   `yc vpc address list`, детали — `yc vpc address get <id>`, история — `yc vpc
   address list-operations <id>`. В консоли то же самое лежит в VPC → IP-адреса:
   `https://console.yandex.cloud/folders/<folder-id>/vpc/addresses`.

## Открытый доступ

`ssh_allowed_cidrs` и `api_allowed_cidrs` (в `locals` модуля) по умолчанию —
`0.0.0.0/0`: источник подключения заранее неизвестен (прокси, смена сети), а
перечислять адреса вручную неудобно. Что это значит на практике:

- **SSH защищён OS Login, а не ключом в метаданных.** Пароля на узлах нет,
  вход — по SSH-ключу из профиля OS Login или по короткоживущему сертификату,
  который выдаёт `yc compute ssh`. Ключи в метаданные не попадают вовсе.
  Сузить доступ по сети — поменять `ssh_allowed_cidrs`.
- **kube-api защищён клиентским сертификатом** и RBAC. Порт 6443 открыт всем,
  но без сертификата apiserver отвечает только на анонимные запросы
  `/healthz`-класса. Сузить — `api_allowed_cidrs`.
- Правило от проверок доступности балансировщика (`loadbalancer_healthchecks`)
  открыто на `6443` независимо от этих переменных: без него цели в целевой
  группе не станут `HEALTHY`.

## Запуск

Все команды — из каталога модуля, `infra/yc/terraform/cluster`.

```sh macOS
export TF_CLI_CONFIG_FILE="$PWD/../.terraformrc"
export YC_SERVICE_ACCOUNT_KEY_FILE="$HOME/.config/yc/terraform-key.json"
export YC_CLOUD_ID="$(yc config get cloud-id)"
export YC_FOLDER_ID="$(yc config get folder-id)"

terraform init
terraform plan
```

`$PWD/../.terraformrc` — потому что конфиг провайдеров лежит в
`infra/yc/terraform/`, на уровень выше модуля. Terraform свой конфиг в каталоге не
ищет: читается только `~/.terraformrc` или путь из `TF_CLI_CONFIG_FILE`. Без
зеркала `init` падает с `Invalid provider registry host` — реестр не отдаёт
провайдера из России.

Провайдер берёт параметры из окружения, а `provider`-блок оставлен пустым:
аргументы блока попадают в сохранённый план (`terraform plan -out`), и токен в
файле плана — лишний риск. Credentials в state не сохраняются.

Вместо сервисного аккаунта для разового плана годится IAM-токен из CLI — он живёт
около 12 часов. Один способ за раз:

```sh macOS
unset YC_SERVICE_ACCOUNT_KEY_FILE
export YC_TOKEN="$(yc iam create-token)"
```

`YC_TOKEN` нужен именно провайдеру Terraform: авторизация `yc` CLI и провайдера —
разные вещи, профиль CLI он не читает. Без него план падает на
`one of 'token' or 'service_account_key_file' should be specified` ещё до чтения
облака.

Первый `apply` создаёт всё с нуля, включая статический адрес балансировщика:
адрес получает новый IP, старый (если он был зарезервирован) остаётся висеть до
удаления руками.

Реестр Terraform не отдаёт провайдера из России и отвечает `does not offer a
Terraform provider registry`; отсюда и зеркало в `TF_CLI_CONFIG_FILE`. Если
включён VPN и реестр доступен, переменную можно не выставлять. Каталог
`.terraform` в git не входит, поэтому после чистого клона (или `git clean -xdf`)
`init` обязателен.

## Значения

Все значения — в одном блоке `locals` в `main.tf`: имя кластера и
балансировщика, регион и порт, домен и имя подзоны, разрешённые сети. Топология
разделена надвое: `subnets` — зона → CIDR подсети, `nodes` — имя → подсеть и
адрес в ней. Так две ВМ могут жить в одной подсети, и добавление узла — одна
строка.

Внутренние адреса закреплены явно (`ip_address`): `d1` — `10.133.0.11`, `d2` —
`10.133.0.12`, `e1` — `10.134.0.11`. Поэтому внутренние адреса не меняются при
пересоздании ВМ, а в подсети остаются предсказуемыми. `.1` в каждой подсети —
шлюз, `.2` — DNS Яндекса, их занимать нельзя. Публичные адреса при этом
динамические (`nat = true`), кроме статического адреса балансировщика.

Переменных у модуля нет намеренно: вызывающих модулей нет, стенд один, а значения
публичные и коммитятся — значит `variable` была бы константой с лишним слоем
indirection. Менять их — правка `locals` через PR, `tfvars` не используется.

Железо узлов — константы в `instances.tf`: 2 ядра, 2 ГБ, 10 ГБ `network-ssd`,
платформа `standard-v3` (Intel Ice Lake), образ `ubuntu-2404-lts-oslogin`
(агент OS Login предустановлен).

## Доступ по SSH (OS Login)

Ключи и пользователи не задаются в конфигурации вовсе: `metadata` узлов
содержит `enable-oslogin = "true"`, а агент на узле берёт данные из профиля
OS Login пользователя в организации. Что из этого следует:

- **Логин — это имя профиля OS Login**, а не `ops`. Профиль создаётся
  автоматически при включении OS Login в организации; посмотреть свой —
  `yc organization-manager oslogin profile list --organization-id <org-id>`.
- **Права внутри узла — из IAM.** `compute.osLogin` даёт вход, `compute.osAdminLogin`
  — вход и sudo. Отзыв роли отзывает доступ сразу на всех ВМ, где включён
  OS Login, без пересоздания машин и правки `authorized_keys`.
- **Ключи — в профиле, а не в метаданных.** Публичный ключ добавляется в
  профиль (консоль → профиль пользователя, или
  `yc organization-manager oslogin user-ssh-key add`), и метаданные ВМ его не
  содержат. Альтернатива ключу — короткоживущий сертификат:
  `yc compute ssh --name yc-a`.
- **Ролей нужно три:** `compute.osLogin` (или `compute.osAdminLogin`),
  `resource-manager.auditor` и выше на каталог, и `compute.operator` для входа
  через `yc compute ssh`.
- **Запасного входа нет.** Cloud-init с пользователем и ключом удалён: если
  OS Login в организации выключат, внутрь узла не попасть никак —
  `serial-port-enable = "0"` тоже закрыт.
- **Ansible.** Для автоматизации понадобится профиль OS Login **сервисного
  аккаунта** — для сервисных аккаунтов профили автоматически не создаются,
  их заводят вручную (`organization-manager.osLogins.admin`).

## После apply

1. **Делегировать подзону.** `terraform output dns_delegation_ns` даёт
   `ns1.yandexcloud.net.` и `ns2.yandexcloud.net.`; они вносятся как NS-записи
   для имени `yc.clusters` в **Spaceship** — там авторитетная зона домена.
   Пока записи нет, зона в Cloud DNS существует, но её никто не спрашивает:
   снаружи `api.yc.clusters.<домен>` не резолвится вообще.
2. **Прописать адрес kube-api в kubespray.** `terraform output api_fqdn` идёт в
   `supplementary_addresses_in_ssl_keys`: по нему apiserver включает имя в SAN
   сертификата, и `kubectl` по `https://api.yc.clusters.<домен>:6443` проходит
   проверку TLS. Без этого сертификат валиден только для внутренних адресов.
3. **Поставить кластер kubespray:** три control plane, каждый из них одновременно и
   worker (`d1`, `d2`, `e1` во всех трёх группах инвентаря). Инвентарь
   генерируется из outputs, инструкция — `infra/yc/ansible/README.md`.
   После установки цели в целевой группе балансировщика переходят в `HEALTHY`.

Домашняя сеть и tailnet резолвят домен через Technitium, а не через Spaceship,
поэтому там подзона по умолчанию останется под wildcard `*.<домен>` — то есть
на домашний узел. Если нужно, чтобы домашние клиенты видели `yc.clusters` так же,
как интернет, те же NS-записи кладутся в `delegations` модуля
`infra/casa/terraform/technitium`; для самого кластера это не требуется.

## Проверка

```sh macOS
terraform output -json nodes
yc compute instance list
yc load-balancer network-load-balancer get nlb-k8s-vm
yc vpc address list
yc dns zone list
dig +short api.yc.clusters.<домен>
nc -vz api.yc.clusters.<домен> 6443
ssh <логин OS Login>@<публичный адрес узла>
yc compute ssh --name yc-a
```

Пока кластер не поставлен, цели в целевой группе остаются `UNHEALTHY`, а
балансировщик — `ACTIVE`: обработчик есть, трафик передавать некому.

## Чего модуль не делает

- **Кластер.** Установка kubespray, инвентарь, конфигурация и join узлов — вне Terraform.
- **Профили и ключи OS Login.** Это уровень организации (Identity Hub), а не
  каталога: `yandex_organizationmanager_os_login_settings` и
  `yandex_organizationmanager_user_ssh_key` требуют прав на организацию, которых
  у сервисного аккаунта модуля нет и быть не должно. При необходимости — отдельный
  модуль с отдельным аккаунтом и org-ролью.
- **Фиксированные адреса узлов.** Упирается в квоту статических адресов.
- **Ingress.** Наружу открыт только kube-api. Пользовательский трафик пойдёт
  через отдельный балансировщик или NodePort, и это осознанное решение, а не
  забытый порт.
- **Проверка в CI.** `terraform fmt` и `tflint` каталог видят, а
  `scripts/terraform-validate.sh` — нет: на раннере нет интернета, и архива
  провайдера `yandex-cloud/yandex` в зеркале RustFS пока нет. Пока не добавлена
  строка в `apps/casa/rustfs/manifests/artifacts.tsv`, `validate` для этого
  модуля гоняется локально.

# external-secrets (`yc`)

External Secrets Operator: переносит секреты из Yandex Lockbox в Kubernetes,
чтобы пароль базы Nexus не лежал ни в репозитории, ни в state Terraform.

## Зачем он здесь

Nexus не умеет стартовать без пароля PostgreSQL. Пароль создаёт Connection
Manager и хранит Lockbox; альтернатива — руками копировать его в Secret и
повторять это при каждой ротации. ESO убирает ручной шаг: `ExternalSecret`
ссылается на секрет Lockbox, оператор сам создаёт и обновляет Kubernetes Secret.

Vault в `casa` для этого не подходит: он живёт в другом кластере и в другой сети,
и доступ к нему из `yc` не настроен. Lockbox — сервис той же облачной площадки,
что и база.

## Как устроено

Оператор — три пода: контроллер, webhook для валидации CR и cert-controller для
сертификатов webhook. Аутентификация в Lockbox — только авторизованным ключом
сервисного аккаунта: ключ лежит в Secret `yc-auth` в namespace оператора и в
репозиторий не попадает.

Сервисный аккаунт `nexus-lockbox` и роль `lockbox.payloadViewer` на секрет
описаны в `infra/yc/terraform/nexus/`; там же — почему ключ создаётся руками, а
не Terraform.

Потребители подключаются через `ClusterSecretStore` в своём юните: store
кластерный, а ключ доступа остаётся в одном namespace.

## Ограничения

- **Ключ доступа создаётся вручную** и не переживает пересоздание кластера: после
  него Secret `yc-auth` нужно положить заново.
- **Один экземпляр каждого пода.** Отказ узла — короткий простой синхронизации;
  секреты, уже попавшие в Kubernetes, остаются на месте.
- **Lockbox — внешняя зависимость.** Недоступность API не мешает работать
  приложениям, но новая версия секрета не приедет до восстановления доступа.

# Uptime Kuma (Terraform)

Мониторы, теги, status page, прокси и настройки Uptime Kuma. Gatus
(`apps/gatus/config/config.yaml`) — источник правды: URL и ожидаемые результаты
проверок здесь его зеркало.

## Запуск

Провайдер ходит в Kuma по Socket.IO через `https://kuma.<домен>`, поэтому с
macOS нужен маршрут в домашнюю сеть (Tailscale). Учётная запись администратора
Kuma не должна быть с 2FA: провайдер её не поддерживает.

```sh macOS
cd terraform/uptime-kuma
terraform init
terraform plan
terraform apply
```

`terraform.tfvars` читается при каждом plan и apply, поэтому параметры вводятся
один раз и интерактивных вопросов Terraform не задаёт. Вводить заново в каждом
новом терминале нужно только реквизиты: это переменные окружения, и
`~/.vault-token` живёт 24 часа, так что `vault login` всё равно приходится
делать заново. Реквизиты лежат в Vault по пути `kv/uptime-kuma/sync` (ключи
`UPTIME_KUMA_USERNAME` и `UPTIME_KUMA_PASSWORD`).

Имена переменных окружения у провайдера другие, без подчёркивания после
`UPTIME`: `UPTIMEKUMA_USERNAME` и `UPTIMEKUMA_PASSWORD`. Ключи в Vault
подчёркивание сохраняют — это два разных пространства имён, и путать их
опасно: с именами с подчёркиванием провайдер молча остаётся без логина.
Без попадания в историю оболочки:

```sh macOS
export UPTIMEKUMA_USERNAME=…
read -rsp "Kuma password: " UPTIMEKUMA_PASSWORD UPTIMEKUMA_PASSWORD && echo
export UPTIMEKUMA_PASSWORD
```

С пустыми реквизитами провайдер не сообщает об этом: клиент пропускает логин и
ждёт списки мониторов, которых без логина не будет. Ошибка выглядит как
недоступность Kuma или непроброс websocket через обратный прокси — отсюда
диагностика вводит в заблуждение.

В state реквизиты не попадают: аргументы блока `provider` Terraform не
сохраняет. `UPTIMEKUMA_ENDPOINT` задавать не нужно, endpoint собран из
`var.domain`.

## Значения

```hcl
domain   = "example.com"     # тот же домен, что в platform/homelab
timezone = "Asia/Yekaterinburg"
```

Адрес сервера отдельной переменной задавать не нужно: он берётся из
`data "external"`, которая на машине, где запущен Terraform, спрашивает
`dns.<домен>` через локальный DNS. Kuma проверяет Xray-вход и Xray-прокси по
этому адресу, а DNS-мониторы через Technitium — по тому же. Если discovery не
сработал (например, macOS не видит домашнюю зону), адрес можно задать явно:

```hcl
host_ip = "192.0.2.10"
```

ClusterIP kube-dns тоже не нужен: Kuma сама резолвит имя резолвера, поэтому
в мониторах «через CoreDNS» стоит `kube-dns.kube-system.svc.cluster.local`.

## Первый apply

Модуль применялся с нуля: база Uptime Kuma была пересоздана вместе с
переносом на внешнюю MariaDB, импортировать было нечего, поэтому
`imports.tf` в модуле нет. План содержал 62 создания и 0 импортов.

Если модуль всё же применяется к существующей базе Kuma, сначала нужно
разово наполнить её — либо импортом, либо ручным переносом: пустая база
означает, что все 62 монитора будут созданы заново вместе с потерей истории
проверок и ручных настроек из UI.

После apply `terraform plan` обязан быть пустым. Если после apply что-то
остаётся — это рассинхрон конфигурации, а не ожидаемое поведение.

Проверить после apply:

1. `terraform plan` пуст.
2. Мониторов 62, и их имена совпадают с `locals.tf`. Status page опубликована
   и отдаёт 200 на `/api/status-page/homelab`. Провайдер версии 0.4.0 не умеет
   управлять `published`, `show_certificate_expiry` и `show_tags`, поэтому
   публикацию и отображение срока сертификата приходится задать один раз в UI.
3. В UI Kuma у мониторов на месте уведомления: провайдер ими не управляет, и
   уведомления заводятся вручную.
4. Мониторы `Mailserver` и `Paperless` могут оказаться DOWN: их корни отдают
   302, а Gatus проверяет 200. Если так — это расхождение исходной проверки,
   и правится либо здесь, либо в Gatus.

## Проверки тела ответа

17 мониторов проверяют не только код ответа. В Gatus это `[BODY].field == value`
или `[BODY] == pat(*x*)`, в Kuma — `json-query` с выражением jsonata либо
`keyword` с подстрокой.

Точное сравнение не-JSON ответа через `json-query` не проходит: значение
разбирается `JSON.parse`, а у ответа вида `OK\n` остаётся хвост перевода строки и
`==` не срабатывает. Поэтому там, где Gatus сравнивает точно
(`VictoriaMetrics`, `vmagent`, `Jellyfin`, `Navidrome`, `Zitadel`), стоит
`json_path = "$trim($)"` с `==`: jsonata срезает пробелы по краям, и сравнение
получается таким же строгим, как в Gatus.

Для `Contains`-проверок Gatus'а (`WUD`, `Seafile`, `Synapse`, `Talk signaling`)
достаточно `keyword` с подстрокой — это ровно то же сравнение.

`Nextcloud` в Gatus проверяет три условия (`installed`, `maintenance`,
`needsDbUpgrade`), а json-query монитор держит одно, поэтому проверяется
`installed`. Остальные два остаются строгими в Gatus, который и алертит.

Смена типа монитора — это пересоздание: Kuma не меняет тип на месте, и
heartbeat'ы нового монитора начинаются с нуля.

## Чего модуль не делает

- **Уведомления.** Ни `ntfy`, ни `telegram` в Terraform не заводятся: их
  реквизиты попали бы в state открытым текстом. Алертинг остаётся у Gatus.
- **Срок действия сертификата.** Gatus роняет endpoint, если сертификат
  истекает раньше чем через 168 часов. У HTTP-мониторов Kuma условий нет.
  Ближайшее, что есть, — `tls_expiry_notify_days = [7]`: уведомление за неделю
  без изменения статуса.
- **Время ответа.** Условие `[RESPONSE_TIME] < 5000` перенести нельзя.
- **Порог алерта.** У Gatus `failure-threshold: 3` и `success-threshold: 2`, у
  Kuma порог до перехода в DOWN — это `max_retries`, а аналога
  success-threshold нет.

## Интервал

Провайдер проверяет `interval >= 20`, поэтому External-контур проверяется раз в
20 секунд вместо 15. Сама Kuma разрешает и меньше, но обойти проверку провайдера
нельзя.

## Старый механизм

Механизм в кластере (`monitors.yaml`, `sync-monitors.ts`, CronJob) снесён: он
описывал те же мониторы, что и модуль, и при запуске переписывал бы их в своё
состояние. Единственный владелец мониторов — этот каталог.
